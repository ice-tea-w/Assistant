# 从设计方案到代码：怎么写这个 Python 模块

> 阅读对象：要接手实现《桌面助手 — 文件安全模块设计方案》的开发者。
> 配套代码：仓库根目录 `file_guard/`，115 个测试全绿（含 33 条安全评审回归）。

---

## 1. 先定分层，再写代码

设计稿第 8 页给的是五层架构。落到 Python 包，一一对应：

```
┌─────────────────────────────────────────────────────────────┐
│ 桌面助手主程序（Electron / WPF / Tauri / Python，均可）        │
│   只做两件事：调接口、把 {"ok":false} 转成 UI 提示            │
└───────────────┬─────────────────────────────────────────────┘
                │ ① 子进程 CLI（--json）  ② 本机 HTTP + token  ③ import
┌───────────────▼─────────────────────────────────────────────┐
│ 交互层（UI）      cli.py / 右键菜单 / 桌面助手弹窗            │
├─────────────────────────────────────────────────────────────┤
│ 业务层            scan.py（检测） audit.py（审计）           │
│                   backup.py（备份） watch.py（监听/自动加密） │
├─────────────────────────────────────────────────────────────┤
│ 底层安全层        crypto.py（PBKDF2 / AES-256-GCM / 密钥管理）│
│                   integrity.py（模块自校验）                  │
├─────────────────────────────────────────────────────────────┤
│ 文件系统层        只读写用户授权路径；系统目录自动跳过          │
└─────────────────────────────────────────────────────────────┘
```

一条铁律：**业务层不直接碰密码学原语，底层不碰业务语义**。这样以后换算法（比如加
Argon2、换 XChaCha20-Poly1305）只改 `crypto.py`，四个功能都不用动。

## 2. 第 6~7 页的四大子模块怎么实现

### 2.1 文件加密解密（`crypto.py`）

**不要**写成"读整个文件 → AES 加密 → 写出去"。大文件会吃满内存，而且没有防截断能力。
这里用的是分块 AEAD（STREAM 构造）：

```python
# 每个容器：80 字节头部 + 若干「密文块 + 16 字节 GCM tag」
header = MAGIC + version + kdf_id + cipher_id + flags \
       + iterations + chunk_size + salt(16) + nonce_prefix(8) + plaintext_size(8) \
       + SHA256(前 48 字节)
# 每块：
nonce = nonce_prefix + struct.pack(">I", index)          # 12 字节，全局唯一
aad   = header + struct.pack(">IB", index, is_final)     # 绑定头部、块号、是否末块
ct    = AESGCM(key).encrypt(nonce, plaintext_chunk, aad)
```

为什么这么设计：

| 攻击/故障 | 被什么挡住 |
| --- | --- |
| 改密文任意一位 | GCM tag 校验失败（`InvalidTag` → `DecryptionError`） |
| 改盐/迭代次数/文件大小 | 头部有 SHA-256，且头部是每块 AAD 的一部分 |
| 截断文件 | 末块的 `is_final=1` 参与 AAD，截断后按末块解会失败；长度不足也直接报错 |
| 交换/重排分块 | `index` 参与 AAD，换位置就解不开 |
| 追加垃圾数据 | 读完声明长度后还有剩余字节 → `CorruptContainerError` |
| 解密中途失败留半截明文 | 先写 `.part` 临时文件，全部校验通过才 `os.replace` 原子替换 |

密钥派生按设计稿要求"密码永不明文保存、防暴力破解"：

```python
def derive_key(password, salt, iterations=600_000):
    return PBKDF2HMAC(hashes.SHA256(), length=32, salt=salt,
                      iterations=iterations).derive(password.encode())
```

每个容器自带随机盐，所以同一密码加密同一文件两次，密文也不同；密码本身不存，
只存在（可选的）DPAPI 保险箱里——那是 Windows 用当前用户账户加密过的密文。

**密钥文件模式**：生成 32 字节随机文件，取 `SHA-256(文件内容)` 当口令材料。
它不是"把密码写文件里"，而是把高熵随机数当密码用（设计稿第 6 页"两种模式"）。

### 2.2 敏感文件检测（`scan.py`）

关键不是"写几个正则"，而是**控制误报**和**尊重隐私**：

```python
# 身份证：18 位正则 + 加权 mod 11 校验位；银行卡：16~19 位 + Luhn 校验
ID_WEIGHTS = (7, 9, 10, 5, 8, 4, 2, 1, 6, 3, 7, 9, 10, 5, 8, 4, 2)
if ID_CHECK_CODES[sum(int(c) * w for c, w in zip(value[:17], ID_WEIGHTS)) % 11] != value[17]:
    return False
```

- 只扫用户**主动指定的路径**，不提供"全盘扫描"入口（第 6 页红字要求）；
- 系统目录（`%SystemRoot%`、`Program Files`…）、`.fgc`、`node_modules` 等自动跳过；
- 文本按 UTF-8 → GB18030 依次尝试解码；docx/xlsx/pptx 用 `zipfile` 读 XML 抽文本（零依赖）；
- 二进制文件只按文件名提示（"2026年劳动合同.pdf" 也会被标风险）；
- 风险分级取命中项最高级，再按权重算 0~100 分给 UI 排序；报告里样本一律打码；
- 扫描过程支持 `ScanControl` 暂停/继续/停止、`throttle_bps` 限速、线程池、低进程优先级。

### 2.3 操作审计日志（`audit.py`）

设计稿要求"本地保存、加密存储、防篡改、可清空"。实现是"逐条加密 + 哈希链"：

```
记录 i 的明文 = {"ts","event","path","detail","user","host","pid"}
nonce_i = 12 字节随机数（存进行里，同时进 AAD）
ct_i    = AES-256-GCM(log_key, nonce_i, 明文, aad=FGL1 ‖ seq ‖ nonce_i)
h_i     = HMAC-SHA256(chain_key, h_{i-1} ‖ nonce_i ‖ ct_i)      # 链
写入行   = {"seq": i, "n": base64(nonce_i), "h": h_i, "d": base64(ct_i)}
```

- 链用 **HMAC** 而不是裸 SHA-256：攻击者能改一行、重算后面的哈希，但没有密码算不出 HMAC；
- `seq` 连续 + 链校验 ⇒ 删中间一条、调换顺序都会暴露；
- **每条记录独立随机 nonce**（v2 格式）：旧实现用"固定前缀 + 序号"拼 nonce，日志被回滚或
  `meta.json` 被旧版本覆盖后继续追加，会出现同一密钥 + 同一 nonce 加密不同明文 —— AES-GCM 下
  这会同时泄露明文异或值与认证密钥。改成逐条随机后，回滚也不会造成复用；旧 v1 记录仍可读。
- **meta 带签名**：`meta.json` 里的盐/前缀/高水位用密码派生密钥做 HMAC，防"只改 meta"的篡改；
  `next_seq` 高水位比日志长就报"被回滚/截断"；
- 追加前先解密最后一条记录确认密码 —— 错误密码不再能写出一条永远解不开的垃圾记录；
- 尾截断本地无法自证（任何"防删最后几条"都要外部锚点），所以提供 `log head`：
  把链头哈希抄到注册表/另一台设备，再用 `log verify --expected-head` 比对；
- `log clear` 是"归档 + 换新盐/新 nonce 前缀"，不是直接删——否则复用 nonce 会毁掉 AES-GCM 的安全性。
  归档文件名带序号，同一秒内多次 clear 不会互相覆盖。

### 2.4 安全备份与恢复（`backup.py`）

两个关键设计：

1. **内容寻址**：对象名 = `HMAC(主密钥派生的子密钥, SHA-256(明文))`，路径 `objects/ab/<name>.fgc`。
   内容没变 → 索引里直接跳过（增量）；同一内容在多个版本/多个路径出现 → 只存一份（去重）。
   用密钥化哈希而不是明文 SHA-256：否则"某文件是否在备份里"可被确认，低熵内容还能被离线暴力。
   旧版本的明文 SHA-256 对象名继续按索引记录读取，恢复不受影响。
2. **索引也加密**：`index.jsonl` 每行都是 AES-GCM 密文 + 哈希链，所以"什么文件在什么版本"
   不会以明文出现在磁盘上。索引里的 `object` 路径会做严格校验（只允许 `ab/<64hex>.fgc`
   且必须落在 `objects/` 内），防止伪造索引把恢复写到别处。

恢复流程：按原始绝对路径 + 版本号找对象 → 解密到临时文件 → 比对索引里的 SHA-256 →
原子替换回目标 → 还原 mtime。源文件删了也能恢复（路径字符串还在索引里）。

两个容易写错、也踩过坑的点：

- **"备份过程中源文件被改"的检查必须真的生效**：`encrypt_file` 要传 `hash_plaintext=True`
  才有 `sha256` 可比（旧实现传了 `False` 却去比对，等于没检查）；
- **版本号不能用 `len(versions)+1`**：保留策略删掉旧版本后长度会变小，版本号会被复用。

### 2.5 补充：模块自校验（`integrity.py`）与目录监听（`watch.py`）

- 第 10 页"恶意程序篡改安全模块"：`integrity init` 生成 `.py` 哈希清单并用密码派生 HMAC 签名，
  `integrity check` 发现被改就告警；
- 第 7 页"记录打开/修改/删除"：轮询快照能可靠抓"新增/修改/删除"；"打开"事件 Python 侧拿不到，
  由桌面助手在打开文件时主动 `audit.record("open", ...)` 上报（生产可换 ETW / `watchdog`）。

## 3. 怎么接进桌面助手（第 8 页"插件化松耦合"）

### 方式 A：子进程 CLI（最简单）

```python
# 桌面助手(Node/Electron) 侧
const { execFile } = require("child_process");
execFile("python", ["-m", "file_guard", "encrypt", filePath, "--json"],
         (err, stdout) => { const result = JSON.parse(stdout); /* 更新 UI */ });
```

- 模块崩了只是子进程退出码非 0，主程序不受影响；
- 想"随时关闭模块"= 不调用它 / 杀掉子进程。

### 方式 B：本地 HTTP 服务（需要常驻会话）

```bash
python -m file_guard serve --port 8765
```

```jsonc
// POST http://127.0.0.1:8765/rpc   Header: X-FG-Token: <~/.file_guard/service.token>
{"method": "scan", "params": {"paths": ["C:\\code\\file_guard\\合同.docx"], "min_risk": "medium"}}
// → {"ok": true, "result": {"summary": {...}, "files": [...]}}
```

- 只监听 `127.0.0.1`，token 每次启动生成；
- 所有异常（包括未预期异常）都转成 `{"ok": false, "error": {...}}`，服务进程不退出；
- 密码只在服务进程内存里，不写盘。

### 方式 C：Python 主程序直接 import

```python
from file_guard import encrypt_file, SensitiveScanner, AuditLog, BackupStore
```

### 右键菜单（第 8 页交互层）

`scripts/install-context-menu.ps1` 写 `HKCU\Software\Classes\*\shell`，注册"加密/解密"两个动作。
它只是 demo 形态（会弹控制台），正式产品建议用 pythonw + tkinter 对话框，或直接做进桌面助手 UI。

## 5. 安全验收清单（可直接拿去评审）

- [ ] 磁盘上 grep 不到明文密码（`vault.bin` 是 DPAPI 密文）
- [ ] 同一密码加密同一文件两次，密文不同（随机盐）
- [ ] 改密文/截断/追加/换块顺序，解密全部失败且不产生 `.part` 残留
- [ ] 日志被改一行 / 删一条 / 换顺序，`log verify` 返回失败
- [ ] 备份对象密文里 grep 不到原文件名和内容
- [ ] 备份恢复后 SHA-256 与备份时一致
- [ ] 扫描不读系统目录、不写用户文件；敏感样本在报告里已打码
- [ ] 模块异常退出后主程序可继续运行并再次拉起服务
- [ ] `integrity check` 能发现自己被改
- [ ] 代码里没有任何上传/联网逻辑（评审时 grep `requests`/`urllib`/`socket`）

## 6. 常见坑

1. **nonce 复用**：AES-GCM 下同一密钥重复 nonce 会直接泄露明文异或值，并可能恢复认证密钥。
   旧实现 nonce = "随机前缀 + 自增块号/序号"：容器每块有随机前缀，没问题；但**审计日志的
   前缀是按日志文件持久化的**，日志被回滚/删除后继续追加就会复用。现在日志改成每条记录
   独立随机 12 字节 nonce（v2），并在 AAD 与哈希链里都绑定它。
2. **不要"加密整个文件后一次性写"**：大文件内存爆炸，且无法防截断。
3. **临时文件**：解密失败要删 `.part`，否则明文残留在磁盘上；并且要用 `mkstemp` 返回的 fd
   直接写，不要先建文件再按名字 `open()`（共享目录下有符号链接替换的 TOCTOU）。
4. **原子替换**：`os.replace` 只在同一分区原子；临时文件要和目标同目录。
5. **KDF 参数**：迭代次数要写进容器头（换机器也能解）；解密前要限制上限，防止恶意文件用
   10 亿次迭代把你卡死（代码里限制 5,000,000）。审计 meta / 完整性清单同样要限制，
   否则"伪造一份 meta 就能让你跑一天 PBKDF2"。
6. **DPAPI 绑定用户**：换 Windows 账户/换机器解不开，所以它只适合"本机免密缓存"，
   不能当作可迁移的密钥备份。
7. **日志/备份并发**：用文件锁（`O_EXCL` 锁文件）串行化写入，别用线程锁糊弄多进程；
   锁的"过期抢占"要确认持有进程真的退出，否则会抢走慢进程的锁、写出重复 seq。
   另外 `os.open` 在 Windows 上默认是**文本模式**，写二进制随机数据必须带 `O_BINARY`。
8. **索引全量重放**：版本多了以后 `_current_entries()` 是 O(n)，上规模要换成"快照 + 增量"，见第 7 节。
   （当前实现加了进程内缓存，目录批量备份不再 O(n²)。）
9. **"删明文"之前先证明能恢复**：自动加密/瘦身类操作，删除源文件前务必解密校验一遍；
   容器写坏、密钥不对时宁可留下明文也不要永久丢数据。
10. **Windows 目录联结不是符号链接**：`os.walk(followlinks=False)` / `Path.is_symlink()`
    都挡不住 junction，必须额外用 `os.path.isjunction()`（见 `fsutil.is_reparse_point`），
    否则"只扫授权目录"的承诺会在一个链接上破功。

## 8. 安全评审与加固（v0.2）

首版实现做过一轮完整的代码安全评审，共发现 20 项可复现问题（4 严重 / 8 中等 / 8 低危）并全部修复，
新增 33 条回归用例（`tests/test_security.py`），全量 115 个测试通过。评审结论、逐条问题清单、
兼容性影响和残余风险见 **[安全评审与加固.md](安全评审与加固.md)**。

实现里几个值得记住的结论：

1. 审计日志的 nonce 不能"持久化一个前缀 + 序号"，必须每条独立随机（否则回滚即复用）；
2. 本地服务要同时做**回环限制 + Host/Origin 校验 + token 文件 ACL**，三者缺一不可；
3. "只扫授权目录"必须显式处理 Windows 目录联结，`os.walk` 的默认行为不够；
4. 任何"删除源数据"的操作前，都要先验证目标数据可完整恢复。
