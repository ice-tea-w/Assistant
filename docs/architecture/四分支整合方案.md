# 四分支整合方案：三条支线怎么落回主模块

> 状态：**分析稿** · 2026-10-29
> 对象：`main` / `feature/plugin-market`（插件市场）/ `qianju`（设备同步·传输）/ `file_guard`（文件安全原型）
> 依据：`文件系统四模块-关联与方案.md`（M1–M4 职责、契约、分期）+ 实测（mirror clone + `merge-tree` + 试合并）

## 0. 结论先行

1. **三条支线不是"三个平行功能"，而是四模块里三个不同模块的实现**：插件市场 = M4，
   设备同步 = M2（且只做到"渠道目录通道"），file_guard = M3 的"保护"能力（参考实现，Python）。
2. **合并的难点不是文本冲突，是三个"谁说了算"**：主面板导航机制、CMake/测试基线、跨模块契约。
   文本冲突只集中在 `qianju` 一个分支的 5 个文件上，另外两个分支能干净合并——但"能干净合并"不等于
   "该直接合并"（file_guard 会静默顶掉主 README）。
3. **顺序有硬约束**：`plugin-market` 把主面板从 `StackLayout + selectedIndex` 改成 `Loader + selectedKey`。
   这一改动是后面所有"往导航里加页面"的分支的地基。先合插件市场，`qianju` 的冲突从 5 个文件涨到 7 个
   （新增 `MainPanel.qml`、`src/main.cpp`），但那是**一次性、机械的**；反过来先合 `qianju`，插件市场的
   导航重构要在旧结构上重做一遍，代价更高。
4. **file_guard 不进产品构建**。它是宿主假设为 Python（文档里按 PyQt/tkinter 写）的独立原型；
   值得吸收的是 FGC1 容器格式、审计链、DPAPI 密钥与 junction 隔离四条**设计**，代码按参考实现归档。
5. **每条支线单独一个 PR、单独验收**，不要"三合一"一次合。合完 `plugin-market` 与 `qianju` 后，
   主模块才第一次同时具备 M1（已有）+ M2（通道）+ M4（插件）三个门面；M3 的判定/账本仍缺。

### 1.1 各支线的真实形态

**`feature/plugin-market`（M4）**
插件是 **QML 包**（`plugin.json` + QML 页面），不是 `.dll`：`runtime` 字段只有 `"qml"` 可用，`"native"` 解析但拒装。
模块分工清楚：`PluginRegistry`（磁盘布局/安装目录）、`PluginCatalog`（市场索引，内置 `seed-index.json`，
可被 `ASSISTANT_MARKET_URL` 覆盖）、`PluginInstaller`（zip 安装 + zip-slip 防护 + sha256）、`PluginLoader`
（QML 加载、给每个插件一个 `PluginHost`）、`PluginManager`（门面，唯一持有四个协作者）、`SemVer`、`PluginArchive`、`PluginManifest`。
宿主面 `PluginHost` 是每插件一个实例，只暴露只读属性 + 少量动作，插件写盘只能进自己的 `data/`。

**`qianju`（M2）**
核心资产是 `ITransport` 抽象（`probe/listRemote/fetch/push/removeRemote/tryLock`）与 `FolderTransport`
（"投递区 = 一个本地/网盘同步文件夹"），加上 `SyncEngine`（三方差集差量）、`ConflictResolver`（冲突副本）、
`DeliveryNaming`、`PathGuard`（路径穿越/保留名/junction）、`SyncDatabase`。
**注意：它没有任何网络代码**——`grep QTcpSocket|QTcpServer|QSslSocket` 在 `src/`、`include/` 零命中。
设计文档 §3.3 写了 `LanTransport(priority=0) → FolderTransport(priority=10)` 的降级链，§4.4 甚至定义了
`ASYN` 帧协议，但 `LanTransport` 未实现。所以它现在等于提案里的 **M2② 渠道目录通道**，不是 M2③ LAN。

**`file_guard`（M3 的"保护"面）**
Python 独立 CLI：FGC1 分块 AES-256-GCM 容器（80 字节头、每块 `AAD = header||index||is_final`）、
PBKDF2 + keyfile / DPAPI `vault.bin`、HMAC 哈希链审计（`h_i = HMAC(chain, h_{i-1}||nonce||ct)` + `next_seq` 高水位）、
内容寻址加密备份、5 s 轮询 watch、本机 HTTP `serve`。无 SQLite、无基线概念；
`integrity.py` 是**模块自校验**（`.py` 哈希清单），不是文件完整性账本。

## 2. 逐支线的整合路径

### 2.1 `feature/plugin-market` → M4（第一个合）

**能进 main 的形态**：代码基本现成，M0–M4 有独立测试工程（`tests/plugin_core_tests.cpp` 2681 行，无框架、手写断言）。

**合之前要做的三件裁剪**（都是提案 §4.4 的硬要求，不是优化）：

| # | 缺口 | 处理 |
|---|---|---|
| 1 | 无 **capability 校验**：`manifest.permissions` 只是解析出来的字符串列 | 能力名固定成枚举/常量表，宿主**每次** API 调用前校验；版本不兼容与能力不足必须是两个错误码 |
| 2 | 无 **`IHostApi` / 宿主解析 actor**：插件是 QML，天然拿不到 `actorId`，但 `PluginHost` 没有"调用主体"概念 | 明确 `PluginHost` 就是 v1 的 IHostApi；所有能落到文件/网络的动作都要带宿主已知的 pluginId，不允许参数里传身份 |
| 3 | 无**安装来源策略**：`PluginInstaller` 校验 sha256 与 zip-slip，但没有"信任的加载位置"与签名 | v1 明确"用户主动安装的完全信任模型"，把这句话写进 `PluginsPage` 的安装确认框与 README，不要留"看起来像沙箱"的 UI |

**顺带的公共收益**（随本分支一起进，见 §3）：主面板导航 `selectedIndex → selectedKey` + `Loader`；
`CMakeLists.txt` 里 `VCPKG_INSTALLED_DIR` 取代硬编码 `C:/vcpkg`；`AUTORCC` 资源依赖显式声明。
后者修的是"改了 QML 但跑起来还是旧界面"这个已知坑，与插件无关，但只有这个分支做了。

### 2.2 `qianju` → M2②（第二个合，必须先 rebase）

**能进 main 的形态**：`ITransport` + `FolderTransport` + `SyncEngine` + `SyncPage` 作为 M2 的**第一个交付单元**
（提案 §4.2 的"② 渠道目录通道"）——但提案要求它排在"① 传输作业内核"之后。两条路：

- **推荐**：把 `qianju` 定位成"通道实现"，作业内核（状态机/分块/最终哈希/隔离区/恢复）作为 M2① 另开分支，
  先落 `ITransport` 接口与 `FolderTransport`，等 M2① 到位后 `SyncEngine` 改为作业内核的客户端。
- 不推荐：直接把 `SyncEngine` 当作业内核交付——它没有分块、没有最终内容哈希、没有接收隔离区，
  与提案 §4.2"未完成校验的文件不得进入正式索引"直接冲突。

**合之前要做的**：

| # | 项 | 说明 |
|---|---|---|
| 1 | rebase 到 `plugin-market` 之后的 main | `MainPanel.qml` 的 `SyncPage{}` 改成往 `builtinNav` 加 `{key:"sync",...}` + `sourceFor("sync")` 分支 |
| 2 | `ConfigManager` 两组键并存 | 冲突只是"两边都在同一个位置加属性"，保留 `fileIndex*` 与 `sync*` 两组即可；但要注意配置是**整文件重写**，需确认未知键不会丢 |
| 3 | `src/main.cpp` 装配点重排 | 插件装配在 panelEngine 之前，`SyncBridge` 在 DB 之后、`TrayManager` 之前；两者都要在 `panelEngine.load()` 前完成 context property 注入 |
| 4 | 删除未实现的 `LanTransport` 承诺 | 设计文档 §3.3/§4.4 保留为"下一步"，但代码/配置里不要出现 `syncPeerAddress/syncPort` 这类假开关（现在是"预留"） |
| 5 | 测试入口统一 | 它把 `enable_testing()` + QTest 的 `assistant_tests` 塞进根 CMake，与 main 已有的 ctest 目标并存 |

### 2.3 `file_guard` → M3（不合并代码，只归档 + 对表）

**不进 main 的三条理由**：宿主假设是 Python（文档按 PyQt/tkinter 写）；无 SQLite（提案要求 `security.db` 为权威库）；
`scan.py` 读正文做内容匹配（提案已决策"敏感发现默认关闭，先做路径/名称规则"）。

**要吸收的四条设计**：

| 设计 | 为什么值得抄 |
|---|---|
| FGC1 容器头 + 每块 `AAD(index, is_final)` | 防截断/防换块序/防追加，是保险箱 v1 最容易做错的地方 |
| 审计链 `HMAC(chain, h_{i-1}||nonce||ct)` + `next_seq` 高水位 + `log head` 外部锚点 | 满足"删行可检"，且不需要可信硬件 |
| DPAPI `vault.bin` 缓存数据密钥 | 提案 §7 选的正是这条路（`CryptProtectData`） |
| `is_reparse_point` 在四条枚举路径统一跳过 junction | 与 A1 踩的 `NoSymLinks` 挡不住 junction 同源 |

**三处必须先对表再写 C++**：① 提案要求**恢复码**，原型没有；② 提案要求**文件名加密**，原型是
`合同.docx.fgc` 原名留盘；③ 审计要落 `security.db`（权威库、分级持久化），原型是加密 JSONL。

**归档方式**：`docs/reference/file_guard/`（3 篇文档 + README）+ `tools/file_guard/`（源码，带本地 `.gitignore`）；
删 26 个 `.pyc`、`scripts/_check.json`、`docs/框架临时验证报告.json`；`合同.docx` 移 `tests/fixtures/` 或改脚本生成；
**保留主 README**，单独一个 `chore(repo):` 提交完成整理。

## 3. 三处必须先统一的公共设施

这三件事三个分支都碰，且**答案只能有一个**，否则每合一次就要重做一次。

### 3.1 主面板导航：`selectedKey` + `Loader`（由 `plugin-market` 定义）

现状：`main` 是 `StackLayout` + `navItems` 数组 + `selectedIndex`（设置页硬编码 `=== 3`）。
`qianju` 在同一个模型上又加了一条 `settingsIndex: navItems.length` 的补丁。
`plugin-market` 直接换成"key 为准 + `Loader` 按 key 算 source + 插件页由 C++ 创建"。

**理由**：页面数量变成运行时可知（插件贡献页面），索引对齐必然失效。这一改动应由第一个需要动态页面的分支
（插件市场）引入，其他分支 rebase 到它上面，而不是各自打补丁。

### 3.2 构建：`VCPKG_INSTALLED_DIR` + `miniz` 依赖

两个分支都修了 `qt.conf` / `run.bat` 里硬编码的 `C:/vcpkg`，写法不同：

| 分支 | 写法 |
|---|---|
| `plugin-market` | `${VCPKG_INSTALLED_DIR}/${VCPKG_TARGET_TRIPLET}` ✅ |
| `qianju` | `${VCPKG_INSTALLED_DIR}/x64-windows`（硬编码 triplet）+ `FATAL_ERROR` 守卫 ✅ |

**取两者并集**：用 `${VCPKG_TARGET_TRIPLET}`，保留 `if(NOT VCPKG_INSTALLED_DIR) message(FATAL_ERROR ...)`。
另外插件市场新增 `find_package(miniz CONFIG REQUIRED)`（Qt6 没有公开 zip API），**本机 vcpkg 尚未安装
miniz**（`C:\vcpkg\installed\x64-windows\share\miniz` 不存在），合入前必须先
`vcpkg install miniz:x64-windows`，否则 configure 直接失败。

### 3.3 测试入口：一个 `tests/`，QTest + ctest

三套并存是当前最脏的部分：

| 来源 | 现状 |
|---|---|
| `main` | 根 CMake 里 `enable_testing()` + `assistant_golden` / `assistant_a3` / `assistant_bench` 三个独立程序 |
| `qianju` | 根 CMake 里再加一段 `enable_testing()` + QTest 目标 `assistant_tests`（编 `tests/test_sync.cpp`） |
| `plugin-market` | 独立 CMake 工程 `tests/CMakeLists.txt`（自带 `project()`，无测试框架，手写断言），与根工程不联动 |

**统一方案**：`tests/CMakeLists.txt` 作为子目录（`add_subdirectory(tests)`），统一用 `Qt6::Test`，
`qt_add_executable` + `add_test` 注册进 ctest；现有三个 acceptance 程序保留为"验收程序"，另立
`acceptance/` 或继续留在 `tests/` 但用 `add_test` 区分标签。`file_guard` 的 Python 测试若归档进
`tools/file_guard/`，则不进 ctest。
**执行时机：P2**（两套 harness 到那时才同时存在，提前统一只能靠猜）。

## 4. 落地顺序

```
P0  chore(repo): 推送 main · .gitignore · 删残留分支 · 契约骨架   （无业务改动，不动 CMake 业务逻辑）
      │
P1  feat(plugin-market): M4 骨架 + 导航 key 化 + CMake 基线修复   （第一个支线 PR）
      │   ├─ 前置：vcpkg install miniz:x64-windows
      │   └─ 验收：M0–M4 用例 + 安装/卸载/禁用 + 插件页出现在导航
      │
P2  feat(sync): ITransport + FolderTransport + SyncPage           （rebase 到 P1 之上）
      │   ├─ 冲突：MainPanel.qml / main.cpp / ConfigManager / CLAUDE.md / devlog
      │   ├─ 顺带：测试入口统一（两套 harness 到这一步才同时存在）
      │   └─ 验收：单机 --instance 双实例 + 三方差集 + PathGuard 拒绝用例
      │
P3  chore(repo): file_guard 归档到 docs/reference + tools/        （不参与构建）
      │
P4  M2① 传输作业内核 / M3-p1 判定与账本（新分支，按提案 §6）
```

**为什么 P1 在 P2 之前**：P1 决定导航模型，P2 的 UI 改动只是"在 key 表里加一行 + 一个 sourceFor 分支"。
反过来，P2 先合会让 P1 的 `Loader` 重构与 `SyncPage` 的 `StackLayout` 插入正面冲突，且冲突解决方向不唯一。

**为什么 CMake 修复随 P1 走、测试统一随 P2 走**：两处改动都在"第二个分支进来时"才有确定答案。
CMake 的 `VCPKG_INSTALLED_DIR` 由插件市场分支写得更完整（用 `VCPKG_TARGET_TRIPLET`），先单独做一遍
只会和它撞同一个 hunk；测试入口要等 `qianju` 的 QTest 目标进来看清两套 harness 的形状，才能一次收敛。
唯一适合提前做的是**非构建性的仓库卫生**（`.gitignore`、删残留分支、契约骨架），它们不与任何分支的 diff 重叠。

## 5. 与四模块提案的差距清单（合并后仍需补）

## 6. 风险与不做的事

| 风险 | 处理 |
|---|---|
| 三个分支合完，四模块契约仍是空的 | P0 之后先落 `include/contract/FileRef.h` 的**语义**（可先只有结构体 + 注释），再合 M2/M4，否则两边各自定义"文件句柄" |
| `qianju` 的 `SyncEngine` 被当成传输内核 | 明确它只是"通道 + 差量"，不承载分块/校验/恢复；否则 M2① 的验收会退化成补丁 |
| file_guard 的 Python 代码"顺手"进了产品构建 | 归档目录不参与 CMake；`requirements.txt` 移出根目录 |
| `plugin-market` 的 `PluginHost` 被当成沙箱 | UI 与文档明确"完全信任、进程内"；不承诺能力隔离 |
| 一次 merge 三个分支 | 禁止：每个支线单独 PR + 单独验收，冲突各自解决 |

**不做**：把三条支线改写成"一个大分支"；在 main 上直接 `git merge` 后手工在冲突文件里做架构决策
（决策应发生在 PR 描述与本文里，而不是冲突标记里）。
