# 插件市场 · 整体模块框架

> 日期：2026-10-05
> 定位：**高层模块框架**（HLD）。回答四个问题——系统由哪些模块组成、各自边界在哪、依赖朝哪个方向、数据怎么流。
> 本文**不含代码、不含字段 Schema、不含错误码、不含排期**。那些在下层文档 `插件市场功能设计.md`（实现级设计 / LLD）。
> 形态前提：插件是 **QML/JS 插件包**（不是 C++ DLL），论证见下层文档 §3 D1。
> 机制来源：DSH 插件管理器的调研结论见下层文档 §1。

---

## 1. 先定问题域：这个功能其实在解决三个独立问题

把"插件市场"拆开，它同时在做三件互不相干的事，混在一起就会写成一坨：

| # | 问题 | 本质 | 对应模块组 |
|---|---|---|---|
| ① | 插件**从哪来** | 分发：把远端的东西拿到本地 | **来源侧** —— `PluginCatalog` |
| ② | 插件**怎么管** | 生命周期：装 / 启 / 停 / 卸，以及"当前是什么状态" | **生命周期侧** —— `PluginInstaller` + `PluginRegistry` + `PluginLoader` |
| ③ | 插件**能干什么** | 能力：装进来之后往宿主里挂什么 | **能力侧** —— `PluginHost` + 贡献点 |

UI 只是这三组的投影。

**这条切分是整个框架的地基**：页面可以换（列表页 → 详情页 → 将来命令行）、索引源可以换（GitHub Pages → 自建 API）、插件形态可以换（QML → 进程隔离），但这三组模块的职责不该跟着变。

反向检查很有效：**一旦 UI 里出现了"下载""解压""写 plugins.json"这类动作，就是分层破了**——不是因为代码丑，而是因为换 UI 时你会把业务逻辑复制一遍。

## 2. 五层结构

```
┌──────────────────────────────────────────────────────────────────────┐
│ L1  表现层  Presentation                                              │
│     PluginsPage · PluginCard · PluginDetailDrawer · PluginInstallDialog│
│     只认"属性 + 方法 + 信号"，不认文件、网络、状态                     │
└───────────────────────────────┬──────────────────────────────────────┘
                                │  context property `plugins`
┌───────────────────────────────▼──────────────────────────────────────┐
│ L2  桥接层  Bridge                                                   │
│     PluginBridge（属性/方法/信号） + PluginListModel（卡片数据）        │
│     只做类型转换与信号转发，不含业务判断                                │
└───────────────────────────────┬──────────────────────────────────────┘
                                │
┌───────────────────────────────▼──────────────────────────────────────┐
│ L3  门面层  Facade                                                   │
│     PluginManager —— 唯一业务入口，也是唯一的"编排者"                   │
│     装完要启用 / 卸载要先停 / 失败要归类 / 视图要合并                   │
└──┬──────────────┬───────────────┬───────────────┬───────────────────┘
   │              │               │               │
┌──▼────────┐ ┌───▼─────────┐ ┌───▼─────────┐ ┌───▼──────────┐
│  L4 能力层                                                      │
│  Catalog   │ │  Installer  │ │  Registry   │ │   Loader     │
│  远端索引  │ │  安装管线   │ │  本地状态   │ │  QML 装载    │
└──┬────────┘ └───┬─────────┘ └───┬─────────┘ └───┬──────────┘
   │              │               │               │
   └──────────────┴───────┬───────┴───────────────┘
                          │
┌─────────────────────────▼────────────────────────────────────────────┐
│ L5  基础设施  Infra                                                  │
│  HTTP · 文件原子写 · 解压 · 哈希 · 版本比较 · 清单解析 · 日志           │
│  不知道"插件"这个概念存在                                             │
└──────────────────────────────────────────────────────────────────────┘

                 ┌──────────────────────────────┐
                 │  插件运行时边界                │
                 │  PluginHost（插件唯一可见面）  │  ← 由 Loader 创建并注入
                 └──────────────────────────────┘
```

| 层 | 允许依赖 | 明令禁止 |
|---|---|---|
| L1 表现层 | L2 暴露的属性/方法/信号 | 直接调 L4、碰 `QFile`/`QNetworkAccessManager` |
| L2 桥接层 | L3 门面 | 写任何业务分支（"如果没装就…"） |
| L3 门面层 | L4 + L5 纯工具 | 自己做 IO、自己解析 zip |
| L4 能力层 | L5 + 纯工具模块 | **互相调用**（唯一的编排点是 L3） |
| L5 基础设施 | Qt / spdlog / nlohmann / miniz | 引用任何"插件"类型 |

### 2.1 最重要的两条架构规则

**规则 A：L4 之间不允许互相调用，全部由 L3 编排。**

看起来"装完顺手启用"是 Installer 的活，但如果 Installer 直接调 Loader，就产生了一条 `Installer → Loader` 的硬依赖：

- 换 Loader（比如将来改成进程隔离）时，Installer 要跟着改；
- "装完是否自动启用"这个业务决策就藏进了 Installer，UI 无法表达"只装不启用"；
- 测试 Installer 时必须构造一个真 Loader。

把顺序知识集中在 `PluginManager` 里，代价是门面多几行编排，收益是每个能力模块都能独立替换、独立测试。

**规则 B：状态只能由归属模块写。**

`plugins.json` 只有 `PluginRegistry` 能写；`plugins/<id>/` 包目录只有 `PluginInstaller` 能写（`PluginHost` 只能写自己的 `data/`）；插件对象只有 `PluginLoader` 能创建和销毁。

这条规则的实际价值：**排查"为什么状态不对"时，永远只有一个地方要查。**

## 3. 模块清单

| 模块 | 层 | 一句话职责 | 有状态？ | 关键依赖 |
|---|---|---|---|---|
| `SemVer` | L5 纯工具 | 版本解析、比较、范围匹配 | 无 | — |
| `PluginManifest` | L5 纯工具 | 解析并校验 `plugin.json` | 无 | `SemVer` |
| `PluginRegistry` | L4 能力 | 本地已装状态 + 目录布局，**唯一真源** | 是（内存 + `plugins.json`） | L5 原子写 |
| `PluginCatalog` | L4 能力 | 远端索引：拉取、缓存、离线降级、过滤 | 是（内存 + 缓存文件） | L5 HTTP |
| `PluginInstaller` | L4 能力 | 安装管线：下载→校验→解压→校验清单→提交 | 是（进行中任务） | L5 HTTP/解压/哈希 + `Registry` + `Manifest` |
| `PluginLoader` | L4 能力 | QML 装载/卸载，贡献登记与撤销 | 是（已装载集合） | Qt QML + `PluginHost` |
| `PluginHost` | L4 边界 | **插件代码唯一可见的 API 面** | 是（插件自己的配置） | L5 文件/日志 |
| `PluginManager` | L3 门面 | 编排四个能力模块，产出统一的"插件视图" | 是（视图缓存） | 上面全部 |
| `PluginBridge` | L2 桥接 | QML ↔ C++：属性、方法、信号 | 否 | `PluginManager` |
| `PluginListModel` | L2 桥接 | 卡片数据模型（角色化） | 是（视图数据） | — |
| QML 页面 ×4 | L1 表现 | 列表 / 卡片 / 详情抽屉 / 安装对话框 | 是（UI 态） | `PluginBridge` |

> `SemVer` 和 `PluginManifest` 之所以单独拎出来叫"纯工具"，是因为它们**不持有任何状态、不碰 IO、不依赖 Qt 之外的东西**——可以脱离整个应用单独写单测。项目里 `FuzzyMatcher`、`Calculator` 就是同一个定位，沿用这个惯例。

## 4. 模块契约

契约只写四件事：**吃什么、吐什么、守什么不变量、失败怎么往外传**。这是"模块框架"最该定死的部分——接口签名会变，契约不该变。

### 4.1 `PluginRegistry`（本地状态，唯一真源）

| 项 | 内容 |
|---|---|
| 输入 | 插件 id + 状态变更（装上 / 启用 / 停用 / 记问题 / 移除） |
| 输出 | 全量已装清单；各插件目录与数据目录的路径 |
| 不变量 | ① 内存与文件始终一致（写失败必须保持旧文件完整）② 只认 id，不认路径 ③ 任何读操作都不改状态 |
| 失败形态 | 写失败 → 返回错误但**不改内存**（宁可这一操作没发生，也不要内存与磁盘分叉） |
| 谁不能碰 | 其他模块不得直接写 `plugins.json` |

### 4.2 `PluginCatalog`（来源侧）

| 项 | 内容 |
|---|---|
| 输入 | "刷新"（可带强制标志）、筛选条件 |
| 输出 | 可安装条目列表 + 一个"当前是新鲜还是缓存"的事实 |
| 不变量 | ① 有缓存就一定有结果（网络失败降级到缓存，不返回空）② 永远能告诉调用方"这份数据是什么时候的" ③ 拉取失败绝不影响已装插件 |
| 失败形态 | 不抛错，只降级：离线 / 缓存过期 / 用内置 seed。**"没有市场数据"和"网络错误"是两个不同的事实，必须分开表达** |

### 4.3 `PluginInstaller`（安装管线）

| 项 | 内容 |
|---|---|
| 输入 | 一个安装源（市场条目 id / 本地 zip / 本地目录）+ 取消请求 |
| 输出 | 阶段进度、日志行、最终结果（成功 / 失败码 + 失败阶段） |
| 不变量 | ① **提交前任何失败都不留半装状态**（临时目录清干净、状态文件一个字节没动）② 提交后失败只降级为"装上但有 problem"，不回滚文件 ③ 同一时刻只有一个安装任务 ④ 取消在提交前一定生效，提交后一定失效（且明确告知） |
| 失败形态 | 用"阶段 + 失败码"表达，不用异常穿越层 |
| 归属 | 唯一能写 `plugins/<id>/` 的模块 |

> "提交后失败不回滚"这条是从 DSH 抄的，也是最反直觉的一条：**"装上了但加载不了"不是"安装失败"**。合成一个结果会让用户陷入"重装 → 又失败 → 再重装"的循环，而实际上文件是好的、只是代码有 bug。分开表达，用户才能做出正确动作（卸载 / 反馈作者）。

### 4.4 `PluginLoader`（运行时装载）

| 项 | 内容 |
|---|---|
| 输入 | 已校验的清单 + 插件目录 |
| 输出 | 已装载的插件对象集合；装载/卸载事件 |
| 不变量 | ① 装载失败必须回到"未装载"，不留半初始化对象和泄漏的上下文 ② 卸载必须触发"贡献撤销"（导航项、命令、provider 全部撤干净）③ 装载失败绝不能让宿主崩溃或退出 |
| 失败形态 | 返回错误文本（给"问题标签"用），不抛异常 |
| 归属 | 唯一能创建/销毁插件对象的模块 |

### 4.5 `PluginHost`（插件可见面 —— 未来的隔离边界）

| 项 | 内容 |
|---|---|
| 输入 | 插件自己的调用（日志、读写自己的配置、弹提示、取路径） |
| 输出 | 数据与动作的结果 |
| 不变量 | ① 插件**拿不到**宿主内部对象（registry、manager、engine 一律不给）② 插件只能写自己的 `data/` ③ 所有能力必须"按需暴露"，不能是"把宿主 QObject 一塞了事" |
| 为什么重要 | 这是全系统**唯一一处**设计成"可被替换为跨进程协议"的接口。将来要做隔离，改的是这一层的实现（QObject 调用 → JSON-RPC），插件侧 API 不变 |

> 如果这一层偷懒，把 `PluginManager` 或 `QQmlEngine` 直接当 context property 塞给插件，那么"将来做隔离"就永久变成不可能——因为插件已经能访问全部宿主内部。**这是本项目里最容易一步走错、且以后无法挽回的地方。**

### 4.6 `PluginManager`（门面 / 编排）

| 项 | 内容 |
|---|---|
| 输入 | 来自桥接层的意图（刷新 / 安装 / 启停 / 卸载 / 打开目录） |
| 输出 | 统一的"插件视图"（市场条目 + 本地状态合并后的结果）+ 变更通知 |
| 不变量 | ① 所有状态变更先落盘、后对外可见 ② `problem` 由**观测**产生（装载真失败了才标），不由**声明**产生 ③ 任何一次失败都不能让门面进入不可用状态（下一个操作照常） |
| 失败形态 | 归类为"错误码 + 人类可读补充"，交给桥接层去翻译 |

### 4.7 `PluginBridge` / `PluginListModel`（桥接）

| 项 | 内容 |
|---|---|
| 输入 | QML 的调用 |
| 输出 | 可绑定的属性、可调用的方法、信号 |
| 不变量 | ① **零业务判断**——不判断"能不能装"，只转发 ② 所有跨线程结果回到主线程再发信号 ③ 模型变更只发最小粒度的通知（单行变化不重建整个模型） |
| 失败形态 | 转发为 `toast(level, text)` 或 `installFinished(ok, code, message)` |

## 5. 状态所有权表（框架里最该先定清楚的一张表）

| 状态 | 归属 | 存储位置 | 丢了会怎样 | 怎么恢复 |
|---|---|---|---|---|
| 市场条目 | `PluginCatalog` | 内存 + `market-cache.json` | 只是看不到"可装什么" | 重新拉；无网则用 seed |
| **已装状态** | `PluginRegistry` | `plugins.json` | **真源丢了 = 用户装过什么不知道** | 只能靠扫 `plugins/` 目录反推（降级，丢 `enabled`） |
| 插件文件 | 文件系统 | `plugins/<id>/` | 相当于没装 | 重新下载安装 |
| 运行态 | `PluginLoader` | 内存 | 插件暂时不生效 | 按已装状态重装载 |
| 视图数据 | `PluginListModel` | 内存 | 页面空白 | 从上面三者重建 |
| 安装任务 | `PluginInstaller` | 内存 + 临时目录 | 这次安装作废 | 用户重试（下次启动清临时目录） |

**推论一：除了 `PluginRegistry`，每一层都可以被丢弃重建。** 所以启动流程是"读状态 → 扫文件 → 装载 → 建视图"，崩溃恢复不需要事务日志。

**推论二：`Registry` 的写必须原子。** 因为它是唯一不可重建的东西，写坏了就真的丢了用户数据。这就是为什么它要用"整文件原子替换"而不是"逐字段追加"。

## 6. 数据流

### 6.1 启动流（决定"插件什么时候出现在 UI 里"）

```
main()
 └─ 装配（唯一装配点）
     ├─ PluginRegistry 读 plugins.json
     ├─ 四个能力模块彼此不认识，只被门面持有
     └─ PluginBridge 绑定到主面板 engine
 └─ engine.load(MainPanel.qml)
 └─ PluginManager.loadEnabledAtStartup()
     ├─ 对每个 enabled 的插件：Manifest 解析 → Loader 装载
     │   └─ 失败：标 problem（观测到的），不阻断后续插件
     └─ 通知"导航变了" → QML 重算导航项
 └─ 窗口显示
```

关键约束：**插件装载必须在 engine 之后、窗口显示之前**。engine 之前没有 QML 环境；窗口显示之后加载会出现"导航项晚一拍蹦出来"的闪烁。

### 6.2 浏览流（来源侧，独立于生命周期）

```
UI 刷新 → Bridge → Manager → Catalog
                              ├─ 缓存新鲜 → 直接返回（标记"缓存"）
                              ├─ 缓存过期 → 条件请求（带 ETag）
                              │    ├─ 成功 → 更新缓存（标记"新鲜"）
                              │    └─ 失败 → 用缓存（标记"离线"）
                              └─ 彻底没网且没缓存 → seed 索引（标记"离线"）
                            → Manager 合并本地状态 → ListModel → 卡片
```

设计要点：**浏览流不碰生命周期侧**。没有插件也能浏览市场；装了插件但没网也能管理。两条流只在 `Manager` 合并视图时相遇。

### 6.3 安装流（跨三组模块的唯一流程）

```
UI 点安装 → Bridge → Manager
  └─ Installer：阶段机（校验 → 解析版本 → 下载 → 校验哈希 → 解压 → 校验清单 → 提交）
       ├─ 提交前失败 → 清理临时文件，Registry 未动 → 报错（带失败阶段）
       └─ 提交成功 → Registry 记账
  └─ Manager 编排：Loader 装载
       ├─ 失败 → 保留文件 + 标 problem + enabled 落盘为"用户选择值"
       └─ 成功 → enabled = true 落盘
  └─ 通知：视图变了 + 导航变了
  └─ UI：进度/日志（流式）→ 完成态
```

注意最后一步的**双信号**：`视图变了`（卡片状态）和 `导航变了`（左侧多一项）。这是两个不同的消费者，不能合成一个信号——否则卡片刷新会连带重建导航。

### 6.4 卸载流

```
UI 二次确认 → Bridge → Manager
  └─ Loader 卸载（必须先撤贡献，再动文件）
  └─ Installer/Registry 层：包目录移到 trash、数据目录清理、Registry 移除 → 落盘
  └─ 通知：视图变了 + 导航变了
```

**顺序不可换**：先卸载再删文件。反了的话会出现"文件没了但对象还活着，下一个操作访问已删路径"。

## 7. 目录框架（模块 → 位置，不含实现）

```
include/core/plugin/          ← 领域层声明
  SemVer · PluginManifest      （L5 纯工具）
  PluginRegistry · PluginCatalog · PluginInstaller · PluginLoader · PluginHost
                               （L4 能力）
  PluginManager                （L3 门面）
src/core/plugin/              ← 对应实现

include/ui/ · src/ui/          ← 桥接层
  PluginBridge · PluginListModel

resources/qml/                 ← 表现层（新增文件必须登记进 resources.qrc）
  PluginsPage · PluginCard · PluginDetailDrawer · PluginInstallDialog

resources/market/seed-index.json   ← 离线兜底索引（编译进 qrc）

docs/plugins/                 ← 插件作者文档：怎么写一个插件包（M5 产出）
```

**分层在目录上就应该是看得见的**：`core/plugin` 里不允许出现 `#include` QML 头，`ui` 里不允许出现 `QSaveFile`。以后 code review 只看 include 就能判断分层有没有破。

## 8. 与现有系统的接缝（模块级）

| 接缝 | 现有位置 | 本次改动 | 性质 |
|---|---|---|---|
| 装配点 | `src/main.cpp` | 新增构造顺序 + 注入 context property | **唯一装配点**，其他模块不自己找依赖 |
| 导航 | `resources/qml/MainPanel.qml` | 导航项变成"内置 + 插件贡献"；设置项索引后移 | 唯一需要小重构的现有 UI |
| 命令 | `AppBridge` | 插件命令注册进命令表 | 加接口，不改现有语义 |
| 搜索 | `AppBridge` + 未来的 `ISearchProvider` | provider 贡献（**等 A7**） | 依赖先行 |
| 配置 | `ConfigManager` | 市场地址 / 镜像 / 缓存时长 | 沿用现有持久化风格 |
| 日志 | `Logger` | 插件日志统一前缀 `plugin:<id>` | 不加新日志设施 |
| 数据库 | `Todo/Notes/Clipboard/History` | **完全不动** | 无耦合（插件状态不入 DB） |

> 有一个刻意的取舍：**插件状态不进 SQLite**。项目约定"每个功能一个独立 DB"，这里破例，理由是状态需要整文件原子替换 + 能人工修复（下层文档 §3 D3）。这条破例已写进下层文档的决策记录，将来接手的人能查到原因。

## 9. 能力侧：插件能挂在哪（扩展点框架）

| 扩展点 | 由谁提供 | 由谁消费 | 何时可用 |
|---|---|---|---|
| 页面 | `Loader` 登记，导航消费 | `MainPanel` 导航 + 内容区 | v1 |
| 命令 | `Loader` 登记 | 搜索框命令表 | v1 |
| 搜索 provider | `Loader` 登记 → 桥成 `ISearchProvider` | 搜索融合层 | **等 A7** |
| 自己的设置页 | 插件包内页面 | 插件详情页 | v2 |

框架上的关键点：**扩展点必须"可撤销"**。每个登记动作都要有对应的撤销动作，且卸载时一次性撤干净。否则"停用/卸载后导航里还挂着一个死链"会成为常驻 bug。这条约束落在 `PluginLoader` 的契约里（§4.4 不变量②）。

## 10. 演进与替换点（这个框架将来会在哪被改）

| 未来变化 | 只需改动 | 不受影响 |
|---|---|---|
| 索引换成自建 API（带分类/评分） | `PluginCatalog` | 生命周期侧、UI |
| 加插件签名校验 | `PluginInstaller` 加一步 | 其他全部 |
| 插件改成进程隔离 | `PluginLoader` + `PluginHost` 的实现（协议不变） | 门面、桥接、UI、插件代码 |
| 插件形态加 C++ 原生 | `PluginLoader` 多一个分支 | 来源侧、状态侧、UI |
| 市场 UI 改成网页/命令行 | L1+L2 替换 | L3 以下全部 |

**这张表是框架好坏的检验标准**：如果某个变化要动三个以上模块，说明职责切错了。

对照一下现状：把"安装管线"塞进 UI 的写法，会在"索引换 API"时同时改动 UI、桥接、网络、状态四处——这就是框架要防的事。

## 11. 模块级风险表

| 模块 | 最可能坏在哪 | 怎么尽早发现 | 怎么降级 |
|---|---|---|---|
| `PluginRegistry` | 写一半断电/被杀进程 → 状态文件损坏 | 原子写 + 启动时校验解析失败就备份并重建 | 扫目录反推（丢 `enabled`，全部按停用处理） |
| `PluginCatalog` | 索引格式变了 / 镜像不同步 / 无网 | 严格 schema 版本校验；无法解析就当"没有市场数据" | 缓存 → seed → 空态，三级降级 |
| `PluginInstaller` | 解压越界、磁盘满、取消时序 | 路径规范化校验；提交前可取消/提交后不可取消的硬边界 | 提交前清理干净；提交后只标 problem |
| `PluginLoader` | 插件 QML 死循环/巨量对象/异常 | 单个插件装载失败隔离；装载不阻塞 UI | 标 problem，可卸载；**绝不让宿主崩** |
| `PluginHost` | 暴露面过大 → 未来无法隔离 | code review 只看"插件能拿到哪些对象" | 收紧暴露面（这是持续纪律，不是一次性设计） |
| `PluginManager` | 编排逻辑膨胀成上帝类 | 只做"顺序 + 合并 + 归类"，出现具体 IO 就下沉 | — |
| UI | 状态模型散在多个页面 | 单一视图模型（ListModel），页面只读 | — |

## 12. 这份框架需要你先拍板的三件事

1. **§2.1 规则 A**（L4 互不调用、全部由门面编排）—— 这条会让 `PluginManager` 稍微厚一点。接受吗？
2. **§5 状态所有权**（`plugins.json` 是唯一真源，其余都可重建）—— 决定了崩溃恢复策略，也决定了它必须原子写。
3. **§4.5 `PluginHost` 的收敛边界**（插件只拿到"数据 + 动作"，拿不到任何宿主内部对象）—— 这条最容易在实现时偷懒，一旦破例，将来做进程隔离就不可能了。

三件都定下来，模块边界就冻结了；之后写代码只是往格子里填，不会再返工。确认后我可以按 M0 拆出"每个模块要写哪些文件、依赖谁"的落地清单（仍然不写代码）。
