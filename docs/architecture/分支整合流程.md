# 分支整合流程：以后每来一批提交怎么合

> 状态：**生效** · 2026-11-05
> 配套：`tools/branch-status.ps1`（对表脚本）、`四分支整合方案.md`（2026-10-29 的一次性整合分析，已执行）
> 适用：trunk-based（`CLAUDE.md` 的 Git 规范），`main` 是唯一发布线

## 0. 一句话

**`main` 承载历史，分支只承载增量。** 每次要合之前先跑一次对表脚本，按四种状态分派；
不要凭记忆判断"合过没有"——`qianju` 就是"合过、但后来被改写"，凭记忆合会把 A2–A7 重放一遍。

## 1. 四条规则（每条都是踩坑换来的）

1. **已推送的分支不改写历史**：不 `rebase`、不 `commit --amend`、不 `push --force`。
   `qianju` 合并后又被 GitHub 网页改写，merge-base 退回 `2445699`，这条分支从此只能 `cherry-pick`。
2. **分支短命**：≤ 2 周、≤ 10 个提交。每周把 `main` **merge 进分支**（不是 rebase），
   让分歧保持在一屏 diff 以内；攒到最后一次合，冲突数量是周同步的十几倍。
3. **合入只走 `--no-ff` + PR**：保留支线形状，冲突在分支上解，决策写在 PR 描述与 devlog 里，
   不写在冲突标记里。合完立刻删远程分支（GitHub 可开 auto-delete）。
4. **归档用 tag，不用活分支**：`archive/<name>` 指向存档提交，然后删分支。
   活分支会继续收到提交，下一次对表又得重新判断一遍。

## 2. 一轮整合的固定动作

```powershell
git switch main
git pull --ff-only                              # 或 git fetch + merge --ff-only origin/main
powershell -ExecutionPolicy Bypass -File tools\branch-status.ps1
```

脚本输出一张表，四列关键信息：

| 列 | 含义 | 怎么用 |
|---|---|---|
| 领先 | 分支上有、main 上没有的提交数 | 0 = 已合完；数字大不代表有真增量（见"基线"） |
| 落后 | main 上有、分支上没有的提交数 | 越大越该先让分支 merge main |
| 基线 | merge-base 的短 hash 与日期 | **远早于分支 tip 的日期 → 历史被改写的强信号** |
| 状态 | 已合并 / 可合并（无冲突）/ 冲突 N | 直接决定下一步 |

## 3. 四种状态，四种动作

| 状态 | 动作 |
|---|---|
| **已合并**（是 main 的祖先） | 打 `archive/<branch>` tag → 删远程分支。**不要再 merge** |
| **可合并（无冲突）** | 在 GitHub 开 PR；本地 `git merge --no-ff`；构建 + `ctest`；写 devlog；推送；删分支 |
| **冲突** | **在分支上** `git merge origin/main` 解冲突 → 推分支 → PR。不要在 main 上解 |
| **历史被改写** | 不要 merge。找出真正的新提交 `git cherry-pick` 到从 main 切的新分支，走 PR |

### 3.1 怎么确认"历史被改写"

三个信号，任一命中就按改写处理：

1. `git log --oneline main..<branch>` 里出现**同标题的重复提交**（例如 `4938e89` 与 `2445699` 都叫
   `feat(phase3): ...`），或反复出现 `Merge remote-tracking branch 'origin/<branch>' into <branch>`；
2. 对表脚本的**基线日期远早于**分支最新提交（`qianju`：基线 2026-09-24，tip 2026-10-29）；
3. `git diff <merge-base>..<branch>` 里出现"删除 main 已经新增的文件"——说明分支把旧版本当成了新改动。

改写的分支**合并一定冲突**，而且冲突文件恰好是 main 后来改过的那些（`qianju` 的 8 个冲突文件就是
`CMakeLists.txt`、`main.cpp`、`MainPanel.qml` 这些公共地基）。

## 5. 防呆（一次性设置，省掉以后每次判断）

- GitHub → Settings → Branches：保护 `main`（Require PR、禁止 force push、Require status checks）。
- Settings → General → Merge button：只留 **Create a merge commit**（对应 `--no-ff`）。
- Settings → General → **Automatically delete head branches**：开。
- CI（GitHub Actions）：`cmake -B build` + `cmake --build` + `ctest`，PR 必过。
  没有 CI 时，合并前本地至少跑一遍 `ctest`。
- 每次合并后在 `docs/devlog/<date>.md` 写三件事：合了什么、冲突怎么解、验收结果。
  这是下一个人对表的依据，也是"合并 ≠ 发布"的证据。

## 6. 什么时候**不要**合并

- 分支只是"别人的试验田"，而 main 已有等价实现（`qianju` 现在就是）；
- 分支带来新的顶层依赖/构建体系（`file_guard` 的 Python）——先问"进不进构建"，不进就归档；
- 分支改公共地基（导航模型、`src/main.cpp` 装配、`CMakeLists.txt` 基线）——必须**先合它**，
  再合依赖它的分支，否则每个后来者都要重做一遍（`四分支整合方案.md` §3）。

## 7. 工具

```powershell
powershell -ExecutionPolicy Bypass -File tools\branch-status.ps1            # 默认先 fetch
powershell -ExecutionPolicy Bypass -File tools\branch-status.ps1 -NoFetch   # 离线
powershell -ExecutionPolicy Bypass -File tools\branch-status.ps1 -FailOnConflict  # 有冲突 exit 1，可挂 CI
```

- 只读（除 `fetch` 更新远端引用），不改工作区、不改分支。
- 默认 `git -c http.sslBackend=openssl fetch`：本机 schannel 后端时常拿不到凭据；
  fetch 失败只警告不中断。
- 脚本存为 **UTF-8 with BOM**：Windows PowerShell 5.1 读无 BOM 的 UTF-8 脚本会按 GBK 解码，中文变乱码。
