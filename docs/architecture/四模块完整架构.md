## 0. 一句话

四个模块 = **四个薄门面 + 一套契约 + 一个组合根**。没有 `FileKernel`，没有 `EventBus`，
没有模块互相 `#include` 内部头，也没有第二个"统一入口"。

```
谁能调谁：门面方法 ✅   契约类型（include/contract/） ✅   应用层编排 ✅
         内部协作者 ❌   别人的数据库表 ❌   别人的 QSqlDatabase 连接 ❌
```

## 1. 全局约束（先定这些，后面才有意义）

| # | 约束 | 违反的后果 |
|---|---|---|
| G1 | **单进程 GUI**；插件 v1 也在进程内 | 没有"跨进程保命"，插件崩溃 = 宿主崩溃（明说不承诺） |
| G2 | **一个数据库文件一个 `QSqlDatabase` 连接名**，连接**线程亲和** | 跨线程复用连接 → 随机 `database is locked` / 崩溃 |
| G3 | **每个库只有一个写者**（见 §11.3） | 两个写者 → 迁移与差量互相覆盖 |
| G4 | 契约头放 `include/contract/`，**只放 POD 与纯虚接口**，不引用任何模块实现头 | 契约层被拖成第二个实现层 |
| G5 | 跨库操作**不假设原子性**，一律用"持久化状态机 + 恢复入口" | 半入库、半删除、账本与索引对不上 |
| G6 | 失败**默认安全**：策略异常 = `Deny`；校验未完成 = 不索引；同名 = 不覆盖；不认识的格式 = 拒绝 | 静默降级一次，以后每次都靠运气 |
| G7 | `Logger` 是**唯一**全局单例；`ConfigManager` 是**唯一**配置来源，插件不得写入 | 配置双写 → 谁最后写谁赢 |
| G8 | 依赖方向**永远向下**：接入层 → 模块层 → 契约层 → 基座层 | 出现反向依赖就是架构腐化的起点 |
| G9 | 文件系统事件**不是审计日志**（会丢、会重、会溢出） | 拿事件流当账本 → 账本不可信 |

│  主面板 MainPanel.qml(导航 key) ← PanelBridge                          │

│  M1 FileIndex      M2 TransferManager   M3 SecurityCenter   M4 PluginManager │
└───────────────────────────────┬────────────────────────────────────────┘

┌ 契约层 ───────────────────────┼────────────────────────────────────────┐
│  C1 FileRef   C2 FileSystemEvent   C3 网关类型(OpRequest/Decision/Result)  │

└───────────────────────────────┬────────────────────────────────────────┘

M4 只持指针。两处都在 `main.cpp` 注入。

## 3. 契约层（C1–C4）

> 现状：**一个都还没落地**。四个分支里只有 `qianju` 的 `ITransport`、`plugin-market` 的 `PluginHost`
> 各自"长得像"契约，但都放在自己模块的目录里。**必须先建 `include/contract/`，再合 M2/M4**，
> 否则两个分支会各自定义"文件句柄"和"宿主能力"。

### 3.1 四个契约

| 契约 | 头文件 | 是什么 | 明确不是 |
|---|---|---|---|
| **C1 `FileRef`** | `contract/FileRef.h` | 跨模块轻量值句柄：`id/path/size/mtime/catMask/flags/secLevel` | 不是物理身份、不是授权凭证、不是快照保证 |
| **C2 `FileSystemEvent`** | `contract/FileSystemEvent.h` | 变化通知：`kind(Added/Removed/Modified/Renamed)/dir/name/generation/overflow` | 不是持久日志、不是不丢的事件流 |
| **C3 网关类型** | `contract/FileOperation.h` | `OpRequest{actor,op,ref,target}`、`Decision{Allow,Ask,Deny,reason}`、`OpResult{ok,code,opId}` | 不包含任何具体 I/O 实现 |
| **C4 `IHostApi` + `Capability`** | `contract/IHostApi.h` | 插件唯一可用能力：`dataDir/settings/toast/contributePage/…` + 固定能力枚举 | 不是沙箱、不是权限系统（进程内完全信任） |

### 3.2 必须写进契约头的不变量（比字段更重要）

1. `FileRef.id` 在**进程重启 / 文件删除 / 句柄失效**后必须显式失效，不能"看起来还能用"。
2. `FileRef` 的 `path/size/mtime` 都可能过期；**受控操作执行前必须重新解析**（优先按已打开句柄）。
3. `FileSystemEvent` 允许重复、乱序、溢出；消费者必须幂等，`overflow=true` 必须触发复核扫描。
4. `Decision` 只有三种结果，**异常/超时/未知一律归入 `Deny`**（不是 `Ask`）。
5. `Capability` 是**固定枚举**，不允许字符串自由拼写；版本不兼容与能力不足是两个错误码。
6. 契约头**不得** `#include` `core/` 或 `database/` 下任何文件（CI 可加 grep 检查）。

### 3.3 冻结时机

| 契约 | 可冻结的时间点 | 冻结前可以只写语义 |
|---|---|---|
| C1 `FileRef` | **现在**（A4 已有快照字段，够用了） | 结构体 + 注释即可，先不让任何模块依赖它 |
| C2 `FileSystemEvent` | A5（`FileWatcher`）落地前 | 同上 |
| C3 网关类型 | M3-p1 开始前 | 同上 |
| C4 `IHostApi` | M4 合并前（P1） | 先覆盖现有 `PluginHost` 的能力集，别提前设计"将来可能要"的能力 |

## 4. M1 文件管理

### 4.1 门面与协作者

| 角色 | 类型 | 职责 | 不该做的事 |
|---|---|---|---|
| **门面** | `FileIndex` | 起一次扫描、发布快照、转发查询、暴露 `stats` | 不实现 DFS / SQL / 打分 / watcher |
| 采集 | `FileScanner`（namespace） | Win32 句柄栈 DFS、目录级剪枝、长路径、可取消 | 不做持久化、不做打分 |
| 内存表示 | `FileSnapshot` + `SnapshotManager` | 不可变列式快照；`atomic<shared_ptr>` COW 发布 | 不支持原地修改 |
| 查询 | `QueryEngine` → `QueryParser` + `ScoreEngine` | 语法（自由词 AND / `-否定`）→ 打分（tier + 贪心子序列 + 有界编辑距离）→ top-K 堆 | 不碰 IO、不碰 DB |
| 采集编排 | `ScanWorker`（`FileIndex.cpp` 内） | 扫描 → 三方差集 → 写库 → 构建快照 → 回传 | 不碰 QML |
| 持久化 | `FileIndexDatabase`（`file_index.db`） | `dirs/files/roots` 三表、UPSERT 批量事务、差量 | 不决定"扫什么" |
| 迁移 | `DatabaseMigrator` | `PRAGMA user_version` 前向迁移，每步一事务 | 不允许 `DROP` 重建 |

### 4.2 两条数据流

```
扫描：startAsync() ─▶ worker 线程
        FileScanner.scan(roots, opts) ─▶ 三方差集 ─▶ FileIndexDatabase.apply()
        ─▶ FileSnapshot::Builder ─▶ SnapshotManager.publish() ─▶ indexReady(entries,ms)

查询：AppBridge.search(text)
        ─▶ FileIndex.query() ─▶ SnapshotManager.current()（拿一份 shared_ptr，不加锁）
        ─▶ QueryParser → ScoreEngine → top-K ─▶ QList<SearchResult>
```

### 4.3 不变量

- 快照**不可变**；查询**全程零锁**（这是 v2 结构存在的唯一理由）。
- 扫描期间 UI 不卡：`startAsync()` 立即返回；扫描中再调只记"待重扫"。
- 剪枝名单**只有一份**（`FileScanner::defaultExcludedDirNames()`），`FileSearcher`(legacy) 也用它。
- 不跟随 reparse point（junction），目录级剪枝在**进入前**判定（A1 的坑）。
- 硬上限截断按 **DFS 前序**进行（顺序变了 golden 就失真）。
- `engine=legacy` 是退路，不是第二套实现方向（A7 删除）。

### 4.4 现状

A2 结构 ✅ / A3 采集与持久化 ✅ / A4 查询与 baseline ✅；A5 增量、A6 冷启动、A7 收尾、A8 拼音未做。
`FileRef` 尚未抽取；`FileIndex::query()` 仍返回 UI 类型 `SearchResult`（合并 M2/M3 时应改为只返回
`FileRef` + 分数，由桥层再拼展示字段）。

## 5. M2 传输与共享

### 5.1 目标结构：一个内核 + 三个交付单元

```
TransferManager（门面，唯一对外）
   ├─ JobQueue / JobState（持久化作业，可恢复）
   ├─ ChunkStream（分块、断点、重试、取消）
   ├─ Hasher（分块哈希 + 最终内容哈希）
   ├─ Quarantine（接收隔离区，未校验不得进索引）
   └─ Channel
        ├─ FolderTransport     渠道目录（投递区 = 一个本地/网盘同步文件夹）   ②
        └─ LanTransport        配对 + 验证过的 TLS + 分块续传              ③
```

### 5.2 作业状态机（发送与接收共用骨架）

```
Queued → Authorizing → Streaming → Verifying → Committing → Done
             │             │            │            │
             └─────────────┴────────────┴────────────┴──▶ Failed / Cancelled / Paused
```

每个状态必须回答四件事：**已完成什么持久化、什么可以安全重试、什么必须补偿、什么只能人工处理。**

### 5.3 接收流水线（硬性要求）

```
远端字节 → quarantine/<opId>.part
        → 分块哈希校验 → 最终内容哈希
        → 路径校验（穿越/ADS/保留设备名/reparse point）
        → 原子 rename 到目标（不覆盖同名，冲突走"副本命名"）
        → 登记来源（M1）→ 更新索引（可恢复）
```

- 远端**不能**决定最终绝对路径；未完成校验的文件**不得**进入正式索引。
- 崩溃后能续：`quarantine` 里的半成品要么继续验证，要么安全清理，**不允许"半入库"**。

### 5.4 与 M1 / M3 的接缝

| 方向 | 规则 |
|---|---|
| M2 → M1 | 只用 `FileIndex` 的公开方法（`query`/登记），**不查 `file_index.db` 表** |
| M2 → M3 | 发送前把 `OpRequest` 交网关判定；**不 include `PolicyEngine`** |
| M3 → M2 | 授权通过后由网关**创建传输作业**，只调 `TransferManager` 的公开方法，不碰通道内部 |
| M1 → M2 | 不知道传输存在；"发送"是接入层的入口，不是索引的方法 |

### 5.5 现状（`qianju` 分支）

已有：`ITransport` 抽象、`FolderTransport`、`SyncEngine`（三方差集）、`ConflictResolver`、
`DeliveryNaming`、`PathGuard`、`SyncDatabase`（`sync_state/conflicts/received`）、`SyncBridge`、`SyncPage`。
**没有**：作业状态机、分块、最终内容哈希、隔离区、LAN 通道（`LanTransport` 只在设计文档里，
`grep QTcpSocket` 零命中）。

结论：它是 **② 渠道目录通道** 的实现，不是 ① 内核。合入后对外定位必须写成"通道"，内核另开分支。

## 6. M3 安全

### 6.1 三分能力（验收方式不同，不可互相代替）

| 能力 | 内容 | 关键组件 | 失败语义 |
|---|---|---|---|
| **发现** | 事件 + 快速签名 + 周期复核，发现"东西变了" | `IntegrityLedger`、`quickSig`、复核扫描 | 读不到 = `不可验证`，**不是"正常"** |
| **判定** | 对经由本应用的受控操作做策略求值、审批、拒绝 | `SecurityCenter`、`IFilePolicy`、`PolicyEngine`、`ApprovalSession` | 异常/超时/审批失效 = `Deny` |
| **保护** | 保险箱、密钥、临时明文生命周期 | `Vault`、`KeyVault`(DPAPI)、`AesGcm`、`NameCipher`、`RecoveryCode` | 解密失败 = 不输出半明文 |

### 6.2 网关与执行器分离

```
接入层 / 插件 / 其他模块
        │ OpRequest（含 actor，由宿主解析）
        ▼
FileOpGateway ── 校验主体 → 重新解析目标 → 策略判定 → 必要时审批 → 再次校验
        │ 授权通过
        ▼
FileOperator（受控执行器）── 实际 I/O，返回 OpResult(opId)
        │
        ▼
事件分发器 → 账本/索引/传输消费者（用 opId 去重）
```

**网关只做授权与协调**，不包揽所有 I/O（这是《关联与方案》决策 1）。受控操作清单：
删除 / 移动 / 复制到外部 / 发送 / 加解密 / 保险箱密钥操作；`Open` 属受控但低风险，审计可异步。

### 6.3 账本与保险箱

- `security.db` 是**权威库**（丢了不可重建），迁移失败 → **停止相关功能并拒绝启动**。
- 审计分级：删除、移动、敏感外发、密钥操作必须记录"请求 / 判定 / 执行结果 / 恢复信息"。
- 哈希链：`h_i = HMAC(chain, h_{i-1} || nonce_i || ct_i)`，配 `next_seq` 高水位防删行，
  `log head` 做外部锚点。**账本只承诺"监控与复核范围内"的发现，不承诺阻止所有外部修改。**
- 保险箱 v1 **只承诺静止态加密**：AES-256-GCM 内容加密 + DPAPI 保护的 DEK + 名称加密 + 恢复码；
  不承诺运行期无明文、不承诺 SSD/备份/分页文件里的绝对擦除。

### 6.4 现状

C++ 侧**零实现**。`file_guard`（Python）提供了可借鉴的四条设计：FGC1 容器头（每块
`AAD=header||index||is_final`）、HMAC 审计链 + 高水位、DPAPI 密钥缓存、junction 统一跳过。
三处必须先对齐再写 C++：**恢复码**（原型没有）、**名称加密**（原型原名留盘）、
**账本落 `security.db`**（原型是加密 JSONL）。

## 7. M4 插件

### 7.1 生命周期状态机

```
Discovered ──install──▶ Installed(disabled) ──enable──▶ Enabled ──load──▶ Loaded
     │                        │                             │              │
     └────────────────────────┴────── uninstall ◀──────────┴──────────────┘
                                                      异常 ──▶ Problem(记录原因，不算崩溃隔离)
```

约束：`init/load` 失败**必须干净回滚**（不留半初始化页面）；`shutdown/unload` **必须幂等**；
禁用后页面立即从导航消失、`PluginHost` 失效；卸载先卸页面再删目录。

### 7.2 组件

| 组件 | 职责 | 边界 |
|---|---|---|
| `PluginManager`（门面） | 编排：注册表 + 加载器 + 安装器 + 市场目录；对外只发信号 | 唯一持有四个协作者 |
| `PluginRegistry` | 磁盘布局（`plugins/<id>/`）、安装清单 `installed.json` | 不加载代码 |
| `PluginCatalog` | 市场索引：内置 `seed-index.json` → 缓存 → HTTP（`ASSISTANT_MARKET_URL`） | 不安装 |
| `PluginInstaller` | 流水线：`inspect → download → extract → validate → commit`；zip-slip 防护 + sha256 | 不加载代码 |
| `PluginLoader` | QML 加载、页面对象生命周期、每插件一个 `PluginHost` | 不写注册表 |
| `PluginHost` | 插件**唯一**可见面：只读属性 + `dataDir` 内的读写 + toast + 页面贡献 | 不暴露 `QQmlEngine` / `PluginManager` / `PluginRegistry` |

### 7.3 能力模型（目标，现状未做）

- 能力名是**固定枚举**（如 `file.read`/`file.write`/`network`/`clipboard.read`/`notification`）。
- 宿主在**每次** API 调用前校验；`permissions` 现在只是展示用的字符串列表。
- **身份由宿主解析**：插件不能通过参数自报 `pluginId` 提权。
- manifest/签名/能力**不是沙箱**：v1 是"用户主动安装的完全信任代码"，UI 与文档都必须这么写。

### 7.4 与其它模块的边界

| 插件想要 | 允许路径 | 禁止 |
|---|---|---|
| 文件 | `IHostApi` 提供的检索/受控操作入口（将来经网关） | 直接 `QFile` 扫盘、直接开 `file_index.db` |
| 网络 | 独立能力 + 用户可见的权限提示 | 借用宿主的 `QNetworkAccessManager` 绕开提示 |
| 其它模块 | 无 | `PluginHost` 之外任何宿主对象 |

### 7.5 现状（`plugin-market` 分支）

QML 插件包（`native` 拒装）、M0–M4 代码齐、独立测试工程、`PluginHost` 已成形。
缺口：能力校验、宿主解析主体、来源策略与签名、UI 里"看起来像沙箱"的措辞。
安装流水线目前**在 GUI 线程**跑（网络异步、解压同步），大包会卡界面，属已知限制。

## 8. 组合根与启动顺序

`main.cpp` 是**唯一**装配点（没有服务定位器、没有全局 `getInstance()`）。

```
 1. ConfigManager.load()                      ← 一切依赖配置的起点
 2. Logger.init(logDir, cfg.logLevel())
 3. DB 统一迁移阶段（《关联与方案》§5.1）
      history.db / todo.db / notes.db / clipboard.db / file_index.db / sync.db / [security.db]
      打开 → 读 user_version → 逐版本迁移 → commit
 4. 桥与门面构造，依赖用 setter 注入（不是构造函数里 new）
      PanelBridge(todo,notes,clip) · AppBridge(history) · FileIndex(dbPath, limit)
      SyncBridge(cfg, sync.db) · PluginManager(registry, loader, installer, catalog)
 5. FileIndex.startAsync()                   ← 必须在 engine.load() **之前**，但它立即返回
 6. 搜索窗口：engine + context(backend/config/appVersion) → MainWindow.qml
 7. 主面板：panelEngine + context(panel/config/plugins/appVersion) → MainPanel.qml
 8. PluginManager.setEngine(&panelEngine) → loadEnabledAtStartup()   ← 必须在面板加载之后
 9. 托盘 / 热键 / 窗口位置持久化接线
```

**三条顺序规则**（每一条都有代价）：

- DB 迁移必须在**任何** QML 之前完成——否则 QML 首次查询会撞上"表还没建"。
- `FileIndex.startAsync()` 必须在 `engine.load()` **之前**调用、且**不得阻塞**——"窗口先起来、
  索引后台跑"的验收依据就是这条调用顺序与它的非阻塞性。
- 插件的 `context property` 必须在 `MainPanel.qml` 加载**之前**注入，`loadEnabledAtStartup()`
  必须在**之后**——早加载拿不到引擎，晚注入会让导航首帧缺项。

## 9. 四条端到端时序

### 9.1 搜索（现状可用）

```
键入 → AppBridge.search(text) → FileIndex.query → 快照(无锁) → QueryParser → ScoreEngine
     → top-K → SearchResult 列表 → QML 列表（40ms 防抖 + IME 拦截）
```

### 9.2 受控删除（目标）

```
用户点删除 → OpRequest(actor=ui, ref) → Gateway
   ├─ 主体校验 → 重新解析（按句柄） → PolicyEngine.decide
   ├─ Deny  → UI 提示原因（不执行）
   ├─ Ask   → ApprovalSession（保存请求上下文 → 用户确认 → 重新校验）→ Allow
   └─ Allow → FileOperator.delete(handle) → OpResult(opId)
              → 审计(security.db) → FileSystemEvent(opId) → 索引增量（去重）→ UI 更新
```

### 9.3 接收文件（目标）

```
Lan/文件夹通道 → quarantine/<opId>.part → 分块校验 → 最终哈希 → 路径校验
   → 原子 rename（不覆盖）→ 来源登记 → FileIndex 增量 → 通知 → 索引可见
（任一步失败：留在 quarantine 或安全清理；**不得**"半入库"）
```

### 9.4 插件安装并出现在导航（现状可用）

```
PluginsPage.install(id) → PluginBridge → PluginManager
   → Installer: inspect → download → extract → validate(manifest/zip-slip/sha256) → commit
   → Registry.upsert → Loader.load（QML 上下文 + PluginHost）
   → navigationChanged → MainPanel 重新计算 navItems → Loader 切页
```

## 14. 演进路线（与《关联与方案》§6 对齐）

```
契约 C1 冻结 ─┬─ A5 事件 → A6 冷启动 → A7/A8 收尾
              │
              ├─ B 治理过滤 ─┐
              ├─ M3-p1 判定与账本 ─┤ → C/D box + 来源追踪 → M2① 作业内核
              │                    │                        → M2② 渠道通道（qianju 归位）
              │                    │                        → M2③ LAN（TLS 实测通过才发）
              │                    └─ M3-p2 保险箱（独立验收）
              │
              └─ M4 插件（P1 先合，能力模型随后补齐）
```

**执行顺序上的三个硬点**：

1. **契约先于合并**：C1 先冻结，否则 M2 与 M4 会各自造"文件句柄"和"宿主能力"。
2. **M2 的内核先于通道交付**：`qianju` 的通道代码可以合，但对外只能作为"实验通道"，不进验收口径。
3. **M3 的判定先于 M2 的发送**：没有 `Decision`，"发送前判定"就是一句空话。

> **M1 管"看得见"，M2 管"出得去进得来"，M3 管"准不准、该不该、要不要保护"，M4 管"谁来加功能"。**
