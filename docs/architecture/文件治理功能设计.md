## 0. 两个功能的关系

两个需求共享同一套底层（扫描器、快照、watcher、SQLite），但**职责边界必须分清**：

```
        ┌─────────────── 采集面（负责任：不漏文件） ───────────────┐
        │  常规索引扫描（用户目录）      下载 box（Ingest 中转站）  │
        │  ← 受 排除规则 + 工程识别       ← 不受种类白名单限制      │
        │  产出：files 全量表            产出：downloads + 去向链   │
        └───────────────────────┬─────────────────────┬──────────┘
                                │                     │
                     ┌──────────▼─────────────────────▼──────────┐
                     │   检索面（负责任：只给出想要的）           │
                     │   内存快照 = 按 种类白名单 从 DB 构建      │
                     │   + 查询期 :kind 过滤 + 排序              │
                     └───────────────────────────────────────────┘
```

下载 box 是**中转站**：文件只是路过，最终由用户手动归档到自己的目录。Assistant 的职责是**登记 + 追踪去向 + 提供跳转**（「最近下载」栏），而不是替用户决定文件该放哪。

**核心设计决定**：
1. **磁盘遍历全量入库（只受排除规则约束），内存快照按当前白名单筛选构建**。这样切换「只要文档 / 含代码 / 全都要」只需从 DB 重建快照（数十 ms），**不需重新扫盘**——这是功能一体验的关键。
2. **下载 box 是采集面，不服从种类白名单**。否则用户把白名单设成「只要 PDF」，一个刚下载的 `.exe` 安装包就会从收件箱里消失——那是数据丢失级的体验事故。box 列表读自己的 DB，与索引过滤完全解耦。
3. **box 是「中转站」而非「归档区」**：文件进 box 只是等待用户整理，用户把它移走是**正常流程而不是异常**。因此系统必须能回答"这个文件现在在哪"——这是**去向追踪引擎**（§2.6）存在的原因，也是本功能真正的技术门槛：`ReadDirectoryChangesW` 只告诉你文件**走了**，不告诉你**去哪了**。

# 功能一：文件种类过滤 + 工程文件排除

## 1.1 概念模型：**四级过滤**（采集过滤 × 检索过滤）

| 层 | 时机 | 机制 | 作用 |
|---|---|---|---|
| L1 根目录 | 扫描前 | `roots[]` 配置 | 决定扫哪里 |
| L2 目录级剪枝 | 遍历每进入一个目录时（**每目录一次**） | `ExcludeRuleSet` + `ProjectGuard` | 整个子树不进入：`node_modules`、`.git`、`build/`、任何被识别为「工程」的目录 |
| L3 文件级归类 | 每个文件（**O(1) 查表**） | `FileClassifier` 扩展名 → `catMask` | 打上种类位掩码，供快照构建/查询期过滤 |
| L4 查询期过滤 | 每次查询 | 查询语法 `:doc` / `ext:pdf` | 在白名单结果内进一步收窄 |

**这里两组概念绝不能混**：

| 组 | 层 | 语义 | 变更代价 |
|---|---|---|---|
| **采集过滤**（Collect Filter） | L1 根目录、L2 目录级剪枝 | 决定**文件是否进入索引数据库** | 改它要**重扫磁盘**（慢，UI 必须提示） |
| **检索过滤**（Query Filter） | L3 文件级归类、L4 查询期过滤 | 决定**进入快照后是否参与搜索、是否出现在结果里** | 改它只**重建快照**（快，数十 ms） |

分界线就是 `files` 表：线以上决定表里有什么，线以下决定快照与结果里给什么。

## 1.2 工程目录识别（ProjectGuard）

**算法**：进入目录 `d` 时，检查 `d` 是否含「工程哨兵文件」（一次目录枚举内顺带判定，零额外 syscall，因为哨兵文件本来就在这次枚举结果里）：

```
哨兵集合（可配置）：
  .git  .hg  .svn                      → VCS 根
  CMakeLists.txt  Makefile  *.sln *.vcxproj  meson.build
  package.json  pnpm-lock.yaml  yarn.lock  tsconfig.json
  Cargo.toml  go.mod  pyproject.toml  requirements.txt  .venv  venv
  *.csproj  build.gradle  pom.xml  Gemfile  composer.json
```

命中即认定 `d` 是工程根，随后按 `projectPolicy` 处置：

| policy | 行为 | 适用 |
|---|---|---|
| `skip`（**默认**） | 整个子树不入库；计数 `projectDirsSkipped` | 只想搜文档/下载的用户，收益最大 |
| `demote` | 入库但打 `Flag::Project` + 打分降权（-30%），且强制排除其构建产物目录（`build/ out/ target/ bin/ obj/ dist/ .vs/ DerivedData/`） | 开发者也想搜到源码，但不希望 build 噪音刷屏 |
| `index` | 如实入库 | 排查问题用 |

**收益可量化**（写入验收）：一个含 `node_modules` 的前端工程目录，通常从 **10 万+ 条目降到几百条**；`skip` 模式下扫描耗时同比例下降。

**注意**：`skip` 是对**包含哨兵的目录整个子树**生效，所以必须先判定父目录再下探，天然要求基础架构 §3.2 的**自建迭代栈**（`QDirIterator` 无法剪枝，这也是顺序重构 S1/S2 必须先落地的原因）。

## 1.3 文件种类归类（FileClassifier）

```cpp
// 16 位类别掩码，一条 AND 就能做过滤
enum class FileKind : uint16_t {
    Document  = 1u << 0,   // doc docx odt rtf txt md tex
    Sheet     = 1u << 1,   // xls xlsx csv ods
    Slide     = 1u << 2,   // ppt pptx odp
    Pdf       = 1u << 3,   // pdf
    Image     = 1u << 4,   // jpg png gif webp bmp svg heic psd ai
    Video     = 1u << 5,   // mp4 mkv avi mov webm flv
    Audio     = 1u << 6,   // mp3 wav flac m4a aac
    Archive   = 1u << 7,   // zip rar 7z tar gz xz
    Installer = 1u << 8,   // exe msi msix appx dmg pkg
    Code      = 1u << 9,   // cpp h py js ts java go rs cs sql sh
    Font      = 1u << 10,  // ttf otf woff woff2
    Data      = 1u << 11,  // json xml yaml toml db sqlite
    Ebook     = 1u << 12,  // epub mobi azw3
    Shortcut  = 1u << 13,  // lnk url
    Disk      = 1u << 14,  // iso img vhd
    Other     = 1u << 15,  // 未命中任何表
};
```

实现要点：
- **查表法**：启动时把「小写扩展名 → catMask」构造成 `std::unordered_map<std::string_view, uint16_t>`（约 300 条内置 + 用户覆盖），索引期每个文件一次哈希查表，O(1)。
- **多段扩展名**：`.tar.gz` / `.tar.xz` 取最长的已注册后缀（先试全后缀 `"tar.gz"`，再退 `"gz"`），避免 `.gz` 单归类造成误判。
- **无扩展名/点文件**：`.gitignore`、`Makefile`、`LICENSE` 有白名单式的「名称表」；其余归 `Other`。
- **不做内容嗅探（magic number）**：读文件头会给扫描引入 IO 与权限失败路径，收益低于成本。留作后续可选开关。
- **可配置**：`kindOverrides: { "psd": "image", "iso": "disk" }`，用户可改归属；也可加「自定义类别」`customKinds`（占用空闲位）。

## 1.4 规则引擎（ExcludeRuleSet）

规则类型与求值：

| 类型 | 匹配对象 | 求值时机 | 数据结构 |
|---|---|---|---|
| `dirNames` | 目录名（精确） | 进入目录时 | `std::unordered_set<std::string>`，O(1) |
| `dirGlobs` | 目录相对路径（`**/build/**`） | 进入目录时 | 编译为分段匹配；常见模式预编译成「段名集合 + 通配回退」 |
| `fileGlobs` | 文件名（`*.tmp`、`~$*`） | 每文件 | 后缀集合优先（`*.tmp` → 查扩展名集合，O(1)），通配符回退 |
| `maxSizeMB` | 文件大小 | 每文件 | 直接比较，用于排除超大文件（如 40 GB 蓝光镜像） |
| `minSizeBytes` | 文件大小 | 每文件 | 排除 0 字节残留 |

**求值顺序与短路**：目录级规则先判（一次剪整棵子树）→ 文件级规则再判。规则在配置加载时**编译一次**（预小写、预拆段、预建集合），扫描循环里只做查表，不做字符串解析。规则集带 `version`（字段哈希），版本变化才触发索引重建（见 §1.6）。

## 1.5 查询语法（QueryParser）

在基础架构 §4.1 的归一化阶段之前插入一个**轻量 tokenizer**，把查询拆成「过滤谓词 + 自由词」：

| 语法 | 含义 | 实现 |
|---|---|---|
| `:doc` `:img` `:vid` `:aud` `:zip` `:exe` `:code` `:pdf` … | 种类过滤（可叠加，取并集的掩码） | 映射到 `kindMask`，与快照 `catMask[i]` 做 `&` |
| `ext:pdf,pptx` | 精确扩展名过滤 | 扩展名集合 |
| `in:box` / `in:<rootAlias>` | 限定范围 | 路径前缀集合（快照里 `rootId[i]`） |
| `src:chrome` `src:wechat` | 按来源过滤（box 文件才有） | `originId[i]`，见功能二 |
| `-词` | 排除词 | 自由词列表独立处理，命中即否决 |
| `"多个词"` | 短语 | 作为一个自由词（保留空格） |
| `size:>10mb` `date:today` `date:7d` | 元数据过滤 | 数值/时间比较，直接读快照的 `size/mtime` |
| 其余裸词 | 自由词，AND 语义，逐词做基础架构 §4 的多词匹配 | 复用现有打分链路 |

设计要点：
- **解析结果是一个 `QueryFilter` 结构 + 自由词列表**，过滤谓词在**位图预筛阶段一起判**（一条 `&` 测试），而不是匹配后再筛——避免为将被过滤掉的条目做 DP 打分。
- **非法/未知 token 降级为自由词**（`:` 开头但没匹配到已知种类时，整串当普通词），避免用户输 `:foo` 时结果全空却不知所措。
- UI 侧提供**过滤 Chip**（全部 / 文档 / 图片 / 视频 / 压缩包 / 安装包 / 代码 / 待整理），点击即等价于插入对应 token，双向同步（Chip 高亮 ↔ 查询文本）。
- 空查询 + 选中某 Chip = 列出该种类最近文件（复用基础架构 §5.5 的「最近文件」通道）。

## 1.6 与基础架构的衔接（关键 delta）

| 基础架构位置 | 增补内容 |
|---|---|
| §3.1 `Snapshot` | 新增 `std::vector<uint16_t> catMask;`、`std::vector<uint8_t> flags;`（`Project`/`Inbox`/`Hidden`/`Duplicate`）、`std::vector<uint16_t> rootId;`、`std::vector<uint16_t> originId;`。内存增量（20 万条）≈ 1.4 MB |
| §3.2 扫描器 | 目录枚举结果先过 `ProjectGuard` + `ExcludeRuleSet` 决定是否下探；文件先过 `FileClassifier` 得 `catMask` 再写 DB |
| §3.5 持久化 | **DB 存全量**（受排除规则约束），`files` 表加 `cat_mask INTEGER`、`flags INTEGER`、`root_id INTEGER`、`origin_id INTEGER`；**内存快照按 `kindFilter` 白名单 + 规则从 DB 构建** |
| §4.1—4.2 查询层 | 归一化前插入 QueryParser；`QueryFilter` 的谓词并入位图预筛条件 |
| §7 配置 | 新增 `kindFilter` / `exclude` / `querySyntax` 相关项（见 §1.7） |
| §9 指标 | 新增：白名单切换（DB→快照重建）< 50 ms；工程目录剪枝后条目数与耗时对比；QueryParser golden 用例 |
| §10 路线 | 新增 **S8**（见 §3） |

**一致性约束**：`kindFilter` / `exclude` 变更 → 只重建快照（快）；`roots` / 排除规则的**目录级**变更 → 需要重扫（慢），UI 必须明确提示「正在重新建立索引（约 N 秒）」，不可静默变慢。

# 功能二：下载 box 中转站（Ingest + 去向追踪）

## 2.1 目标与范围

- **一期**：接管「主浏览器」的下载 → 稳定判定 → 拉入 box → **登记**（路径、大小、时间、种类、身份指纹）→ 出现在「最近下载」栏。
- **常态**：用户在资源管理器里把文件从 box 移到自己想放的目录 → 系统**检测到"离开 box"并记录新路径** → 记录从「待整理」转为「已归档」，随时可一键跳转回文件所在文件夹。
- **后续**：QQ / 微信 / 钉钉等 IM 的接收文件，共用同一管线，只新增「源适配器」（§2.4）。
- **不做**：不做浏览器扩展、不替代浏览器下载、不接管「另存为」到其它目录的文件（默认配置下）、**绝不主动删除用户的文件**。

## 2.2 「接管」的确切语义（box 中转 + 去向追踪）

**已定语义**（取代早期"adopt 就地纳管 / move 搬入收件箱"的二选一讨论）：

```
浏览器下载 ─[稳定判定]─▶ 拉入 box ─▶ 登记入库 ─▶ 「最近下载」可见（状态：待整理）
                                                    │
                        用户手动把它移到自己想放的目录（资源管理器里拖走/剪切粘贴）
                                                    ▼
                        检测到「文件离开 box」─▶ 追踪新位置 ─▶ 更新记录（状态：已归档）
                                                    │
                        「最近下载」里点一下 ─▶ 跳转到文件**现在**所在的文件夹
                                                （未移动的 ─▶ 定位到 box）
```

由这个语义直接推出的设计约束（**不是可选项**）：

| 推论 | 说明 |
|---|---|
| **box 会被清空，这是设计目标而非故障** | 不把 box 当归档区。UI 用"待整理"语义表达：待整理计数、**文件在 box 滞留天数**（"已滞留 12 天"是这个功能最真实的提醒价值），不追求 box 里越来越满 |
| **`leaveBackLink` 作废** | 早期设计想在原目录留硬链接/快捷方式。中转语义下这有害：硬链接会让"文件是否已离开 box"的判断失真（链接仍在、文件仍可访问），**移除该配置项** |
| **自动归档默认关闭**（`autoOrganize: false`） | 用户既然要自己归档，自动搬动只会打架。§2.9 的规则引擎降级为**可选**，且默认只给「推荐去向」提示，不静默移动 |
| **我们永不删除用户的文件** | `inbox.onExternalCopy = keep`（默认）：若用户在别处**复制**了一份而 box 原件仍在 → 原件保留、状态仍是"待整理"，**不触发追踪、不删任何东西**。只有 box 里物理不存在了才进入去向追踪 |
| **只接管新增文件** | `inbox.firstRunPolicy = newOnly`（默认）：绝不批量搬走用户已有的文件；`migrate` 需用户在设置里显式点击 + 二次确认 |
| **可撤销** | `move_journal` 记录我方每次移动 `(from, to, at)`，UI 提供「撤销」（最近一次 / 按天），撤销成功率要求 100%。注意：**用户自己的移动不在撤销范围**（我们只是观察者，无权改动用户的选择） |

## 2.3 完成度检测算法（本功能技术核心）

**问题**：文件出现在目录里 ≠ 下载完成。浏览器边下边写，中途移动会毁文件。

**判定模型：A + B 是「完成」的主判定，C 是增强信号**（不是三条件等权 AND）

```
主判定（必要条件，两条都成立才算"基本完成"）
条件 A  命名信号：文件名不含「临时后缀」
        .crdownload(Chrome/Edge) .part(Firefox) .download .opdownload
        .tmp .aria2 .!ut .td  ← 适配器可声明各自集合
        （Chrome/Firefox 都是「先写临时名，完成时重命名」→ 最终名出现是强信号）

条件 B  稳定信号：size 与 mtime 在连续两次采样（间隔 ≥500 ms）内完全一致，
        且距最后一次变化 ≥ settleMs（浏览器默认 1200 ms，IM 默认 2500 ms）

增强信号（提高置信度，不能单独作为依据）
条件 C  独占信号：CreateFileW(path, GENERIC_READ, dwShareMode=0, OPEN_EXISTING)
        成功 → **当前时刻**没有观察到共享冲突
        失败且 ERROR_SHARING_VIOLATION → 视为"可能仍在写"，退避重试
```

**关于 C 的准确语义（重要）**：C 成功**不等于**"文件此后绝不会再被写"——它只说明**此刻**没有进程以共享方式持有句柄。所以：

- **不要**把 C 当成绝对物理事实；它的作用是**提高置信度**，或在 A/B 存疑时提供额外证据。
- **真正的安全边界来自 A + B**：临时后缀消失 + 大小/时间稳定超过静默期，已覆盖浏览器的实际行为。
- **两个方向的误判代价不对称**：早拉取（误判完成）会**毁掉一个下载**，必须极力避免；晚拉取 1–2 秒只是体验损失。所以宁可等久一点。
- **预期 C 的假阴性来源**（杀毒扫描、OneDrive 占位同步、系统索引器、"下载器稍后又打开文件"）——C 失败走**退避重试**，且**不能让 `Pending` 永久卡住**：超过等待上限后**以 A+B 结论为准并显式记录** `completed_by = "A+B (C 未通过)"`。
- 反之 C 也不能是**唯一**证据：有些下载器完成即关句柄，A 的临时后缀信号才是主线索。

**退避策略**：`1s → 2s → 5s → 10s → 30s`，5 次仍失败 → 状态置 `pending`，UI 显示「待处理（文件被占用）」，并在 watcher 下一次事件或空闲重扫时重试。**永不放弃、永不删源**。

**采样驱动**：不轮询目录（浪费），而是由基础架构 §3.5 的 `FileWatcher`（`ReadDirectoryChangesW`）事件驱动：`FILE_ACTION_ADDED` / `RENAMED_TO` → 启动该文件的「稳定计时」；每个待定文件用一个合并的 `QTimer`（如 500 ms tick）统一做 A+B+C 判定，避免每文件一个定时器。

**可选增强（默认关闭）**：从浏览器 History 库补全来源信息（下载 URL / referrer / MIME）。
- 技术路径：主浏览器识别读注册表 `HKCU\Software\Microsoft\Windows\Shell\Associations\UrlAssociations\http\UserChoice` 的 `ProgId`（`ChromeHTML` / `MSEdgeHTM` / `FirefoxURL`）→ 定位其 profile 的 `History` SQLite → Chrome 运行时持有排他锁，**必须先把 `History` + `-wal` + `-shm` 复制到临时目录再用 Qt SQL 只读打开** → `SELECT ... FROM downloads WHERE target_path = ?`。
- **隐私**：读浏览器历史属敏感操作，默认关闭（`sources.browser.enrichFromHistory: false`），首次开启需明确提示，数据仅存本地 DB、不上传、可一键清除。
- Firefox 的下载记录在 `places.sqlite` 的 `moz_annos`，结构更绕，本期不实现。

## 2.4 源适配器（IDownloadSource）——为 QQ/微信/钉钉预留的扩展点

```cpp
class IDownloadSource {
public:
    virtual ~IDownloadSource() = default;
    virtual QString   sourceId()   const = 0;   // "browser", "wechat", "qq", "dingtalk"
    virtual QString   displayName() const = 0;  // "浏览器下载"

    virtual QList<WatchRoot> roots() const = 0; // { dir, includeGlobs, recursive }

```

已注册适配器与目录发现策略：

| source | 目录 | 说明 |
|---|---|---|
| `browser` | **`SHGetKnownFolderPath(FOLDERID_Downloads)`** | 不要硬编码 `%USERPROFILE%\Downloads`：用户可通过「属性→位置」重定向，且 OneDrive 可能接管。`AppIndexer` 已在用 `SHGetKnownFolderPath`，复用同一套 |
| `wechat` | `%USERPROFILE%\Documents\xwechat_files\<wxid>\msg\file\<YYYY-MM>`（4.x）/ `WeChat Files\<wxid>\FileStorage\File\<YYYY-MM>`（3.x） | 版本间路径差异大 → **配置优先 + 候选路径探测**，不做硬编码假设 |
| `qq` | `Documents\Tencent Files\<QQ>\nt_qq\nt_file\...`（NT 版）/ `FileRecv`（旧版） | 同上 |
| `dingtalk` | `DingTalk\` 及用户自定义接收目录 | 同上 |

**通用的源发现算法**（避免版本变化导致失效）：
1. 用户显式配置的路径（最高优先级，配置文件里可见可改）；
2. 已知候选路径（上表，逐个 `QDir::exists`）；
3. 启发式扫描 `Documents` 与用户目录下匹配已知目录名模式（`*WeChat Files*`、`xwechat_files*`、`Tencent Files*`、`DingTalk*`）的目录；
4. 命中的候选**在设置面板列给用户确认**（不静默接管陌生目录——接管错目录会移动用户的工作文件）。

**多源去重**：同一文件被两个源同时看到（例如用户把微信接收目录指向 Downloads）→ 以**规范化绝对路径**为主键，先声明者获胜（`INSERT OR IGNORE`）。

## 2.5 拉取到 box 与失败处理

```cpp

```

| 场景 | 处理 |
|---|---|
| 目标同名 | 自动改名 `name (1).ext`、`name (2).ext`（在目标目录内绕过重名，语义清晰），DB 记录 `dup_index` |
| 跨卷大文件 | 先查目标卷剩余空间（`GetDiskFreeSpaceExW`），不足则**放弃移动并告警**，绝不删源；复制过程回报进度（状态栏 + 「最近下载」栏进度条） |
| 长路径 > 260 | 全程 `\\?\` 前缀；exe 清单声明 `longPathAware` |
| 被占用/被杀软扫 | 退避重试（复用 §2.3 的退避表），超时 `pending` |
| 进程中途被杀 | `move_journal` 先写 `intent` 再执行 → 启动时对账：`state='moving'` 的行检查目标是否存在且 size 匹配 → 补完（删源）或回滚（清目标残留） |
| 目标在同步盘/只读目录 | 配置校验阶段就拒绝把 box 设在被排除目录、系统目录、只读卷内 |

## 2.6 去向追踪引擎（本功能第二个技术核心）

**问题**：用户把文件从 box 移走后，box 的 watcher 只会给一个 `FILE_ACTION_REMOVED`（或 `RENAMED_OLD_NAME`）——**它不告诉你文件去哪了**。而在新位置所在目录的 watcher 上你会看到一个 `FILE_ACTION_ADDED`（或 `RENAMED_NEW_NAME`），但你无法直接把它和 box 里消失的那个文件对应起来（多个文件同时移动时尤其如此）。这是"记录文件移动后的路径"这个需求的真正难点。

**解法：入 box 时登记「身份指纹」，用指纹把两个互相独立的事件关联起来。** 不扫全盘，也不猜。

### 第一步：入 box 时登记指纹

追踪判定要用到**三种身份**，含义不同、不可互相替代（混用是这类功能最容易出错的地方）：

| 身份 | 由什么构成 | 回答的问题 | 用在哪 |
|---|---|---|---|
| **物理身份**<br>Physical Identity | `(volumeSerial, FileId)` | 「这是不是同一个 NTFS 文件对象？」 | 同卷关联（改名/移动后不变）、box 内对账 |
| **内容身份**<br>Content Identity | `quickSig` | 「内容是不是同一个？」（概率性，非严格） | 跨卷关联（`FileId` 必变）、查重 |
| **元数据身份**<br>Metadata Identity | `size` + `mtime`（`name` 仅作辅助） | 「这个候选够不够像？」用于**缩小候选**，不用于**最终确认** | 离线反查的第一级筛选（§2.6 第六步） |

登记时同时采集三者：

```
physical  = ( volumeSerial, FileId )           ← GetFileInformationByHandleEx(FileIdInfo)
content   = quickSig = Sha256( size ‖ 首 64KB ‖ 尾 64KB )   ← 见 §2.10
metadata  = size, mtime, name
```

**关联规则（对应第三步的路径 A/B）**：

```
同卷：  physical 相等  →  再用 metadata 校验（防 FRN 复用）→ 确认
跨卷：  metadata 缩小候选  →  content 比对  →  唯一命中 → 确认
```

**为什么要分层**：物理身份是最强的（精确、改名不影响），但只在同卷有效；内容身份跨卷有效但有读取成本且是概率性的；元数据身份最便宜但最弱（**绝不能单独用于确认**）。按"强度递减、成本递增"的顺序组合，才能同时满足"准确"和"便宜"。

**关键性质**：NTFS 上 `FileId`（FRN）**在同卷内重命名/移动后保持不变**——这就是我们能关联"消失"与"出现"的物理依据。而取它只需一个我们本来就能打开的句柄：**无需管理员权限、无需读 USN 日志**。

**同样关键的推论**：用户完全可能**改名 + 移动**（`报告.pdf` → `2024报告终版.pdf`），所以**绝不能靠文件名关联，必须靠指纹**。

### 第二步：检测「离开 box」

box 的 watcher 报出 `FILE_ACTION_REMOVED` / `RENAMED_OLD_NAME` → 该下载记录进入 `Tracking`，开启追踪窗口（`tracking.windowSec`，默认 60 s）。

### 第三步：定位新位置（三条路径，按优先级）

| 路径 | 适用 | 判定依据 | 权限 |
|---|---|---|---|
| **A. 指纹精确关联**（同卷，覆盖绝大多数情况） | 新位置在已监听目录内（索引根 + `tracking.extraWatchDirs`） | 其它 watcher 报出 `ADDED`/`RENAMED_NEW_NAME` → 打开候选文件读 `FileId` → 与登记指纹**精确相等**（含卷序列号）→ 确认 | 免管理员 |
| **B. 签名关联**（跨卷 / 指纹不可用） | 跨卷移动是"复制 + 删除"，`FileId` 必然变化 | 窗口内候选满足 `size 相等 ∧ mtime 相等` → 再比 `quickSig`，**唯一命中**才确认 | 免管理员 |
| **C. USN Journal**（可选增强，默认关闭） | 目标目录不在监听范围，仍想精确定位 | `FSCTL_READ_USN_JOURNAL` 直接读 `RENAME_OLD_NAME` / `RENAME_NEW_NAME` 事件对（含 FRN），跨目录也能配对 | **读卷句柄需以读权限打开，通常需管理员权限** → 默认关闭，开启时明确提示提权代价 |

**实测验证（本机，`fsutil file queryfileid` + `Move-Item`）**：

| 操作 | FileId | 修改时间 | 源文件 | 结论 |
|---|---|---|---|---|
| 同卷重命名 | `0x…001700000000204e` → **完全一致** | 保留 | 消失 | 路径 A 成立 |
| 同卷跨目录移动（`a\a.txt` → `a\sub\a.txt`，即 box → 同盘某文件夹的真实场景） | `0x…00070000000bc00d` → **完全一致** | 保留（创建时间也保留） | 消失 | **路径 A 成立** |
| 跨卷移动（C: → E:） | `0x…003f00000000c4f6` → `0x…001800000000204e`（**变了**） | **完整保留**（2020-01-02 精确一致） | 消失 | **路径 B 成立**，且 mtime 判据可靠 |

两条推论：
1. 跨卷移动时 FileId 必然变化，**所以 `quickSig` 必须在入 box 时就算好**（本机 C: → D: 的归档会频繁走路径 B，不能懒计算）——这正是 §2.10 那条"不能懒计算"的实证依据。
2. 跨卷拖动的本质是"复制 + 删源"，因此大文件中途会在目标盘产生 `ADDED` 事件但 size 未写完 → **`size` 相等这一条天然拒绝了未完成的候选**，不会误判。

> 说明：以上用 `Move-Item`（PowerShell，跨卷同样走 copy+delete）验证的是**文件系统语义**；Explorer 鼠标拖动走 `IFileOperation`，修改时间保留行为一致，但仍需在 S10 验收里用**真实鼠标拖动**复测一次。

**绝不猜测**：窗口内没有唯一匹配 → 置 `Unknown`，UI 给「在整个索引里查找（按指纹 / 名字+大小）」「手动指定位置」「标记为已删除」三个出口。**不允许**把"多个候选里挑一个"写进库——记错位置比不知道位置更糟。

### 第四步：多级移动链

用户可能连续移动多次（box → 项目A → 归档2024）。新位置大多落在索引根内，**索引的 watcher 会继续报告该路径的变化**，于是同一套「离开 → 关联」逻辑可以**递归工作**：每次确认后更新 `downloads.cur_path`，并向 `tracking_events` **追加一条链式记录**。「最近下载」里展示当前位置，并可展开查看完整轨迹（回答"这个文件我到底放哪了"）。

### 第五步：兜底与对账

| 场景 | 处理 |
|---|---|
| 移动到未监听目录（如未纳入索引的 `D:\随意`） | 用 `tracking.extraWatchDirs`（**只监听、不索引**的目录，成本极低，建议把常用归档目录加进去）覆盖；仍找不到 → `Unknown` + 手动定位 |
| **关机期间移动**（错过事件） | 事件全部丢失 → 走**离线对账**（详见第六步），靠状态比对 + 指纹/签名反查恢复位置 |
| 用户改名 + 移动 | 指纹照样命中（不依赖名字） |
| 用户在别处**复制**（box 原件还在） | 不触发追踪，状态保持"待整理"（§2.2） |
| 用户直接从 box 删除 | 窗口内无匹配且文件已不存在 → `Deleted`（可选提示可从回收站还原） |
| **FRN 复用风险** | 删除后文件号可能被系统重用 → 指纹确认**必须同时校验 size + mtime**（必要时 `quickSig`），不接受"只看 FileId" |

### 第六步：程序关闭期间的变更（离线对账）

**后果分两层，机制完全不同**：

| 层 | 关闭期间发生了什么 | 处理机制 |
|---|---|---|
| 索引层 | 文件被新建 / 删除 / 改名 / 移动 | 已有的**差量扫描**（基础架构 §3.5：磁盘遍历 vs `files` 表 → added/removed/changed），**无需新机制** |
| 追踪层 | box 里的文件被移走 / 改名 / 删除；源目录里出现新下载 | **启动离线对账**（本节）：事件全部丢失，只能靠"状态比对 + 反查" |

**核心思路**：离线期间没有事件可用，但我们**有指纹和签名**——把它们当搜索键，去启动扫描的结果里**反查**。

#### 对账四级（从便宜到贵，逐级升级）

**级别 0 — box 目录内对账**（必做，成本 = box 内文件数，通常几十个）
枚举 box 目录，对每个文件取 `FileId`，与 DB 里 `in_box=1` 的记录比对：

| 情况 | 判定 | 动作 |
|---|---|---|
| 路径相同 | 无变化 | 更新 `last_verified` |
| **FileId 命中但路径不同** | 在 box 内被**改名**了 | 更新 `box_path`（改名不改内容，指纹不变） |
| FileId 命中但 size/mtime 变了 | 同一文件被**改过内容** | 更新元数据 + 重算 `quickSig` |
| **没命中** | 文件已离开 box | 进入级别 1 |

**级别 1 — `(size, mtime)` 反查 + `quickSig` 确认**（主路径，覆盖绝大多数）
对每个"已离开 box"的记录，在 `files` 表里按 `(size, mtime)` 查候选（走 `idx_files_sizemtime` 索引）：

- 候选 1 个 → **算 `quickSig` 确认**（读首尾各 64 KB）→ 命中即 `FiledAway`（`confidence=strong`，`method=startup-rescan`）
- 多个候选 → 逐个算 `quickSig`；**唯一命中才确认**，否则落 `Unknown`
- 0 个候选 → 级别 2

**关键性质**：这个判据**不含文件名**，所以离线期间"**改名 + 移动**"照样本命中；而修改时间在同卷移动与跨卷复制中都会保留（§2.6 实测表已证实），所以**跨卷离线移动也命中**。**离线期间的多级移动（box → A → B）能一步直接跳到最终位置**——因为 size/mtime 一路都没变。

**级别 2 — 文件名反查 + `FileId` 确认**（覆盖"移动后又编辑过"）
若文件被移走后**又被编辑**（mtime 变了），级别 1 失效。此时改用**原文件名**在 `files` 表里搜候选 → 对候选**取 `FileId` 与登记指纹比对**（同卷移动 FileId 不变）→ 精确命中。

**级别 3 — 兜底与告知**
- `tracking.extraWatchDirs` 里的目录额外做一次**启动补扫**（只取 name/size/mtime/FileId，不建索引），覆盖"归档到未索引的常用目录"
- 仍找不到 → `Unknown`，UI 显示「程序关闭期间移动，位置未知」+ 三个出口：在整个索引里搜 / 手动指定位置 / 标记为已删除
- **不自动判定为"已删除"**：把"不知道"和"删了"混为一谈会让用户以为文件没了（且我们并未真去检查回收站）

#### 一个必须写清的设计决定：索引里**不存** `FileId`

反查要靠指纹，那为什么不让 `files` 表在扫描时顺便存下每个文件的 `FileId`？
**因为那要为每个文件付一次 `CreateFileW + GetFileInformationByHandleEx`**——20 万文件会让扫描从秒级变成几十秒级，代价不可接受。

所以走**两级筛选**：先用 `(size, mtime)` 在 DB 里把候选缩到个位数（索引查询，微秒级），**只对候选集按需取 `FileId`**（几次系统调用，几乎免费）。这与查询层的"位图预筛 → 精细打分"是同一个思想：**便宜的判据先做，昂贵的手段只用在少数候选上**。

#### 时序（很重要，最容易做错）

```
1. 载入 DB → 立即可查询（已有设计）
2. move_journal 的 intent 对账（我方中断的动作）
3. ✗ 此时不能跑去向反查 —— 索引还没扫完，候选集是空的
4. 差量扫描【每完成一个根目录】就对该根的候选做一次流式反查
   （D 盘扫完就能匹配 D 盘的归档，不必等 C 盘）
5. 全部扫描完成后再做一次收尾反查，把仍未决的落 Unknown
6. 结论批量写入 tracking_events，并向「最近下载」栏发一次汇总
```

**UI 反馈**：「最近下载」栏顶部显示「正在核对离线变更…」，完成后给汇总——「离线期间 3 个文件已归档（2 个已知位置，1 个位置未知）」。**安静地改写历史记录而不告知，会让用户觉得这套记录不可靠**。

#### 离线期间的**新下载**（源目录里冒出来的新文件）

- 判据：位于已注册源目录 + 落在**关机窗口**内（`app_meta.last_exit_at` ~ 本次启动）+ 无临时后缀
- 但"Downloads 里的新文件"也可能是**用户自己手动放进去的**，无法百分百区分
- 因此默认 `inbox.offlineCatchUp: "prompt"`：在「最近下载」栏列出来**询问**，用户点一下才拉入 box；`auto` 在关机窗口内自动拉取；`off` 完全忽略
- 精确判据只在开启 `sources.browser.enrichFromHistory` 时可用（查浏览器 History 的 `downloads` 表，默认关闭）

#### 能力矩阵（离线场景哪些能救、哪些不能）

| 离线期间发生的 | 能否自动定位 | 依据 |
|---|---|---|
| 同卷移动到已索引目录（含改名） | ✅ | `(size,mtime)` → `quickSig` |
| 跨卷移动到已索引目录 | ✅ | mtime 保留（实测）→ `quickSig` |
| 多级移动（box → A → B） | ✅ 直接跳到最终位置 | `(size,mtime)` 一路未变 |
| 移动到 `extraWatchDirs` 目录 | ✅ | 启动补扫 |
| 在 box 内改名 | ✅ | 级别 0 的 `FileId` 对账 |
| 移动后又编辑过（**同卷**） | ✅ | 级别 2：名字 + `FileId` |
| 移动后又编辑过（**跨卷**） | ❌ → `Unknown` | FileId 已变、mtime 已变，无稳定判据 |
| 移动到未索引且未配置的目录 | ❌ → `Unknown` | 反查范围之外 |
| 被删除 | 标 `Unknown`（需用户确认） | 不自动判"已删除" |
| 归档到**被排除规则挡住**的目录（如 `node_modules`） | ❌ → `Unknown` | 这类目录不入 `files` 表（实践中可忽略；确有需要就加进 `extraWatchDirs`） |

> 注意：`kindFilter` **白名单不影响反查**——因为"DB 全量入库、快照按白名单构建"（§0 决定 1），`files` 表里始终是全量。这是那条设计决定的又一个红利。

### 开销

- 每条追踪记录在窗口期内最多做 **O(候选数)** 次 `CreateFileW + GetFileInformationByHandleEx`（微秒级），候选数来自同窗口内其它目录的新增事件，正常为个位数；
- **零轮询**：全部由 watcher 事件驱动，窗口超时由一个合并定时器处理；
- 不扫盘、不遍历目录树、不哈希整个文件（除非走到签名路径且需裁决）。

## 2.7 状态机

```
                 ┌──────────── Detected（watcher 报告新文件）
                 ▼
        Stabilizing（A/B/C 三条件判定 + 退避重试）
          ├── 通过 → Ready
          ├── 超时 → Pending ──(事件/空闲重扫)──▶ Stabilizing
          └── 命中排除规则（临时后缀/过小/白名单外） → Skipped（终态，可手动接管）
                 ▼
              Ready ──▶ Fetching（Downloads → box，journal 先写 intent）
                          ├── 成功 → InBox（登记指纹 + quickSig）
                          └── 失败 → Pending / Failed(error_code)

  ── 以上是「我们做的」；以下是「用户做的」，我们只观察、不干预 ──

              InBox（待整理；UI 展示滞留天数）
                ├── 用户移出 box ──▶ Tracking（窗口内关联新位置）
                │                      ├── 指纹/签名唯一命中 → FiledAway（cur_path = 新路径）
                │                      └── 超时 / 多候选未决 → Unknown（提供手动定位）
                ├── 用户在别处复制（原件仍在 box） ──▶ InBox（不变，不追踪、不删）
                ├── 用户删除 ──▶ Deleted
                └── 用户在我方 UI 点「撤销接管」 ──▶ Undone（退回 Downloads）

              FiledAway ──(再次移动)──▶ Tracking ──▶ FiledAway（cur_path 更新，链追加）
                                                     └──▶ Unknown
```

## 2.8 快速管理（"依据该文件夹快速管理"）

**动作清单**（「最近下载」栏 + 搜索结果里对 `:dl` 结果同样可用右键菜单）：

| 动作 | 说明 |
|---|---|
| 打开 / 用…打开 | `ShellExecuteW`；「用…打开」走 `SHOpenWithDialog` 或 `Rundll32 shell32.dll,OpenAs_RunDLL` |
| **跳转到所在文件夹**（选中即跳转，本栏核心动作） | `explorer.exe /select,"<cur_path>"` 打开并选中该文件；**未移动的 → 定位到 box** |
| 复制路径 | 复制**当前位置**（已归档的复制新路径，未移动的复制 box 路径） |
| 重命名（含批量模板） | 模板如 `{date}-{name}`、`{name}_{n}`，支持多选批量 |
| 移动到… | 记住最近 5 个目标目录 |
| 归档到分类 | 触发 §2.9 的规则（默认 `suggest`，用户确认才移动） |
| **加入待办** | 联动既有 `TodoDatabase`：文件路径作为待办内容，形成"下载了要看的 PDF → 待办"闭环 |
| 复制内容到剪贴板 | 文本文件直接读入 `ClipboardDatabase`；图片可复制为图片句柄 |
| 查重 | 触发 §2.10 的签名比对，命中则提示「与已有文件相同」并给出保留选择 |
| 删除到回收站 | `FOF_ALLOWUNDO`，多选批量 |
| 撤销上一次操作 | 基于 `move_journal`，含移动/重命名/归档 |

**UI：新增「最近下载」栏（`RecentDownloadsPage.qml`，挂在 `MainPanel` 侧栏，与剪贴板/待办同级）**：
- **两个分段**：「待整理（仍在 box）」置顶，**「已归档」**（已被用户移出）按时间倒序；
- 列表列：名称（种类徽章）/ 大小 / 下载完成时间 / 来源 / **当前位置**（`box` 或 `文档/2024-报告` 这样的友好路径）/ 状态徽章 / **box 滞留天数**；
- **选中即跳转**：跳转到文件**现在**所在的文件夹并选中它；未移动的定位到 box（§2.8 动作表）；
- 顶部：Chip 筛选（全部 / 待整理 / 已归档 / 文档 / 图片 / 安装包 / 今天）+ 搜索框；
- 底部动作条：多选批量动作 + 撤销 + 统计（今日 N 个 / 待整理 M 个 / 合计 X MB）；
- **状态可见性**：`Unknown` / `Pending` / `Failed` 必须醒目——"文件位置不明却静默不报"是这个功能最不可接受的失败模式；
- 托盘通知：接管成功后 `QSystemTrayIcon::showMessage("已接管 report.pdf (2.1 MB)")`；用户移出后的去向通知（`"report.pdf → 文档/2024"`）**默认关闭**，避免打扰。

**与检索的集成**：box 是普通索引根之一，因此：
- 新接管文件**初始 frecency 给 0.6**，立刻排在搜索结果前列（"我刚下的东西"是最常见意图）；文件被归档后 frecency 跟随 `cur_path` 迁移，不会丢；
- 支持 `:dl` / `in:box` / `src:chrome` 过滤；
- 结果 `subtitle` 显示「来源 · 大小 · 完成时间 · 当前位置」，比裸路径有用。

## 2.9 归档规则引擎（可选，默认关闭）

```json
{
  "inbox": {
    "path": "%LOCALAPPDATA%/AssistantTeam/Assistant/Inbox",
    "firstRunPolicy": "newOnly",
    "offlineCatchUp": "prompt",
    "onExternalCopy": "keep",
    "autoOrganize": false,
    "undoRetentionDays": 30,
    "tracking": {
      "windowSec": 60,
      "extraWatchDirs": ["D:/归档"],
      "useUsnJournal": false,
      "notifyOnFiledAway": false
    },
    "rules": [
      { "name": "文档建议放文档区", "priority": 20, "match": { "kind": "document,sheet,slide,pdf" }, "action": "suggest", "dest": "D:/文档/{yyyy}-{MM}" },
      { "name": "图片建议放图片区", "priority": 30, "match": { "kind": "image" }, "action": "suggest", "dest": "D:/图片/{yyyy}-{MM}" },
      { "name": "大文件提醒", "priority": 5, "match": { "size": ">500mb" }, "action": "notify" }
    ]
  }
}
```

- **默认不自动移动**（`autoOrganize: false`）：规则的默认动作是 `suggest`——在「最近下载」里给该文件标一个"建议去向"，用户点一下才移动。理由见 §2.2：归档是用户的决定。
- 若用户显式开启自动归档，可把动作改成 `move`（带 `dest` 模板），此时**求值按 `priority` 升序、首个命中即生效**（first-match-wins，比"多规则叠加"可预测得多），无语序命中 → `keep`（留在 box 根）。
- **动作**：`suggest`（推荐去向）/ `move`（自动移动，需开启 autoOrganize）/ `notify`（仅通知）/ `skip`（不接管，留在原下载目录——用于"我只想要文档，安装包别动"这类诉求）。
- **模板变量**：`{inbox} {name} {ext} {kind} {yyyy} {MM} {dd} {source}`。
- **安全**：规则产生的目标路径必须通过校验（无 `..`、不落在被排除目录、不发生自我覆盖）；一旦自动移动，必须走同一套 `move_journal` 以便撤销。
- **UI**：规则的增删改 + 「试运行」（对当前 box 文件 dry-run 预览会怎么移动，不实际动手）——让用户敢开自动化的关键。

## 2.10 查重与身份签名

```
quickSig = Sha256( size_le64 || 首 64 KB || 尾 64 KB )     ← 99% 情况足够区分，成本极低
fullSig  = Sha256( 全文 )                                  ← 仅当 quickSig 撞上时才计算
```
- 入库时**只算 quickSig**（大文件也不慢：两次各 64 KB 读）；`fullSig` 懒计算、只对大文件且仅当需要裁决时算。
- 用 `QCryptographicHash`（Qt 内置，无新依赖）。不用 MD5（撞库风险），不引入 xxHash/BLAKE3 依赖（本项目没必要）。
- **双重用途**：`quickSig` 不只是查重凭据，也是**去向追踪的关联凭据**（§2.6 路径 B：跨卷移动时 `FileId` 会变，只能靠它确认"消失的文件"与"出现的文件"是同一个）。因此**入 box 时就必须算好并入库**，不能懒计算。
- 命中重复 → 状态标 `Duplicate`，UI 提供「保留新的 / 保留旧的 / 两个都留」，并在搜索里降权。
- 注意：同名同大小但内容不同（如两份不同的 `报告.pdf`）不会被 quickSig 误判为重复的概率极低，但**裁决必须用 fullSig**，避免误删。

## 2.11 数据表（独立 `downloads.db`，connection name `"downloads"`）

沿用项目既有约定（每功能独立 DB 文件 + 独立连接名，见 `ClipboardDatabase`）。

**两个 DB 的边界必须守死**（也见基础架构 §2.2 / §3.6）：

| DB | 性质 | 谁可以写 |
|---|---|---|
| `file_index.db`（`files`/`dirs`/`roots`/frecency） | **派生数据**，可从磁盘重建 | 只有 `FileIndexDatabase`；迁移失败可直接重建 |
| `downloads.db`（`downloads`/`move_journal`/`tracking_events`/`download_rules`/`sources`） | **权威数据**，磁盘上重建不出来 | 只有 `DownloadsDatabase`；迁移**必须备份**，失败拒绝启动 |

- `FileIndexDatabase` **不许**查 `downloads.db`，`DownloadsDatabase` **不许**管 `files` 表；两者只通过 `FileIndex::upsert(path)` / `remove(path)` 这种接口通信（§2.12）。
- 二者都要走 `DatabaseMigrator`（`PRAGMA user_version`、前向迁移、`ALTER TABLE ADD COLUMN`、禁止 `DROP TABLE` 重建）——细节见基础架构 §3.6。

```sql
PRAGMA journal_mode=WAL;
PRAGMA synchronous=NORMAL;

CREATE TABLE IF NOT EXISTS downloads (
  id           INTEGER PRIMARY KEY,
  source_id    TEXT NOT NULL,          -- browser / wechat / qq / dingtalk
  src_path     TEXT NOT NULL,          -- 来源路径（Downloads / 微信接收目录…）
  box_path     TEXT,                   -- 拉入 box 时的路径（登记时刻）
  cur_path     TEXT,                   -- **文件当前所在路径**（去向追踪持续更新）
  in_box       INTEGER NOT NULL DEFAULT 0,  -- 1 = 仍在 box（待整理）
  name         TEXT NOT NULL,
  ext          TEXT,
  cat_mask     INTEGER NOT NULL DEFAULT 0,
  size         INTEGER NOT NULL DEFAULT 0,
  mtime        INTEGER NOT NULL DEFAULT 0,
  vol_serial   INTEGER,                -- 身份指纹：卷序列号
  file_id      TEXT,                   -- 身份指纹：FileId 128-bit hex（§2.6 第一步）
  sig_quick    TEXT,                   -- 入 box 时必算（查重 + 跨卷去向关联）
  sig_full     TEXT,                   -- 懒计算，仅裁决重复时算
  url          TEXT,                   -- 可选增强：下载 URL
  referrer     TEXT,
  pipe_state   TEXT NOT NULL,          -- 管线状态（一次性）：Detected/Stabilizing/Ready/Fetching/InBox/Pending/Failed/Skipped/Undone
  track_state  TEXT NOT NULL,          -- 去向状态（持续）：InBox/Tracking/FiledAway/Unknown/Deleted
  detected_by  TEXT,                   -- watcher-frn / watcher-sig / usn / startup-rescan / manual
  dup_of       INTEGER REFERENCES downloads(id),
  error_code   INTEGER,
  tags         TEXT,
  created_at   TEXT NOT NULL DEFAULT (datetime('now','localtime')),
  completed_at TEXT,
  fetched_at   TEXT,                   -- 拉入 box 完成时刻
  filed_at     TEXT,                   -- 检测到"已归档"（移出 box）的时刻
  last_verified TEXT
);
CREATE INDEX IF NOT EXISTS idx_dl_pipe    ON downloads(pipe_state);
CREATE INDEX IF NOT EXISTS idx_dl_track   ON downloads(track_state, in_box);
CREATE INDEX IF NOT EXISTS idx_dl_created ON downloads(completed_at DESC);
CREATE INDEX IF NOT EXISTS idx_dl_sig     ON downloads(sig_quick);
CREATE INDEX IF NOT EXISTS idx_dl_cur     ON downloads(cur_path);

CREATE TABLE IF NOT EXISTS move_journal (      -- 撤销与崩溃对账的唯一依据
  id          INTEGER PRIMARY KEY,
  download_id INTEGER REFERENCES downloads(id),
  batch_id    TEXT,
  op          TEXT NOT NULL,                   -- fetch / rename / organize / trash / undo（**仅记录我方动作**）
  from_path   TEXT NOT NULL,
  to_path     TEXT,
  op_state    TEXT NOT NULL,                   -- intent / done / failed（崩溃对账用）
  error_code  INTEGER,
  at          TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);
CREATE INDEX IF NOT EXISTS idx_journal_batch ON move_journal(batch_id);
CREATE INDEX IF NOT EXISTS idx_journal_state ON move_journal(op_state);

CREATE TABLE IF NOT EXISTS tracking_events (    -- 去向链：回答"这个文件我到底放哪了"
  id          INTEGER PRIMARY KEY,
  download_id INTEGER NOT NULL REFERENCES downloads(id),
  from_path   TEXT NOT NULL,
  to_path     TEXT,                             -- NULL = 未能定位（Unknown）
  method      TEXT NOT NULL,                    -- watcher-frn / watcher-sig / usn / startup-rescan / manual
  confidence  TEXT NOT NULL,                    -- exact（指纹命中）/ strong（size+mtime+quickSig）/ unknown
  at          TEXT NOT NULL DEFAULT (datetime('now','localtime'))
);
CREATE INDEX IF NOT EXISTS idx_track_dl ON tracking_events(download_id, at);

CREATE TABLE IF NOT EXISTS download_rules (
  id         INTEGER PRIMARY KEY,
  name       TEXT NOT NULL,
  enabled    INTEGER NOT NULL DEFAULT 1,
  priority   INTEGER NOT NULL DEFAULT 100,
  match_json TEXT NOT NULL,
  action     TEXT NOT NULL,
  dest       TEXT,
  hit_count  INTEGER NOT NULL DEFAULT 0       -- 命中统计：让用户看到规则是否真的有用
);

CREATE TABLE IF NOT EXISTS sources (
  source_id  TEXT PRIMARY KEY,
  enabled    INTEGER NOT NULL DEFAULT 0,
  paths_json TEXT,                             -- 用户确认过的监听目录
  last_seen  TEXT
);

CREATE TABLE IF NOT EXISTS app_meta (           -- 离线窗口判定（§2.6 第六步）
  key   TEXT PRIMARY KEY,                       -- last_exit_at / last_reconcile_at / schema_version
  value TEXT
);
```

> **建模要点**：`pipe_state`（我们的一次性管线）与 `track_state`（文件的持续位置状态）**必须分成两个字段**。一个文件在 box 里只被"拉取"一次，但可以被移动很多次；把两者塞进同一个 `state` 枚举是这类功能最常见的数据建模错误（第二次移动就无处安放）。
>
> `tracking_events` 是**追加型**的（只插入、不更新），因此天然形成「box → 项目A → 归档2024」的完整轨迹；`downloads.cur_path` 只是这条链的最新节点缓存。

**启动对账（两件事，必须在任何 ingest 动作之前跑）**：
1. **我方动作对账**：`SELECT * FROM move_journal WHERE op_state='intent'` → 逐条核对源/目标存在性与 size → 补完或回滚，结论写回 `done`/`failed`。这是"自动化搬文件"崩溃后不丢数据的保证。
2. **box 物理对账（中转语义必需）**：`SELECT * FROM downloads WHERE in_box=1` → 逐个检查文件是否**仍在 box 里**；不在的 → 说明是**关机期间被用户移走/删除了**，进入追踪流程（因错过事件，改用**索引快照按指纹/签名反查**，见 §2.6 第五步）。跳过这一步会导致「最近下载」里长期挂着一堆"待整理"幽灵条目。

| **B**（S8） | 种类与排除：`FileClassifier` + `ExcludeRuleSet`/`ProjectGuard` + `QueryParser` + 快照 `catMask/flags` + Chip UI | 完成即"搜索 + 可控范围"的完整功能；**先做 B 再做 C**，因为 `catMask/flags` 是 `files` 表的 v1→v2 迁移用例，顺便把 `DatabaseMigrator` 立起来 |
| **C**（S9） | Download Box 骨架 | **此阶段不做 Tracking**：先让"下载 → 判定 → 入 box → 用户看到"闭环跑通；`IDownloadSource` 只实现 `BrowserSource`（系统 Downloads），**不碰 IM**、不读浏览器 History |
| **D**（S10） | 去向追踪：`FileId` 同卷 → `quickSig` 跨卷 → 离线对账四级 → `Unknown` 兜底 UI | **先写测试再接 UI**（关联逻辑是纯函数，可合成用例全覆盖）；**USN Journal 单独作为 D7 最后做**：需要提权、有 journal 生命周期问题，且默认关闭——没有它系统依然正确（`Unknown` 是合法终态） |
| **E**（S11） | 归档规则（默认 `suggest`）+ dry-run + 查重 + Todo/剪贴板联动 + IM 源适配器 | IM 源是**最后**才做的（每个都需要真实环境验证目录与"边接收边判定"） |

| Step | 内容 | 验收标准 |
|---|---|---|
| **S8 种类与排除** | `FileClassifier` + `ExcludeRuleSet`/`ProjectGuard` + QueryParser + 快照 `catMask/flags` + 过滤 Chip UI + 配置 | 工程目录（含 node_modules）剪枝后条目数/耗时对比有数据；白名单切换 < 50 ms 且不扫盘；`:doc` `ext:pdf` `-词` golden 用例全绿 |
| **S9 box 骨架** | `DownloadsDatabase`（双状态建模）+ `IngestEngine`（A/B/C 判定 + 退避）+ `FileIdentity`（指纹采集）+ `BrowserSource`（`FOLDERID_Downloads`）+ 拉入 box / 撤销 + 「最近下载」栏（待整理/已归档分段 + 跳转）+ 托盘通知 + **启动双对账** | 浏览器下载 100 次端到端：0 次误拉未完成文件、0 次覆盖同名、100% 可撤销；完成后 ≤ 3 s 出现在「待整理」且 `:dl` 可搜到；跳转定位准确 |
| **S10 去向追踪** | `TrackingEngine`：离开检测 + 指纹关联（同卷）/ 签名关联（跨卷）+ USN 可选 + 多级移动链 + `Unknown` 兜底 UI + **离线对账四级**（§2.6 第六步） | 实时用例：同卷移动、**改名后移动**、跨卷移动、移动到 `extraWatchDirs`、直接删除、**别处复制（不许误报为已归档）**；离线用例：先关程序再移动（同卷/跨卷/改名/多级/移动后编辑），重启后位置正确恢复，救不回的必须落 `Unknown`；误判 0 |

## 4. 风险与不做的部分

| 风险 | 应对 |
|---|---|
| **误移用户文件**（最严重） | 只处理 manifest 内文件；三条件判定；首次启用只接管新文件；全量 journal 可撤销；删除走回收站；配置校验拒绝危险路径 |
| **去向误判**（把别的文件认成这个文件，比"不知道"更糟） | 指纹（卷序列号 + FileId）+ size + mtime 三重校验；跨卷必须 `quickSig` 唯一命中；**多候选一律落 `Unknown` 并让用户指定，绝不猜** |
| box 被清空 → 误以为是故障 | box 定位为**中转站**（§2.2）：UI 用"待整理 + 滞留天数"表达，不追求常驻；清空即"全部已归档"的正常终态 |
| 目标目录不在监听范围（移动到未索引的盘） | `tracking.extraWatchDirs` 覆盖常用归档目录；仍找不到 → `Unknown` + 「在整个索引里查找」+ 手动指定位置 |
| **关机期间移动**（错过全部事件） | **离线对账四级**（§2.6 第六步）：box 内 `FileId` 对账 → `(size,mtime)`+`quickSig` 反查 → 名字+`FileId` 反查 → `Unknown` + 手动定位；必须**等扫描到该根之后**才反查（流式），否则候选集为空；否则「待整理」会堆积幽灵条目 |
| 离线期间新下载与用户手动放文件的混淆 | 默认 `offlineCatchUp: "prompt"`：**只列出来问用户**，不自动搬走（用户自己也往 Downloads 放文件，无法百分百区分） |
| FRN 复用（删除后文件号被系统重用） | 指纹确认**必须同时校验 size + mtime**（必要时 `quickSig`），绝不"只看 FileId" |
| 用户「复制」而非「移动」 | 以 **box 内物理是否存在**为准：原件仍在 → 状态不变、不追踪、不删任何东西（`onExternalCopy: keep`） |
| 浏览器临时后缀/行为变化 | 临时后缀与 settleMs 做成适配器参数 + 用户可配置；三条件里命名信号只作其一，不单靠它 |
| IM 目录随版本变化 | 配置优先 + 候选探测 + 用户确认；不硬编码单一版本路径 |
| 读浏览器历史引隐私顾虑 | 默认关闭、显式开启、仅本地存储、可一键清除 |
| 归档规则误分类 | 默认 `suggest` 不自动移动；开启自动时 dry-run 预览 + 命中统计 + 首个命中即止 + 可撤销 |
| 杀软/OneDrive/网络盘干扰（占用、占位、同步抖动） | 退避重试 + `pending` 可见 + box 不放在同步盘（配置校验提示） |
| 索引 / box / 追踪三路对同一变更重复处理 | 拉取与追踪确认后**直接提交增量补丁**，并让 watcher 事件按路径去重（200 ms 合并窗口） |

**明确不做**：
- 不做文件内容全文检索（基础架构 §8.2 已排除，需另立项并启用 `sqlite3[fts5]`）；
- 不做下载加速/断点续传（不替代浏览器与下载器）；
- 不做云盘双向同步、不做跨设备；
- 不接管浏览器「另存为」到任意目录的文件（除非用户在 `sources.browser.paths` 里显式添加该目录）；
- 不自动删除任何文件（只做移动到回收站，且需用户操作）；
- **不猜测文件去向**：关联不确定时显示 `Unknown` 并请用户指定，绝不把"看起来像"的路径写进记录；
- **不做归档代理**：不替用户决定文件该放哪（自动归档默认关闭，规则默认只给建议）。
