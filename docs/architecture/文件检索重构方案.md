## 1. 现状问题清单

### P0 — 正确性 / 稳定性

| 编号 | 问题 | 根因位置 | 后果 |
|---|---|---|---|
| P0-1 | `QDirIterator` 默认过滤器（`QDir::NoFilter`）**包含符号链接**，`Subdirectories` 会跟随目录符号链接/junction 递归 | `FileSearcher.cpp:77-78` | 用户目录里指向父目录的 junction（OneDrive/开发目录常见）→ 重复索引甚至无限递归 |
| P0-2 | 跳过判定逐文件做 `QDir::toNativeSeparators()`（**每条文件分配一个 QString**）+ 5 次 `contains` | `FileSearcher.cpp:36-44` | 纯性能问题，但放在最热的内循环里，属于设计错误 |
| P0-3 | `20000` 上限**按遍历顺序任意截断**，遍历顺序取决于目录项返回顺序 | `FileSearcher.cpp:79-92` | 结果不可解释：同一台机器两次启动索引内容可能不同；D 盘文件永远进不来 |
| P0-4 | 索引构建在主线程、`engine.load()` 之前**同步**执行 | `main.cpp:66` | 文件多时窗口出现前白屏（冷启动被拖到数百 ms～数秒） |
| P0-5 | 索引建完即冻结，**无任何失效机制**（无 watcher、无手动刷新入口） | `FileSearcher.cpp:48` | 新建/重命名/删除的文件在本次运行中永远不反映 |
| P0-6 | namespace + 文件级静态 `s_index`，无实例、无注入点 | `FileSearcher.cpp:33` | 不可单元测试、不可 mock、不可多实例；与项目其他模块风格不一致 |

> **P0-1 根因修正（2026-09-24，A1 实测）**：光给 `QDirIterator` 加 `QDir::NoSymLinks` **修不掉**。
> ①Qt 的 `QFileInfo::isSymLink()` 只认 `IO_REPARSE_TAG_SYMLINK`，junction 是
> `IO_REPARSE_TAG_MOUNT_POINT`（Qt 6.2 专门补了 `isJunction()` 就是因为它俩不等价）；
> ②`QDirIterator` 的过滤器只决定"返回哪些条目"，**不决定"是否递归"**，`Subdirectories`
> 模式下没有"不下降进某子目录"的开关。A1 实测：加了这个 flag 之后，一个指回父目录的
> junction 仍让索引里多出 126 条 63 层叠罗汉路径。→ P0-1/P0-2 都只能在**是否递归**
> 这一层修，`QDirIterator` 这条路不通（A1 已改用自控递归，A3 换 Win32 迭代栈）。
> 另：本机 Desktop 3.5 万文件 vs 20000 上限 → 索引**全部是 Desktop 的**，
> `Documents`/`Downloads`/`Pictures` 一个文件都没进来，**P0-3 的实际优先级高于原判断**。
> 详见 `docs/troubleshooting/qt-nosymlinks-挡不住junction.md`。

### P1 — 性能

| 编号 | 问题 | 现状代价 |
|---|---|---|
| P1-1 | 每次按键**全量线性扫描** 2 万条，且逐条走完整五级打分 | O(N·L)，2 万条量级约 5–15 ms（未实测，需 §9 补基准） |
| P1-2 | 每轮 `FuzzyMatcher::score` 内部反复 `toLower()`，**每次分配新 QString** | N 次堆分配 / 按键 |
| P1-3 | 收集全部命中（`reserve(1024)` 可能溢出/浪费）后 `std::sort` 全排序，再 `erase` 截断 | O(M log M) + 大数组拷贝，而只需要 top-K |
| P1-4 | `QString`(UTF-16) 存 `name` + `path` 两份，目录字符串高度重复 | 2 万条 ≈ 数 MB；目标是 20 万条级别 |
| P1-5 | `AppBridge::search` 每次按键（长度≥2）同步 `INSERT INTO search_history` | 每按键一次磁盘事务（WAL）；历史表被 `re`/`rep`/`repo`… 前缀垃圾污染 |
| P1-6 | QML `onTextChanged` 无防抖，连打字逐字触发全链路 | 输入 8 个字符 = 8 次全量检索 |

### P2 — 检索质量 / 体验

| 编号 | 问题 | 期望 |
|---|---|---|
| P2-1 | **只匹配文件名**，路径不参与 | `报告` 应能命中 `D:\项目\2024\报告\doc.docx`，且输 `2024 报告`（空格分词）可命中 |
| P2-2 | 子序列匹配缺失 | `chr` 匹配不到 `chrome_installer.exe`，而这是启动器的核心卖点 |
| P2-3 | 无 frecency/使用频率权重 | 常打开的文件应上浮 |
| P2-4 | 空查询时文件完全不出现 | 空查询应显示「最近文件」区块（frecency top-N） |
| P2-5 | 中文场景：IME 预编辑（拼音串）会触发检索 | `niha` 会打到后端并算一次；且中文文件名无法用拼音首字母命中 |
| P2-6 | 只匹配含扩展名的全名 | `report` 匹配 `report.docx` 可以（contains），但 `docx` 会命中大量噪音，缺少「扩展名独立权重」 |
| P2-7 | 结果动作单一：只有「打开」 | 缺「打开所在文件夹」（Ctrl+Enter）、「复制路径」 |

### P3 — 能力缺口

- 无索引持久化：每次冷启动从零爬盘（P0-4 的根因之一）。
- 无内容全文检索（本次**不做**，见 §8.2）。
- 无可配置根目录/排除规则（硬编码 6 个 `QStandardPaths`）。
- 无索引健康度可观测（规模、耗时、命中率、watch 溢出次数都没有暴露）。

## 2. 目标架构

三层 + 一条反馈回路：

```
┌── 采集层 Indexer ──────────────────────────────────────────────┐
│  Scanner（后台线程）: Win32 目录遍历 + ReadDirectoryChangesW     │
│  Store（SQLite）   : files / dirs / roots 表，批量事务差量更新   │
│  产出 → 不可变快照 Snapshot（COW 发布）                          │
└───────────────────────────┬───────────────────────────────────┘
                            │ std::shared_ptr<const Snapshot>
┌── 查询层 QueryEngine ──────▼───────────────────────────────────┐
│  归一化 → 位图预筛 → 分层打分 waterfall → top-K 堆              │
│  + 增量细化缓存（type-ahead）+ 防抖 + 世代计数器（丢弃过期结果） │
└───────────────────────────┬───────────────────────────────────┘
                            │ QList<Match>
┌── 融合层 ResultMerger ─────▼───────────────────────────────────┐
│  ISearchProvider 多路归并（k-way merge）+ frecency 综合分       │
└───────────────────────────┬───────────────────────────────────┘
                            │ 用户执行
┌── 反馈层 Frecency ─────────▼───────────────────────────────────┐
│  只在「执行」时写 frecency / history → 影响下一轮打分            │
└───────────────────────────────────────────────────────────────┘
```

### 2.2 FileIndex 的职责边界（**防上帝对象**，本方案最重要的架构约束）

`FileIndex` 是**门面**，只做四件事：持有依赖、转发调用、持有当前快照、暴露状态。**它不实现** DFS、SQL、模糊匹配、watcher、下载、追踪、规则。

```cpp
class FileIndex {                       // 门面：薄
public:
    void start();                       // 启动：载 DB → 建快照 → 后台扫描 → 起 watcher
    void refresh();                     // 手动重建（配置变更后）
    QList<Match> query(const Query &q); // 转发给 QueryEngine
    IndexStats   stats() const;
    void upsert(const QString &path);   // 供 Ingest/Tracking 提交增量（§3.5）
    void remove(const QString &path);
private:
    std::unique_ptr<FileScanner>       m_scanner;
    std::unique_ptr<FileIndexDatabase> m_database;
    std::unique_ptr<SnapshotManager>   m_snapshots;   // COW 发布
    std::unique_ptr<QueryEngine>       m_query;       // 查询
    std::shared_ptr<const Snapshot>    m_current;     // 当前快照
};
```

判定标准（每次想给 `FileIndex` 加方法时先问）：**这个逻辑能不能放进上面四个协作者之一？** 能，就别加到门面上。下载/追踪同理——它们是 `FileIndex` 的**客户**（通过 `upsert/remove` 通信），不是它的成员。

### 2.3 目标目录结构（**等 A2/A3 落地后再移动，不要现在大搬家**）

```
src/
├── core/
│   ├── file/        FileIndex, FileScanner, FileWatcher, FileSnapshot, FileClassifier, ExcludeRuleSet
│   ├── search/      QueryEngine, QueryParser, ScoreEngine, FuzzyMatcher
│   └── download/    IngestEngine, TrackingEngine, FileIdentity, IDownloadSource
├── database/        FileIndexDatabase, DownloadsDatabase, DatabaseMigrator
```

理由：类数量已经上双（13+），平铺在 `core/` 下会让"哪些属于搜索、哪些属于下载"失去视觉边界。但**移动目录会打乱 include 路径与 `file(GLOB_RECURSE)`（需重新 configure）**，所以安排在搜索链路稳定之后一次性做，避免与功能改动混在同一个提交里。

## 3. 采集层设计

### 3.1 数据结构：先把**逻辑字段**定死，物理表示**先简单、后按测量优化**

**逻辑字段**（这些是设计要表达的内容，与物理表示无关；v1 全部都要有）：

| 字段 | 用途 | 备注 |
|---|---|---|
| `name` | 展示 + 匹配 | 原始大小写 |
| `nameLower` | 匹配 | 预折叠小写，**v1 就必须有**（见下） |
| `path` | **定位键**（不是文件身份，见 §3.6） | 可由 `dirId` + `name` 还原 |
| `dirId` / `extId` | 目录范围过滤 / 扩展名权重 | 字典编码 |
| `size` / `mtimeSec` | 元数据过滤 + **离线去向反查**（治理 §2.6 第六步） | 反查的关键判据 |
| `charMask` | 位图预筛（§4.2） | 优化项 |
| `catMask` | 种类过滤（治理 §1.6） | 治理功能 |
| `flags` / `rootId` / `originId` | `Project`/`InBox`…、`in:`、`src:` 过滤 | 治理功能 |
| `frecency` | 排序加权（§5.4） | Phase A 末 |

**v1 物理表示（先做这个）**：`std::vector<FileEntry>`，`FileEntry` 内用 `QString name/path` + 上述标量字段，`nameLower` 一并预存。
- 20 万条估算 ≈ 50–70 MB（`QString` 头 + 堆缓冲 + 路径重复）→ **超过目标 30 MB、低于预算 40 MB**（§9 的三档口径）
- 选它的理由：实现直白、与现有代码和 Qt API 一致、出错面小；**而上面那些"省内存"的手段都不是当前已知的瓶颈**

**优化候选（全部 gated：先跑 baseline，命中阈值才做，按收益/复杂度排序）**：

| 优化 | 触发条件 | 收益 | 复杂度 |
|---|---|---|---|
| `nameLower` 预计算 | **不 gate，v1 就做** | 消除每按键 N 次 `toLower()` 堆分配（现状 P1-2） | 极低（一个字段） |
| 目录字典编码（`dirId`） | 内存 > 预算 | 消除路径重复，约 10× | 低 |
| SoA 拆列 | P99 超阈值且 profile 显示 cache miss 主导 | 顺序扫描带宽 | 中 |
| UTF-8 存储 | 内存 > 预算，且 SoA 已做仍不够 | 字符串内存减半 | **中高**（大小写/归一化要自己处理，非 ASCII 风险最高） |
| `charMask` 位图预筛 | P99 超阈值且候选集仍大 | 省 60–90% DP 调用 | 低（一个字段 + 一条 AND） |
| 细化缓存（type-ahead） | 上一条仍不够 | 消除重复扫描 | 中（正确性有坑，§4.5） |

**唯一的硬约束**：**物理表示必须藏在 `Snapshot` 的只读接口之后**（`nameAt(i)` / `pathAt(i)` / `lowerAt(i)` / `sizeAt(i)` …），查询引擎只通过接口访问，不直接摸容器。

> 这才是"先简单、后优化"能成立的前提：上面任何一项改动都能单独替换，不波及查询层与测试。反过来，如果 v1 就让查询层直接遍历 `vector<FileEntry>`，后面换表示法就要重写查询引擎——那才是真正的复杂度代价。

（另：P1-2 的"N 次 `toLower()` 分配"属于**现状缺陷**而非优化，所以 `nameLower` 不进 gate。）

### 3.2 遍历算法：目录级剪枝 + 迭代式 DFS

现有 `QDirIterator` **无法剪枝子树**（不能跳过已进入的目录），这是 P0-1/P0-2 的结构性根因。改为自建迭代栈：

```
stack = roots
while stack:
    dir = pop
    if isReparsePoint(dir) or dirName in SkipList: continue        # 目录级剪枝，每目录一次而非每文件一次
    entries = FindFirstFileExW(dir + "\*", FindExInfoBasic, FIND_FIRST_EX_LARGE_FETCH)
    for e in entries:
        if e.isDir: stack.push(child)                              # 不跟随 reparse point（P0-1）
        else: emit(e)                                              # 一次拿全 name/size/mtime，零额外 stat
```

优于现状的三点：
1. **Win32 `FindFirstFileExW` + `FIND_FIRST_EX_LARGE_FETCH`**：一次系统调用批量返回 `WIN32_FIND_DATA`（含大小/时间），省掉 `QDirIterator` 每项一次 `stat`；`FindExInfoBasic` 不取短名（8.3），更快。
2. **目录级剪枝**：累加式 `std::string_view` 路径，全程零分配（用栈式路径缓冲区，push/pop 尾段）。
3. **不跟随 reparse point**：直接规避 P0-1 的递归风险，不需要额外 visited-set。

**治理功能的挂载点（L2/L3 过滤，见 `文件治理功能设计.md` §1.6）**：
- 目录枚举结果先过 `ProjectGuard`（哨兵文件识别 + `projectPolicy: skip/demote/index`）与 `ExcludeRuleSet`（目录名/目录 glob）→ 决定**是否下探**，命中即整棵子树一次跳过（`skip` 下 `node_modules` 这类目录的收益是数万条目级）；
- 通过的文件先过 `FileClassifier` 得到 `catMask` 再写 DB；
- **DB 全量入库（只受排除规则约束），内存快照按当前 `kindFilter` 白名单构建** → 切换「只要文档 / 全都要」只重建快照、不重扫磁盘。

保留现有关键策略：**跳过隐藏项**（`FILE_ATTRIBUTE_HIDDEN`/`SYSTEM`，沿用现状语义）、跳过 `node_modules`/`.git`/`.cache`/`__pycache__`/`.svn`，新增可配置排除（§7）。

### 3.3 上限策略：**完整索引优先，绝不静默驱逐**（修 P0-3）

早期草稿设计过「索引满 → 按 frecency 驱逐」。**这个设计是错的，已废弃**：文件索引被驱逐后，用户搜 `important` 搜不到自己明明存在的文件，行为变成"文件会凭空消失"——对搜索来说，**正确性远比内存重要**。

改为三档，全部**显式可见**：

| 档 | 阈值 | 行为 |
|---|---|---|
| 正常运行 | ≤ 软预算（默认 30 万条） | 无提示，全量索引 |
| **超预算** | > 软预算 | **继续索引**，只在日志 + 设置面板显示实际条目数与占用，并给出"如何缩小规模"的引导 |
| 硬保护上限 | > 硬上限（默认 100 万条） | **停止索引**（不驱逐已有条目）并在状态栏醒目提示"索引已达上限，X 个目录未纳入"；附一键跳设置 |

**控制规模的手段是"少收"而不是"事后丢"**，而项目里已经有正确的工具：`roots` 白名单、`ExcludeRuleSet`、`ProjectGuard`、`kindFilter`（治理功能）——把选择权交给用户，而不是替用户丢掉文件。

（`files` 表本身是全量入库的，条目数多不等于快照大：快照按 `kindFilter` 白名单构建，两者是两条独立的规模杠杆。）

### 3.4 线程模型：COW 快照，读无锁

```
GUI 线程                         工作线程 (QThread)
  FileIndex::query()  ──读──▶  m_snapshot (shared_ptr<const Snapshot>)
                                   ▲
                     build() 新 Snapshot ── 原子发布 ──┘
```

- 构建阶段在工作线程上造**全新** `Snapshot`，构建完 `m_snapshot.store(newSnap)` 一次性发布。
- 读者取 `m_snapshot.load()` 得到 `shared_ptr` 副本后整轮查询期间无需加锁（快照不可变，天然线程安全）。
- 发布原语：优先 `std::atomic<std::shared_ptr<const Snapshot>>`（C++20，MSVC 19.3x 支持）；若编译不过，降级 `std::shared_mutex` 读写锁（读多写极少，也可选）。
- **不用 `QReadWriteLock` + 原地修改**：原地改会迫使查询持锁、且索引重建期间阻塞 UI，与 P0-4 的修复目标冲突。
- GUI 线程永不阻塞：索引未就绪时 `query()` 返回空 + `indexingReady=false`，QML 显示「正在建立索引…」。

### 3.5 持久化与差量更新

SQLite 只做**冷启动加速 + frecency 存储**，不做查询路径（查询走内存快照）。注意区分两种「过滤」：**排除规则（L2/L3）决定什么进 DB**，**种类白名单（kindFilter）只决定内存快照装什么**——后者因此可以随时切换而无需扫盘。

```sql
PRAGMA journal_mode=WAL;
PRAGMA synchronous=NORMAL;
PRAGMA cache_size=-8000;

CREATE TABLE IF NOT EXISTS dirs (
  id   INTEGER PRIMARY KEY,
  path TEXT NOT NULL UNIQUE
);

CREATE TABLE IF NOT EXISTS files (
  path       TEXT PRIMARY KEY,   -- 规范化绝对路径
  name       TEXT NOT NULL,      -- 原始大小写
  name_lower TEXT NOT NULL,      -- 折叠小写
  dir_id     INTEGER NOT NULL REFERENCES dirs(id),
  ext        TEXT,
  size       INTEGER NOT NULL,
  mtime      INTEGER NOT NULL,   -- Unix 秒
  frecency   REAL    NOT NULL DEFAULT 0
) WITHOUT ROWID;
CREATE INDEX IF NOT EXISTS idx_files_dir  ON files(dir_id);
CREATE INDEX IF NOT EXISTS idx_files_free ON files(frecency DESC);
-- 下面这条是「离线去向反查」用的（治理文档 §2.6 第六步）：按 (size,mtime) 把候选缩到个位数，
-- 再只对候选取 FileId / 算 quickSig。索引里**不存** FileId，否则扫描要为每个文件付一次系统调用。
CREATE INDEX IF NOT EXISTS idx_files_sizemtime ON files(size, mtime);

CREATE TABLE IF NOT EXISTS roots (
  path       TEXT PRIMARY KEY,
  enabled    INTEGER NOT NULL DEFAULT 1,
  last_scan  INTEGER
);
```

**启动流程（两阶段）**：
1. `loadFromDb()`：一条 `SELECT` 灌满快照（20 万行 ≈ 数十 ms）→ **立即可查询**，UI 无白屏。
2. 后台扫描：与 DB 内容做**三方差集**，只处理变化：

```
diskSet   = 磁盘遍历结果 {(path, size, mtime)}
dbSet     = SELECT path,size,mtime FROM files
added     = diskSet − dbSet
removed   = dbSet − diskSet
changed   = 交集内 (size,mtime) 不等者
```

写回用单事务 + `prepared statement` 批量（`BEGIN IMMEDIATE` … `COMMIT`，每 1000 行一提交），避免每行一次 fsync。

**运行期增量**：`ReadDirectoryChangesW(..., bWatchSubtree=TRUE, FILE_NOTIFY_CHANGE_FILE_NAME|DIR_NAME|SIZE|LAST_WRITE)`，每根目录一个句柄。必须处理两类失败：
- `ERROR_NOTIFY_ENUM_DIR`（缓冲区溢出，目录变更太快）→ **降级为该根目录全量重扫**，累加 `watchOverflowCount` 指标；
- OneDrive/网络盘占位文件不可靠 → 兜底**空闲期定时重扫**（如 10 min，仅在窗口隐藏且 CPU 空闲时）。

> 不用 `QFileSystemWatcher` 的原因：它的 Windows 后端基于 `FindFirstChangeNotification`，单句柄**不递归子树**，对 6 个根目录下成千上万子目录会退化成「枚举并逐目录注册句柄」，句柄数爆炸且新增子目录需重新注册。`ReadDirectoryChangesW` 一个句柄管整棵子树，语义正确得多。

**三消费者设计（治理功能需求）**：`FileWatcher` 同时服务三条链路——索引链路（内容变更 → 增量 upsert）、box 链路（新文件 → 完成度判定 → 拉入）、**去向链路（任意监听目录的新增/重命名事件 → 与待追踪指纹比对）**。三者对「新文件」的语义需求不同（索引关心最终状态，box 关心"是否写完"，追踪关心"这个新出现的文件是不是刚离开 box 的那个"），所以 `FileWatcher` 只负责**产出标准化事件**：完成度判定（三条件 + 退避）放在 `IngestEngine`，身份关联放在 `TrackingEngine`。box 拉取与去向确认完成后**直接通知 `FileIndex` 做增量 upsert**，不绕回 watcher，避免同一变更被处理两次（按路径 200 ms 合并去重）。

### 3.6 Schema Migration 与"谁是权威数据"

两个 DB 的**性质不同，迁移策略必须不同**：

| DB | 性质 | 迁移失败怎么办 |
|---|---|---|
| `file_index.db` | **派生数据**（可从磁盘重建） | **丢弃重建**（代价 = 重扫一遍），不背复杂迁移的历史包袱 |
| `downloads.db` | **权威数据**（下载记录 / 去向链，磁盘上重建不出来） | **必须迁移 + 先备份**；失败则**拒绝启动**并保留备份，**绝不静默重建** |

实现约定：
- 版本号用 SQLite 原生 `PRAGMA user_version`（不额外建表）。
- **只做前向迁移**：`migrate_1_to_2()` / `migrate_2_to_3()` … 顺序执行，**每步一个事务**；**禁止 `DROP TABLE` + 重建**（会丢数据）；加列用 `ALTER TABLE … ADD COLUMN`（SQLite 支持，带默认值即可）。
- **启动时序**：打开 DB → 读 `user_version` → 逐版本迁移 → commit → **之后才允许任何其它 DB 访问**。迁移必须是第一个动作，不能"用到哪个表再顺手建"。
- 备份：`downloads.db` 迁移前复制为 `downloads.db.bak-v<ver>-<date>`，保留最近 2 份。
- **落地时机**：本方案的字段增补（`cat_mask` / `flags` / `root_id` / `origin_id`、`idx_files_sizemtime`）就是 v1 → v2 的第一个真实用例，**A3 就要把这个框架做出来**，不要等到"以后需要再加"。

**附：`files.path` 是定位键，不是文件身份**
- `files` 用 `path` 作主键是对的——它本质是一个**路径索引**：同一物理文件出现在两个路径（硬链接、重复复制）就该有两行，搜索时也都该被搜到。
- **物理身份**（`volumeSerial` + `FileId`）只属于 `FileIdentity`，只服务下载 box 与去向追踪（治理 §2.6），**不进 `files` 表**（性能论证见治理 §2.6 第六步）。
- 把这条边界写死，以后就不会出现"两个模块对'同一个文件'理解不一致"的隐性 bug。

## 4. 查询层设计

### 4.1 分层打分 waterfall（便宜的先行、昂贵的有门禁）

> **v1 先做朴素版**：线性扫描 + 分层 tier 判定 + top-K 堆 + 多词 AND。
> 位图预筛（§4.2）与增量细化缓存（§4.5）属于 §3.1 的 **gated 优化候选**——等 §9 第一步的 baseline 出来、确有需要再上。结构上先按 `QueryEngine` 的四个子步骤（Parser → CandidateFilter → Score → TopK）分好，插入优化时不用改动调用方。

```
输入 q（原始）
 1. 归一化      NFC + 折叠小写（若全 ASCII 走 std::string 快路径），得 qLo, qMask
 2. 候选集      ← 增量细化缓存：q 以上次查询为前缀 ? 上次候选 : 全量
 3. 位图预筛    (charMask[i] & qMask) == qMask ?          ← O(1)/条，通常淘汰 90%+
 4. tier 判定   exact / prefix / word-boundary / contains ← memchr + memcmp，无分配
 5. 精细打分    仅对 tier ≥ 阈值者跑 ScoreEngine（DP）
 6. top-K       min-heap 维护 K 个最佳                        ← 替代全排序
```

### 4.2 位图预筛算法（关键性能杠杆）

给每个字符映射到 64 位中的一个 bit（`char → bitIndex`，用一张 256 项的 `uint8_t` 表把 ASCII 压到 64 桶，非 ASCII 归入溢出桶并置 `hasNonAscii` 标志）。索引条目存 `charMask`，查询也算出 `qMask`：

```cpp
if ((entry.charMask & qMask) != qMask) continue;   // 缺任一查询字符 → 必然不匹配
```

- 正确性：子序列匹配的必要条件就是「查询字符集 ⊆ 目标字符集」，所以不会漏结果（安全剪枝）。
- 收益：ASCII 短查询（2–4 字符）能淘汰绝大部分条目，且是单条 `AND` + 分支预测友好的顺序扫描，实测常规能省 60–90% 的 DP 调用（fzf 类工具采用同类位图预筛思路）。
- 非 ASCII（中文）查询：`qMask` 命中溢出桶，预筛自动退化为「不筛」，正确性不受影响，只损失加速。

### 4.3 匹配算法选型

| 层级 | 算法 | 说明 |
|---|---|---|
| 精确 / 前缀 | `std::string_view::compare` / `starts_with` | 零分配，命中即最高 tier |
| 词边界 | 分隔符表 `space - _ . / \ (` 后首字符比较 | 索引期可预生成「词首字符掩码」进一步加速 |
| 子串 | `memchr` 找首字符 + `memcmp` 校验 | 短串上显著快于 BMH/KMP；不引入第三方 |
| 子序列（**新增，修 P2-2**） | **fzf v2 的 Smith-Waterman 变体**：DP + 位置加成表（首字符/词边界/CamelCase/连续命中加成，gap 罚分），单行滚动数组 | 提供「chr → chrome_installer.exe」与大写缩写「CI → Chrome Installer」体验；O(len(q)·len(name))，靠 §4.2 预筛把调用次数压下来 |
| 拼写容错 | **有界编辑距离（Ukkonen cutoff / 带状 DP）**：仅当 len(q) ≥ 4 且前面全部失败时启用，带宽 `k = 1+(len(q)>=8)`，超界立即返回 | 修 typo（`reprot` → `report`），且因为带宽限制复杂度从 O(n·m) 降到 O(k·n) |
| 相似度排序（可选后期） | Damerau-Levenshtein（补相邻换位） | 只在编辑距离 tier 内做最终排序微调 |

**多词查询（修 P2-1）**：按空白切词，逐词对「文件名 + 词首字符 + 目录段」做 AND 匹配，任一 token 无匹配即剪掉；路径命中给较低 tier 权重（文件名 > 目录名 > 全路径）。

### 4.4 top-K 选择（修 P1-3）

```cpp
std::priority_queue<Match, std::vector<Match>, std::greater<>> heap;  // 大小为 K 的 min-heap
for (...) { if (heap.size() < K) heap.push(m); else if (m.score > heap.top().score) { heap.pop(); heap.push(m); } }
```

复杂度 O(N log K)，K=20 时 log K ≈ 4.3，且**只分配 K 个结果**（现状：`reserve(1024)` + 全排序 + 截断）。收尾用 `std::sort_heap` 输出有序列表。

### 4.5 增量细化缓存（type-ahead refinement）

打字序列 `r → re → rep → repo → repor → report` 上，后一次候选集是前一次的子集，只需在**上次候选**上筛，不必回全量：

```cpp
struct RefineCache { std::string query; std::vector<uint32_t> candidates; };
if (!cache.query.empty() && startsWith(qLo, cache.query))  pool = cache.candidates;
else                                                       pool = all();
```

配合「缓存深度 1 + 长短查询回退」（查询长度 ≤ 2 时不吃缓存，避免大候选池被反复扫）即可拿到大部分收益，内存开销一个 `vector<uint32_t>`。**注意**：候选集必须存**上一轮全部命中**（而非 top-K），否则会出现「结果凭空消失」的 bug —— 这是本方案最容易踩的坑，需在基准/用例里覆盖。

### 4.6 防抖与过期结果丢弃（修 P1-6）

- **QML 侧**：`onTextChanged` 不再直接调 `backend.search`，改为 `debounceTimer.restart()`（`interval: 40`）；同时拦截 IME 预编辑：`if (searchInput.inputMethodComposing) return;`（修 P2-5）。
- **C++ 侧**：`AppBridge::search` 内 `const quint64 gen = ++m_queryGen;`，异步路径回填前校验 `gen == m_queryGen`，不匹配直接丢弃，防止旧查询覆盖新结果。
- 40 ms 是体验与开销的折中（低于 30 ms 几乎无合并效果，高于 80 ms 手感变钝）；最终值以 §9 的主观延迟测试为准。

### 4.7 复杂度对比

| 阶段 | 现状 | 重构后 |
|---|---|---|
| 候选规模 | N（全量） | N → 预筛后 c（常为 5%–30%）→ 细化缓存后更小 |
| 打分 | N × 五级（含 N 次 `toLower` 分配） | c × 位图 + tier；DP 仅 d 条（d ≪ c） |
| 选择 | O(M log M) 全排序 + 截断 | O(c log K) 堆 |
| 结果分配 | M 个 `SearchResult` | K 个 |
| 主线程阻塞 | 建索引同步阻塞启动 | 0（后台线程 + DB 冷启动秒开） |

## 5. 融合层与排序

### 5.1 提供者抽象

```cpp
class ISearchProvider {
public:
    virtual ~ISearchProvider() = default;
    virtual QString providerId() const = 0;
    virtual QList<SearchResult> query(std::string_view text, int limit) = 0;
};
```

`FileIndex`、`AppIndexer`（改造为 provider）、`Calculator`、内置命令各自实现；`AppBridge` 只负责：
1. 按查询特征决定**启用哪些 provider**（纯数字+运算符才启用 Calculator，避免每次按键都跑解析器）；
2. **k-way merge**：各 provider 取 top-K 后归并（`std::partial_sort` 或 k 路堆），而非现状「拼一个大 `QList` 再全排序」（`AppBridge.cpp:120-125`）；
3. 结果去重（同一路径被 app/file 双份命中）、`SearchResult` 转换、状态栏文案。

### 5.2 综合分公式

```
finalScore = 1000·tierWeight + quality(0..200) + 150·frecency + typeBonus
```

- `tierWeight`：沿用 `FuzzyMatcher` 现有五级语义（精确 1.0 / 前缀 0.9 / 词边界 0.8 / 包含 0.6–0.4 / 编辑距离 0.4–0）——**保持现状语义不变**，只把「同一 tier 内的精细程度」交给 `quality`（fzf DP 归一化输出）与 `frecency`。
- `frecency` ∈ [0,1]，见 §5.4；`typeBonus`：文件 0 / 应用 +30 / 内置命令 +40（同分时应用与命令优先，符合启动器直觉）。
- 计算结果落在 `SearchResult::score`，QML 侧无需改动即可复用现有排序展示。

### 5.3 搜索历史写入时机（修 P1-5）

现状「每次按键 INSERT」改为：
- **执行**时写 `command_history` / frecency（唯一有价值的信号）；
- 每次按键的查询**不落盘**；若确实要保留搜索词统计，改为**会话结束/窗口隐藏时批量提交一条**（去重前缀：只保留最长那次查询）。

### 5.4 frecency 反馈回路

**衰减分桶（Mozilla Places 风格，简单稳）**：

| 最近使用距今 | 权重 |
|---|---|
| < 4 小时 | 100 |
| < 1 天 | 70 |
| < 1 周 | 50 |
| < 4 周 | 30 |
| < 6 月 | 10 |
| 更早 | 0 |

`frecency = min(Σweights / 300, 1.0)`（300 ≈ 三次「刚用过」即饱和）。查询时读内存快照里的 `frecency` 数组（构建快照时从 `files.frecency` 载入），执行后**异步**更新 DB 与内存快照中该条的值（不动其它字段，无需重建快照）。

### 5.5 空查询的「最近文件」（修 P2-4）

空查询时不返回空，而是返回 frecency top-8 的**最近使用文件**作为独立分组（`subtitle: "最近使用"`），与内置命令并列；`FileSearcher` 现有的「空查询不返回文件」语义在 `providerId == "files"` 层面保留，由融合层单独发这条 query。

### 5.6 并行化：先测再上

20 万条 + 位图预筛的预期单线程耗时约 1–3 ms，**低于** 4 ms 的目标预算内。因此：**默认单线程**，仅当 §9 基准显示 P99 > 8 ms 时，才启用 `Qt6::Concurrent` 分片（按 `Snapshot` 连续区间切 4 片，各片取 top-K，最后 k-way merge）。理由：并行化引入线程池竞争、结果非确定性排序、缓存行争用，代价高于本期收益，且会掩盖真正该做的算法优化。

```json
{

    "enabled": true,
    "roots": ["%DESKTOP%", "%DOCUMENTS%", "%DOWNLOADS%", "%PICTURES%", "%MUSIC%", "%MOVIES%", "D:/Work"],

    "debounceMs": 40,
    "watchEnabled": true,
```

- 路径支持 `%DESKTOP%` 之类占位符展开（`QStandardPaths` 映射），便于跨机迁移。

- **治理功能新增两节**：`fileIndex.kindFilter` / `fileIndex.exclude`（种类白名单、排除规则、工程策略）与 `inbox` / `sources`（box 路径与去向追踪参数、归档规则、下载源开关与目录）——完整 schema 见 `文件治理功能设计.md` §1.7 / §2.9。

## 8. 技术选型对照

### 8.1 选型总表

| 关切 | 选择 | 理由 |
|---|---|---|
| 索引存储 | **内存 COW 快照** + SQLite 持久化 | 查询路径零 IO；持久化解决冷启动与 frecency |
| 持久化引擎 | 现用的 SQLite（vcpkg sqlite3 3.53.3，经 Qt6::Sql） | 项目已用、够用；无需新增依赖 |
| 目录遍历 | Win32 `FindFirstFileExW`(`FindExInfoBasic` + `LARGE_FETCH`) | 批量返回元数据、可目录级剪枝、规避符号链接递归 |
| 变更监听 | `ReadDirectoryChangesW`（递归、每根一句柄） | 单句柄管子树，优于 `QFileSystemWatcher` 的注册式模型 |
| 预筛 | 64 位字符位图 + 增量细化缓存 | 每条约 1 条 AND，无漏检风险 |
| 子序列打分 | fzf v2 风格 Smith-Waterman 变体 DP | 启动器体验基准线（chr→chrome） |
| 拼写容错 | 有界编辑距离（Ukkonen cutoff / banded DP） | 只在长查询+全失败时启用，复杂度可控 |
| top-K | min-heap O(N log K) | 消除全排序与 1024 预留 |
| 并发 | 单线程查询 + 后台索引线程 + COW 发布 | 实测优先，避免过度并行化 |
| 并行查询 | 预留（Qt6::Concurrent 分片） | 仅 P99 > 8 ms 时启用 |

### 8.2 明确不选的技术及理由

| 候选 | 不选的理由 |
|---|---|
| **SQLite FTS5**（含 trigram tokenizer） | ① **本机当前不可用**：vcpkg sqlite3 只启用 `json1`，`FTS5`/`FTS3`/`rtree` 均未编译（已扫描 `sqlite3.dll` 验证），要用得先 `vcpkg install "sqlite3[fts5]"` 并可能触发 qtbase 重配；② 即便可用，trigram tokenizer 只解决**子串**，不解决子序列（`chr`→`chrome`）与拼写容错，而后者才是启动器主场景；③ 倒排索引对 2–3 字符查询选择率极低，postings 扫描量接近全量，却额外付出索引体积；④ 仍要回表取 `path`/`frecency` 再排序，无法替代内存打分。**结论：文件名检索不用 FTS5**；若将来做「文件内容全文检索」，再单独立项并启用 `sqlite3[fts5]`（或该场景改上独立的全文引擎）。 |
| Xapian / Tantivy(Rust) / Lucene | 为文档级全文检索设计，索引体积、查询延迟、构建时间都远超「文件名模糊检索」需求；引入 C++ 之外的语言运行时或重依赖，与「学习项目、边做边学」的定位不符。 |
| RocksDB / LevelDB | 只解决 KV 存储，不解决匹配算法；本项目数据量（20 万级）用不上 LSM。 |
| 三元组倒排（自建 trigram index） | 能加速子串，但内存约等于名字长度 × 常数（20 万条 ≈ 数十 MB），与 §3.1 的快照方案收益重叠、复杂度更高，本期不做。 |
| `QFileSystemWatcher` | 见 §3.5，非递归 + 句柄爆炸。 |
| 直接上多线程并行查询 | 见 §5.6，先优化算法常数与候选集，再考虑并行。 |

## 9. 验收指标与度量手段

新增 `tests/bench_file_index.cpp`（`QElapsedTimer` + 合成语料）。

**第一步：先建 baseline，不设断言。**
本文档早期版本写的 `P50 < 3 ms / P99 < 8 ms` 是**没有实测支撑的估计**（连现状 2 万条的 5–15 ms 都标注为"未实测"）。所以先只测、只记录：

| 规模 | 测什么 |
|---|---|
| N = 2 万 / 5 万 / 10 万 / 20 万 | 查询 P50 / P95 / P99（查询长 1–3、4–8 两档）、冷启动到可查询、全量扫描耗时、快照内存 |

记录到 `docs/devlog/`，**据此再定优化目标**。理由很直接：为了一个拍脑袋的 3 ms 去堆复杂算法，是这套方案里最可能发生的浪费。

**第二步：baseline 出来后，用三档口径设阈值**（Target = 期望 / Budget = 可接受 / Fail = 必须动手）

| 指标 | Target | Budget | Fail（触发优化） |
|---|---|---|---|
| 查询延迟 N=20 万（查询长 1–3） | P50 < 3 ms，P99 < 8 ms | P50 < 6 ms，P99 < 15 ms | P99 > 25 ms |
| 查询延迟 N=20 万（查询长 4–8） | P50 < 2 ms，P99 < 5 ms | P50 < 4 ms，P99 < 10 ms | P99 > 20 ms |
| 快照内存 N=20 万 | ≤ 30 MB | ≤ 40 MB | > 60 MB（触发 §3.1 优化候选） |
| 冷启动到「可查询」 | < 150 ms | < 300 ms | > 600 ms |
| 首次全量扫描 20 万条 | < 8 s（后台） | < 15 s | > 30 s |
| 增量更新（watcher 事件 → 可查询） | < 100 ms | < 300 ms | > 1 s |

**第三步：正确性指标——这些是硬门槛，不打折**

| 指标 | 要求 |
|---|---|
| 结果正确性 | 合成语料 golden 用例：子序列、多词、typo、中文、短路路径全部命中 |
| 细化缓存一致性 | 缓存命中路径与全量路径的**结果集逐条一致**（§4.5 最易出错处） |
| 种类白名单切换（DB → 重建快照，不扫盘） | < 50 ms（20 万条） |
| 工程目录剪枝 | 含 `node_modules` 的前端工程条目数下降 ≥ 95%，扫描耗时同比例下降（记录实测对比） |
| 查询语法正确性 | QueryParser golden 用例：`:doc` `ext:pdf` `in:box` `src:chrome` `-词` `size:>10mb` |
| 下载接管端到端 | 浏览器下载 100 次：0 次误拉未完成文件、0 次同名覆盖、100% 可撤销；完成后 ≤ 3 s 出现在 box 且 `:dl` 可搜到 |
| 去向追踪 | 同卷指纹命中率 ≥ 99%、跨卷签名命中、改名后移动仍命中、未监听目录正确落 `Unknown`；**误判 0** |
| box / 移动健壮性 | 拉取失败率 < 0.1%；对账用例（`intent` 残留 + 「待整理」幽灵条目）全部正确补完/回滚/转追踪 |

基准语料：程序化生成（不同深度、非 ASCII 占比 10%、长路径 5%），可重复。每项优化前后各跑一次并记录到 `docs/devlog/`，避免「凭感觉优化」。

## 10. 分阶段实施路线

> **总原则：架构一次设计完整，功能分阶段落地**——不要一开始就把 FileIndex / Watcher / Ingest / Tracking / USN / IM 源 / 归档规则全部实现。
> 下表括号里是早期编号（S1–S11），便于与治理文档对照。**Phase A 完成即是一个可用产品**（搜索），B 让搜索可控，C/D/E 才是"文件治理"。

### 10.0 与 GUIDE 项目阶段的关系，以及为什么是这个顺序

| 顺序 | 做什么 | 理由 |
|---|---|---|
| 1 | **Phase 3 收尾 → tag `v0.3.0`** | 剩余项很小且与文件子系统无关（热键自定义、开机启动、剪贴板相对时间、`Style.qml` 抽公共主题、真机走查、版本号 bump）。**大改之前先有一个已知良好、可回退的 tag**，是最主要的理由 |
| 2 | **A1 止血**（半天，独立 patch） | 修的是每天都在发生的体验问题（每按键写一次 SQLite、junction 递归重复索引、输入无防抖、IME 预编辑触发搜索），**不依赖任何架构改动**，先落地先受益 |
| 3 | **Phase A（A2–A7）** | 这是地基：门面 + COW 快照 + watcher + `ISearchProvider`。GUIDE Phase 4（插件系统）**自己要求"核心架构稳定后再做，否则接口会频繁变动"**，而 A7 的 provider 抽象正是那个稳定点 |
| 4 | **Phase B**（治理过滤） | 规模小、收益直接；顺手把 `DatabaseMigrator` 立起来（`cat_mask` 等字段就是第一个真实迁移用例） |
| 5 | **Phase C → D → E** | Box → 去向追踪 → 自动治理与多源，逐层加复杂度；**USN 与 IM 源放最后** |
| 6 | **GUIDE Phase 4**（插件 + 发布） | 此时 provider 接口已稳定，插件可以直接实现 `ISearchProvider`，不必改两遍 |

**为什么不选另外几种排法**：

| 排法 | 问题 |
|---|---|
| 先做插件系统（GUIDE Phase 4） | 插件接口要建在 `ISearchProvider` 上；先做就要在旧模型上定接口，A7 之后再改一遍——**GUIDE 自己已经写明这个风险** |
| 先做 Download Box（Phase C） | Box 依赖 watcher（A5）与索引的 `(size,mtime)` 反查（A3）——先做就得自制一套遍历/事件逻辑，随后被 A 阶段替换，等于写两遍 |
| 长期并行两条线（Phase 3 收尾 + 重构） | 学习型项目单线程更稳；而且收尾只有几天，串行成本远低于并行的上下文切换成本 |

**两条补充**：
- **发布/打包不必等到最后**：GUIDE Phase 4 的"安装包制作"与插件系统无耦合，建议在 v0.3.0 之后插一次 **1–2 天的打包 spike**（vcpkg 环境下 Qt 部署 + NSIS），把部署问题提前暴露，不影响主线。
- **GUIDE 3.5「性能优化（启动速度）」与本文 A2/A6 本质是同一件事**：现状 P0-4 就是启动慢的根因（索引在主线程同步构建、`engine.load()` 之前）。所以"先重构"并不与 Phase 3 收尾冲突——那一条本来就是 A2/A6 要做的内容。

## 11. 风险与取舍

| 风险 | 应对 |
|---|---|
| 长路径（> 260 字符） | 遍历用 `\\?\` 前缀；需 exe manifest 声明 `longPathAware` + 注册表项；本期至少保证不崩溃、不索引失败 |
| 权限拒绝目录（`Program Files` 子目录、其他用户目录） | 逐目录 `try` 式跳过并计数，日志 `debug` 级汇总，不中断扫描 |
| OneDrive/云占位文件（`FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS`） | 只读元数据不读内容即可，天然安全；但 mtime 可能变化频繁 → watcher 事件做 200 ms 合并去抖 |
| 网络盘 | 默认不纳入 roots；若用户配置了，关闭 watcher 只保留空闲重扫 |
| 快照重建期间的查询 | COW 保证旧快照继续可服务，切换是原子的，无需停查询 |
| 细化缓存正确性 | §4.5 的「缓存必须存全量命中」是最易出错点，须有专门用例；缓存命中路径与全量路径的结果集必须逐字节一致（基准里加断言） |
| 索引体积/内存超预期 | **不驱逐**：软预算只提示、硬上限停止索引并醒目告警（§3.3）；缩小规模靠 `roots` / 排除规则 / `kindFilter`，由用户决定 |
| 学习曲线（fzf DP / COW / Win32 变更通知） | 每步先在 `docs/learning/` 写笔记（项目已有此惯例），DP 部分先写朴素版 + 基准，再优化 |

## 12. 保持不变的部分（避免过度重构）

- `SearchResult` 结构与 `typeString()`、`toMap()` 协议。
- `FuzzyMatcher` 的**五级 tier 语义**（文档与注释已对外表达，作为 tier 层保留）。
- `AppBridge` 作为 QML 唯一门面的定位。
