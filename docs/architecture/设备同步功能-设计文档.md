# 设备同步功能 设计文档（软件工程导论实践）

> **实践目标**：让装有两台 Assistant 的电脑可以共享文件、各自编辑后自动合并。
> **本文字数定位**：需求规格 + 概要设计 + 详细设计 + 测试计划 + 分工与实施计划，一份文档覆盖软工导论实践的全部设计类交付物。
> **前置约束**：功能**集成进现有 Assistant**，复用其 QML 主面板、SQLite 约定、日志与构建体系。
> **明确不做**（见 §9 红线）：NAT 穿透、CRDT 实时协同、虚拟文件系统驱动。

---

## 1. 需求分析

### 1.1 问题背景

两台电脑之间的文件共享，现有做法各有明显缺陷：

| 做法 | 缺陷 |
|---|---|
| U 盘 / 微信传文件 | 手工、易漏、无法追踪"哪份是最新" |
| OneDrive / 坚果云同步盘 | 冲突时静默生成副本，用户不知道发生过什么；无法按需选择共享哪些目录 |
| Syncthing | 功能强，但配置面向技术人员，无统一入口，与已有工具链割裂 |

本功能的目标：**在 Assistant 内提供一个可感知、可控制、冲突可见的文件同步能力**。

### 1.2 用例图

```
                    ┌─────────────────────────────────────┐
                    │          设备同步子系统              │
                    │                                     │
   ┌──────┐         │  (UC1) 配对设备                      │
   │      │─────────┼─▶(UC2) 配置共享目录                  │
   │ 用户 │         │  (UC3) 执行同步                      │
   │      │─────────┼─▶(UC4) 查看同步状态                  │
   └──────┘         │  (UC5) 处理冲突                      │
                    │  (UC6) 查看冲突历史                  │
                    └─────────────────────────────────────┘
                              ▲              ▲
                              │              │
                     ┌────────┴───┐   ┌──────┴──────┐
                     │ 对端设备    │   │ 共享目录/网盘│
                     │ (Assistant) │   │ (传输媒介)   │
                     └────────────┘   └─────────────┘
```

### 1.3 用例描述（关键两个）

**UC3 执行同步**

| 项 | 内容 |
|---|---|
| 参与者 | 用户、对端设备 |
| 前置条件 | 已完成 UC1 配对；已完成 UC2 共享目录配置；传输通道可用 |
| 主流程 | 1. 用户在 SyncPage 点击「立即同步」<br>2. 系统选取可用传输通道（见 §3.3 降级策略）<br>3. 拉取对端文件清单<br>4. 对每个文件执行三方差集判定（§4.2）<br>5. 按判定结果执行上传/下载/更新基线<br>6. 刷新界面状态，写入同步日志 |
| 备选流程 | 3a. 对端清单拉取失败 → 报错并终止，不改动任何文件<br>4a. 判定为冲突 → 转入 UC5 |
| 后置条件 | 两端共享目录内容一致；冲突文件保留双方版本；`sync.db` 基线已更新 |

**UC5 处理冲突**

| 项 | 内容 |
|---|---|
| 前置条件 | 同步过程中检出 `SyncAction::Conflict` |
| 主流程 | 1. 保留本地版本原文件不动<br>2. 将对端版本下载为冲突副本，命名为 `<原名> (冲突副本 来自<设备名> <时间戳>)<扩展名>`<br>3. 向 `conflicts` 表插入记录<br>4. 在 SyncPage 冲突列表展示，提供「打开所在文件夹」 |
| 后置条件 | **双方版本都不丢失**；用户可自行判断保留哪份 |

### 1.4 功能需求

| 编号 | 需求 | 优先级 |
|---|---|---|
| FR1 | 两台设备可通过配对码建立信任关系，配对信息持久化 | 高 |
| FR2 | 用户可配置一个或多个共享目录（含增删改） | 高 |
| FR3 | 支持手动触发同步，并显示进度与结果 | 高 |
| FR4 | 新增、修改的文件在两台设备间保持一致 | 高 |
| FR5 | 两端对同一文件都做过修改时，必须生成冲突副本，**禁止静默覆盖** | 高 |
| FR6 | 冲突记录可在界面查看，含时间、路径、双方哈希 | 中 |
| FR7 | 支持定时自动同步（间隔可配置） | 中 |
| FR8 | 删除操作同步，但对端删除前先移入 `.sync/trash/`（可恢复） | 中 |
| FR9 | 同局域网时优先走直连通道，不可用时自动降级 | 中 |
| FR10 | 最小化到托盘后同步仍可进行 | 低 |

### 1.5 非功能需求

| 编号 | 需求 | 验收方式 |
|---|---|---|
| NFR1 | **跨网络可用**：同一局域网与异地两种场景都能完成同步 | 两种环境各演示一次 |
| NFR2 | **不丢数据**：任何情况下冲突双方的版本都必须留存 | 冲突场景检查磁盘上两份文件均存在 |
| NFR3 | **安全**：配对需人工确认；接收端拒绝一切越出共享根的路径 | `test_path_guard` 全绿 |
| NFR4 | **增量**：未修改的文件不重复传输 | 二次同步时统计传输字节数，未变文件为 0 |
| NFR5 | **可演示**：单台电脑开两个实例即可完整演示全流程 | 答辩现场演示 |
| NFR6 | **可测试**：核心判定逻辑为纯函数，可单元测试 | 覆盖率报告中算法模块 ≥ 80% |
| NFR7 | **可恢复**：同步过程被中断后，再次同步能正确收敛 | 中途杀进程后重启同步，无重复/无残留 |
| NFR8 | **不阻塞界面**：同步在后台线程执行，界面可正常操作 | 同步大目录时界面不卡顿 |

> NFR5 是本设计的一项硬约束：它决定了必须存在**不依赖真实网络的传输通道**（§3.3）。答辩现场没有第二台电脑、没有可用网络是常态。

## 3. 概要设计

### 3.1 分层架构

```
┌───────────────────────────────────────────────────────────────┐
│  表示层   resources/qml/SyncPage.qml                          │
│           主面板第五页：配对 / 共享目录 / 同步按钮 / 状态 / 冲突表│

├───────────────────────────────────────────────────────────────┤

│           ├── 通道选择与降级                                    │

│           └── 结果汇总与日志                                    │
│           core/sync/ConflictResolver   冲突判定（纯函数）      │
│           core/sync/PathGuard          路径安全校验（纯函数）  │
├───────────────────────────────────────────────────────────────┤

│           devices / sync_state / conflicts 三张表              │
├───────────────────────────────────────────────────────────────┤
│  传输层   core/sync/ITransport  ← 接口，运行时可替换            │
│           ├── core/sync/LanTransport      直连（QTcpSocket）   │
│           └── core/sync/FolderTransport   共享目录中转（文件系统）│
└───────────────────────────────────────────────────────────────┘
```

### 3.2 为什么把传输抽象成接口（本设计的核心决策）

因为**两种网络场景的技术代价差异极大**：

| 场景 | 若走直连需要解决 | 实际代价 |
|---|---|---|
| 同一局域网 | 设备发现、协议、传输 | 可控 |
| 异地（跨 NAT） | 上述全部 **+ 端口映射 / STUN / TURN / 中继服务器** | 不可控，且需要额外服务器成本与运维 |

而如果引入一个「共享目录」通道——把文件写进一个由 OneDrive / 坚果云 / Syncthing 负责异地传输的目录——异地场景就被外部工具消化了，**本系统零网络代码即可跨网工作**。

于是：

- `LanTransport`：`QTcpSocket` 直连，同一局域网下快，体现网络编程能力
- `FolderTransport`：以共享目录为中介，异地可用，且**单机双实例即可演示**

两者实现同一个 `ITransport` 接口，`SyncEngine` 只依赖接口，**依赖倒置**。互换实现不影响业务逻辑一行代码。

### 3.3 通道选择与降级策略

```
SyncEngine::sync()
   │
   ├─ 遍历已注册通道，按优先级排序：LanTransport(priority=0) → FolderTransport(priority=10)
   │
   ├─ 对每个通道调 probe()
   │     LanTransport::probe()    : 向对端 IP:PORT 发起连接，300ms 超时
   │     FolderTransport::probe() : 检查共享目录存在、可写、清单文件可读
   │
   ├─ 取第一个 probe() 成功的通道执行本次同步
   │
   └─ 全部失败 → 返回 SyncResult::NoChannelAvailable（界面提示"无可用通道"）
```

降级是**每次同步时重新判定**，不是启动时一次性决定——否则从公司回到家（换了网络）后不会自动切回直连。

### 3.4 线程模型

- `SyncEngine::sync()` 在 `QThread` 中执行，不阻塞 GUI（满足 NFR8）
- `LanTransport` 的 `QTcpSocket` 在使用线程内创建（Qt 要求 socket 与所属线程的事件循环一致）
- `SyncDatabase` 连接在使用线程内创建，**遵守"每个 DB 独立连接名"的项目约定**（连接名 `sync_worker`，避免与主线程 `sync` 冲突）
- 进度通过信号跨线程投递，`SyncBridge` 转发给 QML

## 4. 详细设计

### 4.1 核心接口契约（冻结）

本节三份接口同属**冻结契约**（见 §5.1），是四名成员并行开发的边界。任何改动必须全员同意并同步更新本文档——接口一旦漂移，并行开发立即退化为互相等待。

#### 4.1.1 传输层 `ITransport`

```cpp
// include/core/sync/ITransport.h
#pragma once

#include <QList>
#include <QString>

/// 对端一个文件的元信息。hash 为空表示对端未提供哈希。
struct RemoteFileInfo
{
    QString relPath;    // 相对共享根的路径，始终使用 '/' 分隔
    qint64  size  = -1; // -1 表示文件不存在（删除标记）
    qint64  mtime = 0;  // Unix 秒
    QString hash;       // SHA-256 十六进制小写；空 = 未提供
};

/// 传输层抽象。SyncEngine 只依赖本接口，不依赖任何具体实现。
///
/// 实现必须满足：
///   1. 所有 relPath 使用 '/' 分隔，且已经过 PathGuard 校验后才可写入本地
///   2. fetch/push 失败时返回 false，且不得留下不完整的落盘文件
///   3. 不抛出异常
class ITransport
{
public:
    virtual ~ITransport() = default;

    /// 通道名，用于日志与界面显示。
    virtual QString name() const = 0;

    /// 优先级，数字小的先尝试。
    virtual int priority() const = 0;

    /// 健康探测：本通道当前是否可用。必须快速返回（建议 < 1s），不得阻塞。
    virtual bool probe() = 0;

    /// 拉取对端完整文件清单。
    virtual QList<RemoteFileInfo> listRemote() = 0;

    /// 取回对端文件到 destPath（destPath 为本地绝对路径，由调用方保证安全）。
    virtual bool fetch(const QString &relPath, const QString &destPath) = 0;

    /// 把本地文件推送到对端 relPath 位置。
    virtual bool push(const QString &localPath, const QString &relPath) = 0;

    /// 请求对端移除 relPath（对端实现应移入回收目录而不是直接删除）。
    virtual bool removeRemote(const QString &relPath) = 0;
};
```

#### 4.1.2 引擎层 `SyncEngine`

```cpp
// include/core/sync/SyncEngine.h
#pragma once

#include <QObject>
#include <QList>
#include <QString>

#include <memory>

#include "core/sync/ITransport.h"

class SyncDatabase;

namespace Sync {

/// 一次同步的汇总结果。
struct SyncResult
{
    enum Status {
        Ok,                   // 全部处理完成
        NoChannelAvailable,   // 所有通道 probe() 均失败
        RemoteUnreachable,    // 通道可用但对端清单拉取失败
        Aborted               // 用户取消或遇到致命错误
    };

    Status  status     = Ok;
    int     uploaded   = 0;
    int     downloaded = 0;
    int     conflicts  = 0;
    int     deleted    = 0;
    int     failed     = 0;   // 单个文件失败计数，不影响整体完成
    qint64  bytesMoved = 0;
    QString message;          // 失败原因，供界面显示（status != Ok 时非空）
};

/// 同步引擎。所有磁盘与网络 I/O 都在本类内完成。
/// 不依赖任何 QML 类型，可脱离界面单独测试。
class SyncEngine : public QObject
{
    Q_OBJECT
public:
    explicit SyncEngine(QObject *parent = nullptr);

    void setDatabase(SyncDatabase *db);        // 不接管所有权
    void setLocalRoot(const QString &root);    // 本地共享根，绝对路径
    void setDeviceName(const QString &name);   // 用于冲突副本命名

    /// 传入全部候选通道。sync() 内部按 priority() 升序依次 probe()，
    /// 取第一个可用者执行本次同步（见 §3.3）。
    void setTransports(const QList<std::shared_ptr<ITransport>> &list);

    /// 执行一次完整同步。**阻塞调用**，应在工作线程中执行（见 §3.4）。
    SyncResult sync();

signals:
    /// percent: 0-100；currentFile: 正在处理的相对路径
    void progress(int percent, const QString &currentFile);
    /// action: "upload" | "download" | "conflict" | "delete" | "skip"
    void fileHandled(const QString &relPath, const QString &action);

private:
    SyncDatabase *m_db = nullptr;
    QString       m_localRoot;
    QString       m_deviceName;
    QList<std::shared_ptr<ITransport>> m_transports;
};

} // namespace Sync
```

### 4.2 差量判定：三方差集（核心算法）

对每个文件，比较三份状态：

- **L**（Local）：本地磁盘现状
- **S**（Synced baseline）：上次同步完成时的状态，存在 `sync_state` 表
- **R**（Remote）：对端清单中的状态

```cpp
// include/core/sync/ConflictResolver.h
#pragma once

#include <QString>

namespace Sync {

/// 一个文件在某一侧的状态。
struct FileState
{
    qint64  size  = -1;   // -1 = 文件不存在
    qint64  mtime = 0;    // Unix 秒
    QString hash;         // SHA-256；空 = 未计算

    bool exists() const { return size >= 0; }
};

enum class SyncAction
{
    None,            // 无需动作
    Upload,          // 本地改动 → 上传
    Download,        // 对端改动 → 下载
    UpdateBaseline,  // 两端改成同一内容 → 只更新基线
    Conflict,        // 两端改成不同内容 → 生成冲突副本
    DeleteLocal,     // 对端删除且本地未改 → 本地移入回收目录
    DeleteRemote     // 本地删除且对端未改 → 请求对端移入回收目录
};

/// 判定两个状态是否"相同"。
///
/// 规则：双方都有 hash 时只比 hash；任一方缺 hash 时退化为 (size, mtime) 比较。
/// 不存在状态（size < 0）与任何存在状态都不相同。
bool sameState(const FileState &a, const FileState &b);

/// 三方差集判定。纯函数，无副作用，无 I/O —— 便于单元测试。
SyncAction decide(const FileState &L, const FileState &S, const FileState &R);

/// 生成冲突副本的文件名（不含目录）。
/// 例：报告.docx + 设备名"笔记本" + 时间 2026-09-24 15:30:00
///     → "报告 (冲突副本 来自笔记本 20260924-153000).docx"
QString makeConflictName(const QString &originalName,
                         const QString &peerDeviceName,
                         qint64 detectedAtEpoch);

} // namespace Sync
```

```cpp
// src/core/sync/ConflictResolver.cpp
#include "core/sync/ConflictResolver.h"

#include <QDateTime>
#include <QFileInfo>
#include <QRegularExpression>

namespace Sync {

bool sameState(const FileState &a, const FileState &b)
{
    if (a.exists() != b.exists())
        return false;
    if (!a.exists())              // 两边都不存在
        return true;

    // 优先比哈希：mtime 会被复制/同步工具改写，不可靠
    if (!a.hash.isEmpty() && !b.hash.isEmpty())
        return a.hash.compare(b.hash, Qt::CaseInsensitive) == 0;

    return a.size == b.size && a.mtime == b.mtime;
}

SyncAction decide(const FileState &L, const FileState &S, const FileState &R)
{
    const bool localChanged  = !sameState(L, S);
    const bool remoteChanged = !sameState(R, S);

    // 情况 1：双方都没动
    if (!localChanged && !remoteChanged)
        return SyncAction::None;

    // 情况 2：只有本地动了
    if (localChanged && !remoteChanged) {
        if (!L.exists() && S.exists())
            return SyncAction::DeleteRemote;   // 本地删除
        if (L.exists() && !S.exists())
            return SyncAction::Upload;          // 本地新增
        return SyncAction::Upload;              // 本地修改
    }

    // 情况 3：只有对端动了
    if (!localChanged && remoteChanged) {
        if (!R.exists() && S.exists())
            return SyncAction::DeleteLocal;     // 对端删除
        if (R.exists() && !S.exists())
            return SyncAction::Download;        // 对端新增
        return SyncAction::Download;            // 对端修改
    }

    // 情况 4：双方都动了 —— 内容是否恰好一致？
    if (sameState(L, R))
        return SyncAction::UpdateBaseline;

    // 情况 5：真冲突
    return SyncAction::Conflict;
}

QString makeConflictName(const QString &originalName,
                         const QString &peerDeviceName,
                         qint64 detectedAtEpoch)
{
    const QFileInfo fi(originalName);
    const QString base = fi.completeBaseName();
    const QString suffix = fi.suffix();

    const QString stamp =
        QDateTime::fromSecsSinceEpoch(detectedAtEpoch).toString("yyyyMMdd-HHmmss");

    // 设备名可能含非法文件名字符，做最小净化
    QString peer = peerDeviceName;
    peer.replace(QRegularExpression(R"([\\/:*?"<>|])"), QStringLiteral("_"));

    QString name = QStringLiteral("%1 (冲突副本 来自%2 %3)").arg(base, peer, stamp);
    if (!suffix.isEmpty())
        name += QLatin1Char('.') + suffix;
    return name;
}

} // namespace Sync
```

### 4.3 路径安全校验

这是文件同步最经典的漏洞面：**恶意或损坏的对端清单里一个 `../../Windows/System32/x.dll` 就能写到共享目录之外**。

```cpp
// include/core/sync/PathGuard.h
#pragma once

#include <QString>

namespace Sync::PathGuard {

/// 路径是否安全（可作为共享根之下的相对路径使用）。
///
/// 拒绝：空路径、绝对路径、盘符形式、".."段、Windows 保留设备名、
///       NTFS 备用数据流（冒号）、段名含控制字符、超长段名。
bool isSafeRelativePath(const QString &relPath);

/// 在 root 之下解析 relPath。
/// - relPath 不安全 → 返回空字符串
/// - 解析后最终路径（含符号链接/junction 解引用）越出 root → 返回空字符串
/// - 正常 → 返回规范化后的绝对路径
QString resolveUnder(const QString &root, const QString &relPath);

} // namespace Sync::PathGuard
```

```cpp
// src/core/sync/PathGuard.cpp
#include "core/sync/PathGuard.h"

#include <QDir>
#include <QFileInfo>
#include <QRegularExpression>
#include <QSet>

namespace Sync::PathGuard {

namespace {

/// Windows 保留设备名（不区分大小写，且带扩展名也算，如 "CON.txt"）。
const QSet<QString> &reservedNames()
{
    static const QSet<QString> s = {
        QStringLiteral("CON"),  QStringLiteral("PRN"),  QStringLiteral("AUX"),
        QStringLiteral("NUL"),  QStringLiteral("COM1"), QStringLiteral("COM2"),
        QStringLiteral("COM3"), QStringLiteral("COM4"), QStringLiteral("COM5"),
        QStringLiteral("COM6"), QStringLiteral("COM7"), QStringLiteral("COM8"),
        QStringLiteral("COM9"), QStringLiteral("LPT1"), QStringLiteral("LPT2"),
        QStringLiteral("LPT3"), QStringLiteral("LPT4"), QStringLiteral("LPT5"),
        QStringLiteral("LPT6"), QStringLiteral("LPT7"), QStringLiteral("LPT8"),
        QStringLiteral("LPT9")
    };
    return s;
}

} // namespace

bool isSafeRelativePath(const QString &relPath)
{
    if (relPath.isEmpty())
        return false;

    // 绝对路径与盘符（"C:foo" 这种驱动器相对路径同样危险）
    if (QDir::isAbsolutePath(relPath))
        return false;
    if (relPath.length() >= 2 && relPath.at(1) == QLatin1Char(':'))
        return false;

    // UNC 形式
    if (relPath.startsWith(QStringLiteral("\\\\")) || relPath.startsWith(QStringLiteral("//")))
        return false;

    // 控制字符（含换行、制表）—— 可用于欺骗日志与界面
    for (const QChar &c : relPath) {
        if (c.unicode() < 0x20)
            return false;
    }

    // NTFS 备用数据流：文件名中的冒号
    if (relPath.contains(QLatin1Char(':')))
        return false;

    const QString normalized = QString(relPath).replace(QLatin1Char('\\'), QLatin1Char('/'));
    const QStringList segments = normalized.split(QLatin1Char('/'), Qt::SkipEmptyParts);

    if (segments.isEmpty())
        return false;

    for (const QString &seg : segments) {
        if (seg == QStringLiteral(".") || seg == QStringLiteral(".."))
            return false;
        if (seg.endsWith(QLatin1Char('.')) || seg.endsWith(QLatin1Char(' ')))
            return false;   // Windows 会静默去掉尾部的点与空格，可用于绕过检查
        if (seg.length() > 255)
            return false;

        const QString stem = seg.section(QLatin1Char('.'), 0, 0).toUpper();
        if (reservedNames().contains(stem))
            return false;
    }

    return true;
}

QString resolveUnder(const QString &root, const QString &relPath)
{
    if (!isSafeRelativePath(relPath))
        return QString();

    const QString normalized = QString(relPath).replace(QLatin1Char('\\'), QLatin1Char('/'));
    const QString rootAbs = QDir(root).absolutePath();
    const QString joined  = QDir(rootAbs).absoluteFilePath(normalized);

    // 关键一步：解引用符号链接与 junction 后再复核前缀。
    // 只做字符串前缀比较是不够的 —— 共享目录里可能存在指向外部目录的 junction。
    // 项目已有同类踩坑记录：docs/troubleshooting/qt-nosymlinks-挡不住junction.md
    const QFileInfo fi(joined);
    const QString canonicalParent = fi.dir().canonicalPath();
    if (canonicalParent.isEmpty())
        return QString();       // 父目录不存在或无法解析

    const QString canonicalRoot = QFileInfo(rootAbs).canonicalFilePath();
    if (canonicalRoot.isEmpty())
        return QString();

    const QString canonicalFull = QDir(canonicalParent).absoluteFilePath(fi.fileName());

    const QString rootWithSep = canonicalRoot.endsWith(QLatin1Char('/'))
                                    ? canonicalRoot
                                    : canonicalRoot + QLatin1Char('/');
    if (canonicalFull != canonicalRoot && !canonicalFull.startsWith(rootWithSep, Qt::CaseInsensitive))
        return QString();

    return canonicalFull;
}

} // namespace Sync::PathGuard
```

### 4.4 直连通道协议

固定帧头 + 变长载荷，全部小端序。

```
 0        4      6      8              12                    12+len
 +--------+------+------+---------------+----------------------+
 | magic  | ver  | type | payloadLen    | payload              |
 | "ASYN" | 0x01 | u16  | u32           | JSON 或 裸字节        |
 +--------+------+------+---------------+----------------------+
```

| type | 名称 | 方向 | 载荷 |
|---|---|---|---|
| 0x01 | Hello | C→S | `{deviceId, deviceName, pairCodeHmac}` |
| 0x02 | HelloAck | S→C | `{accepted: bool, reason}` |
| 0x10 | ListRequest | C→S | 空 |
| 0x11 | ListResponse | S→C | `[RemoteFileInfo…]` 的 JSON 数组 |
| 0x20 | FileRequest | C→S | `{relPath, offset}` |
| 0x21 | FileChunk | S→C | 裸字节（≤ 64 KiB） |
| 0x22 | FileEnd | S→C | `{relPath, hash}` |
| 0x30 | FilePush | C→S | `{relPath, size, hash}` 后接裸字节 |
| 0x31 | PushAck | S→C | `{ok: bool}` |
| 0x40 | DeleteRequest | C→S | `{relPath}` |
| 0x41 | DeleteAck | S→C | `{ok: bool}` |
| 0xFF | Error | 双向 | `{code, message}` |

**要点**：

- `FileRequest` 携带 `offset`，因此**天然支持断点续传**：连接中断后重发带 offset 的请求即可
- 分块 64 KiB：足够大以减少往返，足够小以保持进度反馈粒度
- `Hello` 的 `pairCodeHmac` = HMAC-SHA256(配对码, deviceId)，避免明文传配对码；**配对码由首次配对时双方人工确认**（NFR3）
- 接收落盘策略：先写 `relPath + ".part"`，`FileEnd` 校验哈希通过后再 `rename` 为正式文件。**哈希不符则丢弃 `.part`**，保证不留下损坏文件

### 4.5 共享目录通道（FolderTransport）

预先约定共享目录的布局：

```
<共享目录>/
├── .sync/
│   ├── manifest-<设备A的ID>.json   # 设备 A 发布的文件清单（含 size/mtime/hash）
│   ├── manifest-<设备B的ID>.json   # 设备 B 发布的文件清单
│   ├── device.json                 # 本设备 ID 与名称
│   └── trash/                      # 对端要求删除的文件移到这里，而不是真删
└── (用户共享的实际文件…)
```

> 清单文件**按设备分文件**（`manifest-<deviceId>.json`）而不是共用一个 `manifest.json`：两台设备各自写各自的清单，避免互相覆盖。这是 §9.2 风险表中"两实例同时写共享目录"的缓解措施。

由于共享目录本身由网盘（OneDrive / 坚果云 / Syncthing）负责异地传输：

- `probe()`：检查目录存在、可写、对端清单文件可解析
- `listRemote()`：读 `.sync/manifest-<对端设备ID>.json`
- `fetch()`：从共享目录复制到本地共享根
- `push()`：复制到共享目录，然后原子更新本设备的清单文件
- `removeRemote()`：在共享目录里把文件移入 `.sync/trash/`

**注意**：清单文件的写入必须原子（写临时文件后 `rename`），否则网盘可能同步到半个文件。这是本通道最容易出错的地方，需在测试中专门覆盖。

**`tests/test_conflict_resolver.cpp`** —— 覆盖 §4.2 判定表全部七行与边界。本文件可直接编译运行：

```cpp
#include <QtTest>
#include <QRegularExpression>

#include "core/sync/ConflictResolver.h"

using namespace Sync;

namespace {

FileState present(qint64 size, qint64 mtime, const QString &hash)
{
    FileState s;
    s.size  = size;
    s.mtime = mtime;
    s.hash  = hash;
    return s;
}

/// 文件不存在：size 保持默认的 -1
FileState absent()
{
    return FileState{};
}

} // namespace

class TestConflictResolver : public QObject
{
    Q_OBJECT

private slots:

    // ---- 判定表第 1 行：双方都没动 ----
    void cr01_noChange()
    {
        const FileState a = present(100, 1000, "aaaa");
        QCOMPARE(decide(a, a, a), SyncAction::None);
    }

    // ---- 判定表第 1 行的边界：三方都不存在 ----
    void cr02_allAbsent()
    {
        QCOMPARE(decide(absent(), absent(), absent()), SyncAction::None);
    }

    // ---- 判定表第 3 行：本地修改，对端未动 ----
    void cr03_localModified()
    {
        const FileState S = present(100, 1000, "aaaa");
        const FileState L = present(120, 2000, "bbbb");
        QCOMPARE(decide(L, S, S), SyncAction::Upload);
    }

    // ---- 判定表第 2 行：本地删除，对端未动 ----
    void cr04_localDeleted()
    {
        const FileState S = present(100, 1000, "aaaa");
        QCOMPARE(decide(absent(), S, S), SyncAction::DeleteRemote);
    }

    // ---- 本地新增（基线不存在） ----
    void cr05_localAdded()
    {
        const FileState L = present(100, 1000, "aaaa");
        QCOMPARE(decide(L, absent(), absent()), SyncAction::Upload);
    }

    // ---- 判定表第 5 行：对端修改，本地未动 ----
    void cr06_remoteModified()
    {
        const FileState S = present(100, 1000, "aaaa");
        const FileState R = present(120, 2000, "bbbb");
        QCOMPARE(decide(S, S, R), SyncAction::Download);
    }

    // ---- 判定表第 4 行：对端删除，本地未动 ----
    void cr07_remoteDeleted()
    {
        const FileState S = present(100, 1000, "aaaa");
        QCOMPARE(decide(S, S, absent()), SyncAction::DeleteLocal);
    }

    // ---- 对端新增（基线不存在） ----
    void cr08_remoteAdded()
    {
        const FileState R = present(100, 1000, "aaaa");
        QCOMPARE(decide(absent(), absent(), R), SyncAction::Download);
    }

    // ---- 判定表第 6 行：双方都改但结果相同（hash 相同、mtime 不同）----
    void cr09_bothChangedToSame()
    {
        const FileState S = present(100, 1000, "aaaa");
        const FileState L = present(120, 2000, "cccc");
        const FileState R = present(120, 3000, "cccc");   // mtime 不同，hash 相同
        QCOMPARE(decide(L, S, R), SyncAction::UpdateBaseline);
    }

    // ---- 判定表第 7 行：真冲突 ----
    void cr10_realConflict()
    {
        const FileState S = present(100, 1000, "aaaa");
        const FileState L = present(120, 2000, "bbbb");
        const FileState R = present(130, 3000, "cccc");
        QCOMPARE(decide(L, S, R), SyncAction::Conflict);
    }

    // ---- 边界：hash 为空时退化为 (size, mtime) 比较 ----
    void cr11_noHashFallsBackToSizeMtime()
    {
        const FileState S = present(100, 1000, QString());
        const FileState L = present(100, 2000, QString());   // size 同、mtime 不同
        QCOMPARE(decide(L, S, S), SyncAction::Upload);
    }

    // ---- 边界：本地删除 + 对端修改 → 冲突，不允许静默覆盖 ----
    void cr12_deleteVsModify()
    {
        const FileState S = present(100, 1000, "aaaa");
        const FileState R = present(120, 2000, "bbbb");
        QCOMPARE(decide(absent(), S, R), SyncAction::Conflict);
    }

    // ---- 边界：hash 比较不区分大小写 ----
    void cr13_hashCaseInsensitive()
    {
        const FileState S = present(100, 1000, "AABB");
        const FileState L = present(100, 1000, "aabb");
        QCOMPARE(decide(L, S, S), SyncAction::None);
    }

    // ---- 边界：size 相同、mtime 相同、hash 不同 → 仍算改动 ----
    void cr14_sameSizeSameMtimeDifferentHash()
    {
        const FileState S = present(100, 1000, "aaaa");
        const FileState L = present(100, 1000, "bbbb");
        QCOMPARE(decide(L, S, S), SyncAction::Upload);
    }

    // ---- 冲突副本命名：结构正确 ----
    // 实现用**本地时区**格式化时间戳，所以这里只断言结构，不断言具体时间字符串，
    // 否则测试结果会随运行机器的时区变化。
    void cr15_conflictNameFormat()
    {
        const QString prefix = QStringLiteral("报告 (冲突副本 来自我的笔记本 ");
        const QString name = makeConflictName(QStringLiteral("报告.docx"),
                                              QStringLiteral("我的笔记本"),
                                              1758701400);
        QVERIFY(name.startsWith(prefix));
        QVERIFY(name.endsWith(QStringLiteral(").docx")));

        const QString stamp = name.mid(prefix.length());
        QVERIFY2(
            QRegularExpression(QStringLiteral(R"(^\d{8}-\d{6}\)\.docx$)")).match(stamp).hasMatch(),
            qPrintable(stamp));
    }

    // ---- 冲突副本命名：设备名含非法字符时被净化 ----
    void cr16_conflictNameSanitizesPeer()
    {
        const QString name = makeConflictName(QStringLiteral("a.txt"),
                                              QStringLiteral("bad/name:x"),
                                              1758701400);
        QVERIFY(!name.contains(QLatin1Char('/')));
        QVERIFY(!name.contains(QLatin1Char(':')));
    }
};
```

## 8. 与现有项目路线的关系

Assistant 本体的 **v0.4 文件子系统（A1–A8）** 与本功能是两条独立的线：

| 项 | 关系 |
|---|---|
| 与 A2（`FileSnapshot` COW 快照） | **无强依赖**。快照是"索引内存表示"，同步用的是 SQLite 基线，两者目标不同。将来若要复用，属优化而非必需 |
| 与 A5（`FileWatcher` / `ReadDirectoryChangesW`） | **有增强关系**。A5 完成后，同步可从"手动/定时"升级为"变更即时触发"，但**本设计的默认定时方案不依赖它** |
| 与 `FileSearcher` 的硬编码搜索根 | **必须解耦**。`FileSearcher.cpp:96-103` 写死了 6 个标准目录，同步模块**自己维护共享目录清单**，不改动那个待重构的模块 |
| 与 `AppBridge` | **无耦合**。同步不进入搜索框的 Provider 体系，是主面板的一个独立页面 |

**结论**：本功能是自包含的，不会因 A2–A8 未完成而无法交付。这对课程项目的进度可控性至关重要。

## 9. 风险与红线

### 9.1 红线（任一被突破即应重新评估范围）

1. **不做 NAT 穿透**。异地场景一律走 `FolderTransport`。STUN/TURN/中继服务器会吃掉整个学期。
2. **不做 CRDT 实时协同**。本设计是文件级同步 + 冲突副本，用户需自行合并冲突副本。若答辩要求"实时看到对方编辑"，只能在 Assistant 自有笔记上另立子项目，不能塞进本设计。
3. **不做文件系统过滤驱动**。无法接管 Word 等外部程序的文件读写。

### 9.2 技术风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 网盘同步延迟导致读到过期的对端清单 | 判定基于过期信息，可能误判 | 清单内带 `generatedAt` 时间戳，超过阈值提示"对端信息可能过期"；原子写清单 |
| 两实例同时写共享目录 | 清单互相覆盖 | 清单文件名带设备 ID（`manifest-<deviceId>.json`）；写入用原子 rename |
| 大文件（>1GB）传输中断 | 需重传全部 | 分块 + offset 断点续传（§4.4） |
| 文件正在被其他程序占用 | 读写失败 | 逐文件捕获失败并计数，不中断整体同步 |
| 路径大小写差异（Windows 不敏感、清单可能来自其他来源） | 同一文件被判为两个 | 入库前统一 `relPath` 为小写归一化形式 |
| 时间戳精度（FAT 与 NTFS 不同） | mtime 比较误判 | **优先比 hash**，mtime 仅在无 hash 时兜底（§4.2 已如此设计） |

### 9.3 管理风险

| 风险 | 缓解 |
|---|---|
| 4 人接口不一致导致集成失败 | W1–W2 冻结契约；集成在 W6 而非最后一周 |
| 关键技术路径（SyncEngine）延期 | B 的任务优先级最高；A 的断点续传可降级 |
| 答辩现场演示失败 | `FolderTransport` 单机演示 + 录制备用视频 |
| 组员贡献不均衡 | 按 §5.2 模块划分落实责任人，每人交付物可独立验证（有对应测试） |
| 需求蔓延（"再加个实时协同吧"） | 本文 §9.1 红线为范围基准，变更需全员同意并更新文档 |

## 10. 附录

### 10.1 术语

| 术语 | 含义 |
|---|---|
| L / S / R | 本地状态 / 上次同步基线 / 对端状态 |
| 三方差集 | 由 L、S、R 三者比较推出同步动作的方法 |
| 冲突副本 | 双方都改过同一文件时，保留下来的第二份文件 |
| 通道（Transport） | 完成文件搬运的具体方式：直连或共享目录 |
| 基线（Baseline） | 上次同步完成后记录的文件状态，`sync_state` 表 |

### 10.2 状态机（单文件生命周期）

```
        首次出现
           │
           ▼
      ┌─────────┐   同步成功    ┌──────────────┐
      │ 未同步   │─────────────▶│ 与基线一致    │
      └─────────┘              └──────┬───────┘
                                      │
                     ┌────────────────┼────────────────┐
                     │本地改           │对端改           │双方都改
                     ▼                ▼                ▼
              ┌───────────┐   ┌───────────┐   ┌──────────────┐
              │ 待上传     │   │ 待下载     │   │ 冲突          │
```
