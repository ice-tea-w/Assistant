# 插件接口对外开放 · 可行性分析

> 日期：2026-11-04
> 问题：把「插件市场」做成一个**能暴露给别人用**的接口，并配一份 README。
> 配套产物：`docs/plugins/README.md`（面向插件开发者的接口文档，已写）
> 关联基线：`插件市场-模块框架.md`（§4.5 `PluginHost` 收敛边界）、`四分支整合方案.md`（§2.1 三处裁剪）、`四模块完整架构.md`（契约 C1–C4）

---

## 0. 结论先行

| 候选"接口" | 谁的接口 | 可行性 | 结论 |
|---|---|---|---|
| **A. 插件 SPI**（插件作者 ↔ 宿主） | 第三方开发者 | **高** | **v1 就做**。机制已跑通，缺的是版本号、契约冻结和文档——正是现在做的 |
| **B. 市场协议**（索引/包 ↔ 宿主） | 索引托管方 / 发布者 | **高** | **v1 就做**。`index.json` + zip + sha256 已实现，缺的是把"这是稳定协议"说清楚 + 一个真实托管点 |
| **C. 进程外 API**（其他程序 ↔ 市场） | 其他应用 | **中低** | **v1 不做**。形态能想到，收益不清楚，风险很大（见 §6） |
| **D. C++ 头文件库**（其他 C++ 工程复用） | 其他项目 | **低** | 不做。会把 ABI 绑死，和 D1 决策冲突 |

**一句话**：这份"接口"应该被定义成**插件 SPI + 市场协议**，不是"给别的程序调用的 API"。前者几乎已经做完了，后者会把整个信任模型翻过来。

**阻塞项只有 6 个**（§4），合计约 **6–9 人日**能把 A 变成一个敢对外承诺的接口；B 只差一个静态托管点。

## 1. 先分清：现在代码里有三处"外面"

当前实现里已经存在三层边界，混在一起谈会得出错误结论：

| 层 | 谁在用 | 现在叫什么 | 稳定性 |
|---|---|---|---|
| **插件 SPI** | 第三方插件作者 | `plugin.json` + context property **`host`**（`PluginHost`） | 机制完整，**没有版本号** |
| **QML 内部桥** | 宿主自己的 QML 页面 | context property `plugins`（`PluginBridge`）+ `pluginApi.acquirePage()` | 内部，随时可改 |
| **C++ 门面** | 宿主 `main.cpp` | `PluginManager` | 内部，随时可改 |

"暴露给别人使用"的**只能是第一层**：`PluginBridge` 和 `PluginManager` 是宿主的私事，插件不该看见，其他程序更不该。

好消息是：`PluginHost` 的设计（`插件市场-模块框架.md` §4.5）本来就是按"未来可替换成进程外协议"来收敛的——6 个只读属性 + 5 个方法，没有一个是内部对象。**这层天生适合当公开接口。**

## 2. 现状盘点

### 2.1 已具备（可以直接写进文档当承诺）

| 能力 | 位置 | 说明 |
|---|---|---|
| 清单严格校验 | `src/core/plugin/PluginManifest.cpp` | id 正则、SemVer、路径逃逸、重复 id、runtime 白名单，全部硬校验 |
| 版本区间 | `SemVer.cpp` | `>=`/`<`/`^`/`~`/`x`/`\|\|` 子集，拒绝 `*` 与 `latest` |
| 插件 API 面收敛 | `PluginHost.h/.cpp` | 6 属性 5 方法；`openPath` 白名单（https/http/mailto + data 目录） |
| 页面贡献 + 懒加载 + 缓存 | `PluginLoader.cpp` | 同一 context，`host` 可用；停用即销毁 |
| 安装管线 | `PluginInstaller.cpp` | zip-slip 防护、sha256、版本一致性、失败回滚 |
| 状态原子写 | `PluginRegistry.cpp` | `QSaveFile` 整文件替换，写失败回滚内存 |
| 错误码体系 | `PluginInstaller/Manager` | 14 个稳定 code（README §10 已列） |
| 装载失败不崩 | `PluginLoader.cpp` | QML 编译/实例化失败 → 记 `problem`，继续加载下一个 |
| 测试 | `tests/plugin_core_tests.cpp` | **625 项检查 0 失败**（SemVer / Manifest / Registry） |

### 2.2 半成品（写进文档会变成假承诺）

| 项 | 现状 | 风险 |
|---|---|---|
| `permissions` | 只解析 + 展示，**没有任何执行拦截** | 若文档暗示"声明了才给你网络"，就是虚假安全 |
| `contributes.commands` | 解析、保存、**无消费方** | 作者按文档写完发现搜索框没反应 |
| `contributes.searchProviders` | 同上，且缺 `ISearchProvider` | 同上 |
| `contributes.settings` | 解析，无 UI 入口 | 同上 |
| 市场索引 | 默认 **seed-only**（编译进程序的示例数据） | "市场"目前不能真装 |
| 安装确认框 | **没有信任提示文案** | `四分支整合方案.md` §2.1 明确要求补 |

> 处理方式已写进 README：**把"未启用"标成未启用**（README §6），而不是删掉字段或含糊其辞。接口文档的第一职责是准确，不是好看。

### 2.3 缺失（不补就无法对外承诺）

1. 没有 **API 版本号**：插件只能靠 `manifestVersion` 猜宿主能力；
2. 没有**契约头文件**：`include/contract/` 不存在（`四分支整合方案.md` §5 也点了这条）；
3. 没有**兼容性测试样本**：没有一个"用到全部 API 的插件"当金丝雀；
4. 没有**脚手架 / 打包工具**：作者要手搓 zip 和 sha256；
5. 没有**示例仓库**：唯一示例在用户 `%LOCALAPPDATA%` 里，不在版本库里；
6. 没有**弃用流程**：删字段/改语义时怎么通知作者，无规定。

## 3. 对外承诺什么、不承诺什么

这是整份分析的**核心判断**。接口的价值不在"给了多少能力"，在"承诺了能不能守住"。

### 3.1 敢承诺（v1）

- `plugin.json` 的字段语义（`manifestVersion = 1`）
- `host` 的 6 个属性 + 5 个方法**只增不改**；删改语义必须升 `manifestVersion`
- 页面贡献机制（装载/懒加载/停用销毁）
- 错误码的**分类含义**（具体文案可能变）
- 安装管线对 zip 的检查项（sha256、zip-slip、版本一致）

### 3.2 不敢承诺（v1，必须写进文档）

| 不能承诺 | 为什么 |
|---|---|
| 插件不会崩 / 不会拖垮宿主 | 进程内、无沙箱。QML 死循环 = UI 卡死，JS 崩溃 = 进程没了 |
| `permissions` 会被强制执行 | 现在只是声明。**要说"仅用于展示"** |
| 插件间可以互相依赖 | 没有依赖解析，也没有计划 |
| 热更新 | 必须重启（QML 组件缓存 + 已实例化对象） |
| 跨 Qt 大版本稳定 | 插件跑在宿主的 QML 引擎里，宿主升级 Qt 可能导致行为差异 |
| 插件能改宿主内置界面 | 只能**新增**页面/命令/provider，不能改内置页 |
| 签名/来源可信 | 只有 sha256（防篡改，不防冒充） |

### 3.3 一个容易忽略的点：QML 本身就是接口的一部分

插件作者写的不是 C++，是 QML。这意味着接口的稳定性**同时受 Qt 约束**：

- 插件里 `import QtQuick.Layouts` 能用，是因为宿主引擎加载了它；
- 宿主升级 Qt6 次版本时，个别控件行为可能变化；
- `Style` 单例拿不到（qrc vs file:// 的 import 路径差异）——这已经被迫变成"插件自己配色"的约定。

**可行性结论**：这层可以做，但要接受"插件的视觉一致性靠约定，不靠强制"。README 里给了宿主色板（§5.4）就是这个妥协的产物。

## 4. 阻塞项与最小解法

按"是否阻塞对外承诺"排序。工作量是人日，含自测。

| # | 问题 | 为什么阻塞 | 最小解法 | 估时 |
|---|---|---|---|---|
| **G1** ~~没有 API 版本号~~ ✅ 已实现 | 作者无法判断"宿主支持我要的东西吗"；也无从表达弃用 | `PluginHost` 加 `Q_PROPERTY(int apiVersion CONSTANT)`（值 `1`），`PluginManifest` 加可选 `engines.api` 区间；README 写清 `apiVersion` 与 `manifestVersion` 的区别 | ~~0.5~~ **已落地** |
| **G2** | 能力只声明不执行 | 文档若含糊就是虚假安全 | 二选一：**(a)** 明确"仅展示"（0 成本，README 已按此写）；**(b)** 在 `PluginHost` 每个方法入口加能力检查（`host.log` 不需能力，`openPath` 需 `shell`，未来网络需 `network`），失败返回 false + 错误码 | (a) 0 / (b) 2–3 |
| **G3** | 契约不在版本库里 | 没有可审查的单一事实来源；改接口时容易漏文档 | 新增 `include/contract/IHostApi.h`：纯注释 + 常量（apiVersion、能力名、错误码），**不新增实现**；`PluginHost` 头里注明"实现此契约" | 1 |
| **G4** | 没有金丝雀插件 | 改了 `PluginHost` 没人发现插件会坏 | `tests/fixtures/plugin-full/`：一个用到**全部** host 属性/方法 + 页面 + 设置的插件；ctest 里装它、启它、断言 5 项 | 1.5 |
| **G5** | 作者上手成本高 | 手搓 zip + 算 sha256，一步劝退 | `tools/plugin-pack.ps1`（打 zip + 输出 sha256 + 生成索引条目 JSON）；`tools/plugin-new.ps1`（从模板生成骨架） | 1.5 |
| **G6** | 没有真实市场托管点 | "市场"没有落点，README 的发布章节永远是"等通知" | GitHub Pages 托管 `index.json` + Releases 放 zip；`ASSISTANT_MARKET_URL` 已在（`main.cpp:197`），只需给默认值 | 1 |

**合计：约 6–7 人日（走 G2-a）或 8–10 人日（走 G2-b）。**

> G2 建议：**v1 走 (a) 明确"仅展示"**，把执行留到真做网络/文件能力时一起设计。理由：现在 `host` 能做的事（日志/设置/提示/开链接/data 目录）本身都无害，为它们加权限检查是给自己加仪式感；而一旦开始给 `network`/`fs.write` 这类能力，权限才有意义——那时一起设计才不返工。

## 5. 接口形态建议

### 5.1 分层（最终形态）

```
第三层 进程外 API（不做）        ← 其他应用
        ↑ 需要 HTTP/IPC + 鉴权 + 信任模型重做
第二层 市场协议（已实现，待托管）  ← 索引托管方 / 发布者
        index.json + zip + sha256
第一层 插件 SPI（已实现，待版本化）← 第三方插件作者
        plugin.json + host 对象
```

**关键判断：三层不能一起做。** 第一层是"给别人扩展能力"，第三层是"把安装权交给别人"——后者的信任模型完全不同。

### 5.2 为什么第三层（进程外 API）现在不做

| 顾虑 | 说明 |
|---|---|
| 本质是远程代码执行入口 | 一个能在你机器上装插件的 HTTP 接口 = 任何本地进程（含恶意软件）都能装任意代码。必须配对鉴权、来源限制、用户确认，等于把 §9 的安全模型重做一遍 |
| 需求不明确 | "别人"要的到底是**查询**（有哪些插件、装了什么）还是**安装**？前者只读、几乎无风险；后者高风险。现在无法判断 |
| 与已有设计冲突 | `模块框架.md` §4.5 的收敛边界是为了"将来把插件挪到进程外"，那是**插件**隔离，不是**市场**暴露。方向相反 |
| 有更便宜的替代 | 真要给其他程序用，**CLI 子命令**（`Assistant.exe --plugin list`）比常驻 HTTP 服务简单一个数量级，且天然受用户控制 |

**如果将来一定要做**，建议形态（按风险从低到高）：

1. **只读 CLI**（`--plugin-list --json`）：无风险，1–2 人日；
2. **本地 HTTP 只读**：`127.0.0.1` 随机端口 + 每次启动生成的 token（写进 `%LOCALAPPDATA%\...\api-token`），只暴露 list/detail；
3. **安装类操作**：必须有**明确的人类确认**（弹窗/托盘气泡），不能由 API 静默完成。

### 5.3 市场协议（第二层）现状与缺口

已定：`index.json` 结构、`latest`/`versions`、`sha256`/`size`、`minAppVersion`、多镜像降级、缓存 + ETag + seed 兜底。

缺的只有一件事：**一个真实托管点 + 发布流程**。没有它，README 的"发布到市场"章节只能是"等通知"。

## 6. 版本与兼容策略（建议）

| 版本轴 | 作用 | 规则 |
|---|---|---|
| `manifestVersion` | 清单**格式**版本 | 现在 `1`。加必填字段 / 改字段语义才升；升了旧宿主拒绝加载并提示 |
| `engines.assistant` | 兼容**宿主版本** | 已有。宿主升级时用它挡住明显不兼容的插件 |
| `apiVersion`（**建议新增**） | 兼容**宿主 API 面** | 与 `manifestVersion` 解耦：新增 host 方法 **不**升 `manifestVersion`，只升 `apiVersion`。插件可写 `"engines": { "api": ">=1" }` |
| README 变更记录 | 作者可见的变更日志 | 每次改接口必须记一行（已建立，README §13） |

**弃用流程（建议写死）**：标记 deprecated → 至少保留一个次版本并记日志警告 → 下个次版本才删。没有这个流程，"只增不改"就只是口号。

## 8. 风险表

| 风险 | 概率 | 影响 | 处理 |
|---|---|---|---|
| 作者按文档用了"未启用"的 `commands`/`searchProviders` | 高 | 中（作者失望/报 bug） | README §6 明确列出"已解析未生效"；清单校验时对用到它们的插件写一条警告日志 |
| 接口被当成沙箱 | 中 | 高（安全误解） | README §9 + 安装确认文案都明写"完全信任、进程内"；**不做**看起来像权限拦截的 UI |
| 宿主升级 Qt 后插件行为变 | 中 | 中 | README §3.2 写清"跨 Qt 大版本不承诺"；金丝雀插件在 CI 里跑 |
| 真实市场托管后出现恶意插件 | 中 | 高 | v1 是"用户主动安装 + 完全信任"；签名留 v2；索引侧可加人工审核 |
| `apiVersion` 加了但没人用 | 中 | 低 | 金丝雀插件必须声明并断言它 |
| 三份插件文档（模块框架 / 功能设计 / 代码骨架）与 README 口径不一致 | 高 | 中 | README 是**对外唯一事实来源**；三份内部文档在开头指向它 |

**最后一条是真问题**：现在 `docs/architecture/` 下并存三份插件文档，`docs/plugins/README.md` 是第四份。对外文档必须只有一份，否则"以哪个为准"会反复消耗沟通成本。

## 9. 需要拍板的三个决策

1. **接口范围**：只做"插件 SPI + 市场协议"（推荐），还是要连"其他程序可调用的 API"一起做？
   → 选后者的话，先回答"对方要的是查询还是安装"，答案会决定做 CLI 还是 HTTP。
2. **权限模型**：v1 明确"声明仅展示"（推荐，0 成本），还是现在就加能力执行？
3. **市场托管点**：用 GitHub Pages + Releases（推荐，零运维），还是先只支持本地/侧载安装，把"市场"概念延后？

三个都定了，P-A 就能直接开工；P-A 做完，这份 README 就是可以发给第一个外部作者的东西了。
