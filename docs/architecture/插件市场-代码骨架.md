## 0. 先裁定一处冲突：插件形态

PPT 和 LLD 在**最根本的一点上不一致**，必须先钉死，否则骨架会白写。

| 维度 | PPT 方案：C++ DLL + ABI v1 | LLD 方案：QML/JS 插件包 |
|---|---|---|
| 插件载体 | `assistant_plugin.dll` + `IPlugin` 纯虚接口 | `main.qml` + 资源文件 |
| 契约 | `assistant_plugin_api.h`，header-only，ABI 版本门禁 | `plugin.json` 清单 + `host` 上下文对象 |
| 兼容性风险 | **高**：MSVC 工具集 / Qt 版本 / `/MD` / Debug-Release 全要对齐 | **无**（QML 由宿主引擎解释执行） |
| 能否卸载干净 | 难（`LoadLibrary` 后基本卸不掉，与 DSH 同样需重启） | 可以（`QQmlComponent` 对象可删、context 可删） |
| 用户可审阅 | 否（二进制） | 是（纯文本，教学价值高） |
| 出错代价 | 段错误直接崩进程 | QML 异常可捕获，标 `problem` 不崩 |
| 能力上限 | 高（任意 Win32） | 中（Qt 能做的都能做，Win32 需另包） |
| 与现有架构契合 | 中（需发明一套 C ABI） | 高（项目本来就是 QML 驱动） |

### 裁定

**以 LLD 的 D1 为准：v1 只做 QML/JS 插件包。**

理由不是"QML 更好"，而是**风险隔离**：

```
插件市场这条链路 = 索引 → 下载 → 校验 → 安装 → 回滚 → 加载 → 卸载
ABI 那条链路     = 工具链对齐 → 接口冻结 → vtable 稳定 → 版本演进
```

两条链路都很难。**混在一起会两头都做不完**——这是 LLD §D1 的原话，也是本项目的实际时间约束。

### PPT 的三部分如何处置

| PPT 内容 | 处置 |
|---|---|
| §4 插件接口规范（`IPlugin` / `IHostServices` / `getExtension`） | **降级为预留**。`plugin.json` 里保留 `"runtime": "native"`，v1 直接拒绝安装 |
| §7 ABI 兼容性策略（`/MD`、只增不改、COM 式接口演进） | **保留为独立文档**，等真有人需要原生插件时再启动；届时要求 `ISearchProvider` 已经 A7 稳定 |
| §3 分层架构、§6 市场协议、§8 安全模型、§9 时序图 | **仍然有效**，已被 LLD 吸收（数据模型、状态机、安全模型章节） |

> 一句话：**PPT 的"市场"部分作数，"DLL 接口"部分入库封存。**

**读法**：箭头 = 依赖方向。注意两条硬规则（框架 §2.1）：

| 规则 | 在文件层的体现 |
|---|---|
| **A. L4 之间不互相 include** | `PluginInstaller.cpp` **不得** `#include "PluginLoader.h"`；需要"装完启用"时由 `PluginManager` 串起来 |
| **B. 状态只有归属模块能写** | `plugins.json` 只有 `PluginRegistry` 写；`plugins/<id>/` 只有 `PluginInstaller` 写；`PluginHost` 只能写 `data/` |

> 这两条在 code review 时**只看 `#include` 就能验**：`src/core/plugin/` 下任何 .cpp 里出现另一个 L4 的头文件，就是破层。

### 2.2 纯工具层（L5）

#### `SemVer.h`

```cpp
#pragma once
#include <QString>
#include <QStringView>
#include <optional>

namespace semver {

struct Version {
    int major = 0;
    int minor = 0;
    int patch = 0;
    QString pre;            // 预发布标记，仅比较"有/无"（LLD §16.1 的子集）
};

std::optional<Version> parse(QStringView text);
int  compare(const Version &a, const Version &b);
bool satisfies(const Version &v, QStringView range);   // ">=0.6.0 <1.0.0"，空格分隔多条件

} // namespace semver
```

> **不收任何 Qt 对象例外**：`QStringView` 只读，不持有状态。整个 `semver` 命名空间无状态、无 IO → 可脱离应用单测（对齐项目里 `FuzzyMatcher` / `Calculator` 的定位）。

```cpp
#include <QByteArray>
#include <QList>
#include <QString>
#include <QStringList>
#include <optional>

struct PageContribution     { QString id, title, icon, source; };
struct ProviderContribution { QString id, title, trigger; int priority = 100; };
struct CommandContribution  { QString id, title, keyword; };

struct PluginManifest {
    int     manifestVersion = 1;
```

#### `PluginRegistry.h`

```cpp
#include <QDateTime>

struct InstalledPlugin {
```

### 2.6 ⚠ 实现反馈：`PluginListModel` 已废弃，改用 `QVariantList`

**前端写完之后发现这一层不需要独立类，已按项目既有约定改掉。**

项目里所有列表（`TodoPage` / `NotesPage` / `ClipboardPage`）都是 `model: panel.todoList` + `modelData.xxx`，
即 C++ 侧暴露 `QVariantList`（`QList<QVariantMap>`），QML 直接用 JS 数组语义。引入一个
`QAbstractListModel` 子类会成为项目里唯一的第二种列表写法，徒增维护成本。

**因此 `PluginBridge` 实际要暴露的接口改为：**

```cpp
class PluginBridge : public QObject {
    Q_OBJECT
    Q_PROPERTY(QVariantList installedList READ installedList NOTIFY listsChanged)
    Q_PROPERTY(QVariantList availableList READ availableList NOTIFY listsChanged)
    Q_PROPERTY(QVariantList categories    READ categories    NOTIFY catalogChanged)
    Q_PROPERTY(bool        isOffline      READ isOffline      NOTIFY catalogChanged)
    Q_PROPERTY(QString     fetchedAtText  READ fetchedAtText  NOTIFY catalogChanged)
    Q_PROPERTY(bool        loading        READ loading        NOTIFY loadingChanged)
public:
    Q_INVOKABLE void refresh();
    Q_INVOKABLE void install(const QString &id);
    Q_INVOKABLE void installFromZip(const QString &zipPath);
    Q_INVOKABLE void cancelInstall(const QString &requestId);
    Q_INVOKABLE void setEnabled(const QString &id, bool want);
    Q_INVOKABLE void uninstall(const QString &id);
    Q_INVOKABLE void openPluginDir(const QString &id);
signals:
    void listsChanged();
    void catalogChanged();
    void loadingChanged();
    void toast(const QString &level, const QString &text);
};
```

**每行的字段（QML 直接按名取）：**

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` / `name` / `version` / `summary` / `icon` | QString | 卡片主体 |
| `state` | QString | 上表 7 种之一，**由 C++ 判定**，QML 不做判断 |
| `badge` / `badgeKind` | QString | 角标文案与配色（`accent`/`gray`/`orange`/`red`/空） |
| `problem` | QString | 非空时卡片转红、可从详情卸载 |
| `enabled` | bool | 开关状态（`state==problem` 时恒 false） |
| `percent` | int | 安装进度 0–100（非 installing 时忽略） |
| `categories` | QStringList | 仅市场条目有；用于分类筛选 |
| `permissions` | QStringList | 详情面板展示，QML 侧映射成中文 |

> 设计收益：`PluginBridge` 只剩"查表 + 转 QVariantMap"，没有任何模型信号维护代码；
> QML 侧用 `modelData.xxx` 与其余三个页面完全一致。
> **§1.1 文件清单里的 #21 `PluginListModel.h` / #22 `PluginListModel.cpp` 作废，总数由 27 降为 25。**

## 5. `main.cpp` 装配骨架

```cpp
// ── 插件子系统（在主面板 engine 之前构造）──
PluginRegistry  registry;                       // 路径由 QStandardPaths 决定
registry.load(nullptr);                         // 失败降级为"空 registry"，不阻断启动

// ── 主面板 engine 加载之后 ──
loader.setEngine(&panelEngine);
pluginMgr.setEngine(&panelEngine);
panelEngine.rootContext()->setContextProperty("plugins", &pluginBridge);

// ── 窗口显示之前：一次算好导航项，避免"导航晚一拍蹦出来" ──
pluginMgr.loadEnabledAtStartup();

// ── 退出前 ──
// pluginMgr.unloadAll();   // 在 aboutToQuit 里
```

**顺序约束**（框架 §6.1）：

| 时机 | 为什么 |
|---|---|
| 构造在 `panelEngine.load()` **之前** | `PluginManager` 需要先存在才能注入 context property |
| `loadEnabledAtStartup()` 在 `engine.load()` **之后** | engine 不存在就没有 QML 环境可装载 |
| 在窗口 `show()` **之前** | 否则导航项会出现"晚一拍"的闪烁 |

### 8.3 一个需要现在决定的技术细节

**`Style` 单例在插件里能不能用？**

LLD §8.1 的结论是 **v1 不让插件用宿主 `Style`**，理由是插件目录不在 QML import path 里，要引入 QML module 机制，多一个坑。插件自己写色值，宿主在 README 给推荐色板。

**代价**：插件页面和宿主页面会有视觉差异（尤其深色模式下）。
**收益**：少一条"插件加载时才暴露"的失败路径。

我倾向**接受 LLD 的结论**，但这一点值得你确认 —— 因为它是"演示时好不好看"和"实现风险"之间的权衡。
