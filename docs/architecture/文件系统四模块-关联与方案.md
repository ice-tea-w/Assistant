# 文件系统四模块：关联性与实施方案

> 状态：**提案 v2（架构评审后修订）** · 2026-10
> 修订依据：架构评审意见 + 四项决策（见 §10）
> 修订原则：不重写既有文件检索与治理设计，不新增独立业务模块，不改变既有版本号映射。
> 涉及尚未验证的功能，**只冻结必要契约和不变量，不提前冻结实现细节**。
> 既有结论见 `文件检索重构方案.md`（A 阶段）、`文件治理功能设计.md`（B–E）、`v0.4-实施清单.md`（A1–A8）。

## 修订记录（v1 → v2）

| # | v1 的表述 | v2 的修订 | 触发原因 |
|---|---|---|---|
| 1 | 安全必须是"必经之路" → `FileOpGateway` 是全应用唯一写文件处 | 网关负责授权与协调，**实际文件 I/O 由受控执行组件完成** | 防止网关变成包揽所有 I/O 的上帝对象 |
| 2 | "跨模块契约只能有四个，多一个都不加" | 四个契约是**当前目标集合**；允许经论证的公开业务 API | 机械冻结数量会逼出畸形绕过 |
| 3 | 事件消费者"固定 5 个"作为架构不变量 | 5 个是**当前实现约定**，不是长期不变量 | 消费者会增长；不变的是"显式组装"而非数量 |
| 4 | `FileRef` 是"跨模块唯一句柄" | 同时是**非授权凭证**；敏感操作前必须重新解析验证 | 路径/大小/时间戳都会过期，且存在 TOCTOU |
| 5 | 判定超时/异常 → `Deny` | 扩展到**审批失效、规则更新、长作业授权生命周期** | 长生命周期操作的授权语义没定义 |
| 6 | TLS 不可用 → 退化到 TCP + 应用层 AES-GCM | **禁止退化**；TLS 后端不可验证则暂停 LAN 发布 | 应用层 AES-GCM 不是 TLS 的替代品 |
| 7 | 插件 `actorId` 由调用方填写 | 宿主解析**实际调用主体**，不信任插件自填 | 自填 actorId 等于可自授权 |
| 8 | A3 建表"顺手留两列" `sec_level`、`prov_id` | **分别论证**，不默认同时加 | 不能"因为将来可能需要"无限扩索引模型 |
| 9 | 跨库关联靠应用逻辑维护 | 必须用**可恢复状态机**，禁用隐式原子性假设 | 独立 DB 之间没有事务保证 |
| 10 | "这张表会改变 CLAUDE.md 的排期" | 阶段调整**不自动触发版本号变更** | 保持 v0.4.x / v0.5.x / v0.6.0 既有定位 |

## 0. 结论先行

1. **四个模块保持原有职责划分。** M1 管理文件索引与治理，M2 管理传输作业与共享，M3 负责安全判定、
   完整性账本与保险箱，M4 负责插件扩展与能力管理。模块之间通过明确批准的公开 API、共享契约和
   应用层编排协作，**不依赖其他模块的内部实现**。

2. **统一文件操作边界，但不建立包揽所有 I/O 的超级对象。** `FileOpGateway` 负责请求校验、
   策略判定、审批协调与执行结果关联；本地文件执行组件负责实际文件系统操作；`TransferManager`
   负责异步传输作业与网络通道。所有**需要授权的受控操作**必须经过统一边界，但
   **不要求每次读取文件分块都重新执行一次策略判定**。

3. **身份、定位、快照和授权状态分别定义。** `FileRef` 是跨模块传递的轻量值句柄，不等同于
   持久化物理身份，也不构成授权凭证。路径、大小、时间戳、分类及密级都可能过期；
   安全敏感操作必须在执行前**重新验证目标对象和请求条件**。

4. **事件通知用于增量处理，不作为完整审计日志。** `ReadDirectoryChangesW` 产生的通知可能丢失、
   重复或溢出。消费者必须支持重复处理、失败隔离和恢复扫描；涉及传输、入库、账本与索引的
   跨数据库流程必须通过**可恢复状态机**修复中断后的不一致。

5. **实施顺序仍采用依赖阶梯，但不强制所有功能串行。** 先稳定文件身份、事件恢复和受控操作边界，
   再完成治理过滤、安全判定及本地 box/追踪闭环，之后分阶段交付传输作业内核、渠道通道和 LAN 通道。
   保险箱独立验证密钥与恢复机制；插件仍安排在核心 API 稳定后。
   **mDNS 暂不纳入首版交付要求**，后续根据实际发现需求评估。

## 1. 术语与前提

| 词 | 含义 | 注意 |
|---|---|---|
| **基座** | `FileIdentity` / `FileSnapshot`+`SnapshotManager` / 事件分发器 / 各数据库访问组件 / `DatabaseMigrator` / `Logger` / `ConfigManager` | **不是一个新类**。不要造 `FileKernel` 门面，那会变成第二个上帝对象 |
| **门面** | 每个模块对外暴露的薄类：M1 `FileIndex`、M2 `TransferManager`、M3 `SecurityCenter`、M4 `PluginManager` | 沿用重构方案 §2.2：逻辑能不能放进协作者？能就别加到门面 |
| **契约** | 模块之间明确的耦合面（§3.3 的 C1–C4） | 契约头放 `include/contract/`，不得引用任何模块的实现头 |
| **公开业务 API** | 模块门面上**明确批准**的方法，供其他模块或应用层调用（如 `FileIndex::upsert()`） | 与"内部实现头"的界线见 §3.4 |
| **受控操作** | 需要授权、会改变文件系统状态或把内容送出本机的操作：删除/移动/复制到外部/发送/加解密/保险箱密钥操作 | `Open` 属于受控但低风险，审计可异步 |
| **调用主体（actor）** | 请求的实际发起方，**由宿主解析**，不是调用方自报 | 插件自填 `actorId` 无效（§4.4） |
| **快速签名（quickSig）** | 低成本变化筛查用的内容指纹 | **不等于**完整内容哈希（§4.3） |
| **恢复状态机** | 跨库/跨步骤流程的持久化状态与恢复入口集合 | 禁止假设跨库原子性（§5） |
| **M1–M4** | 本文对四个模块的简称，**与 Phase A–E、GUIDE 的 Phase 0–4 都不是一套编号** | 见 §6 映射表 |

**技术前提**（沿用重构方案 §0，不重复论证）：Win32 目录遍历 + `ReadDirectoryChangesW`、
SQLite WAL、Qt6 Quick、vcpkg、单进程 GUI 应用。

## 2. 职责划分

### 2.1 每个模块回答一个问题

职责说不清时，用"它回答哪个问题"来判。一个问题只能有一个模块回答——两个模块都能回答的事，
必然会长出两套不一致的实现。

| 模块 | 回答的问题 | 主要输出 | 明确**不**回答 |
|---|---|---|---|
| **M1 文件管理** | 盘上**有什么**、在**哪**、怎么**找到**它 | 索引快照、查询结果、分类/排除、box 登记与去向 | 该不该被操作（问 M3）、怎么送出去（问 M2） |
| **M2 传输与共享** | 文件怎么**出去**、怎么**进来** | 传输作业（状态机/分块/校验/重试/恢复）、设备配对、通道 | 文件是什么（问 M1）、能不能发（问 M3） |
| **M3 安全** | 这件事**该不该允许**、东西**有没有被动过**、**怎么保护** | 判定结果（Allow/Ask/Deny）、完整性账本、审计、保险箱 | 文件在哪（问 M1）、怎么发（问 M2） |
| **M4 插件** | 谁**来加**新能力、加的能力**能碰什么** | 扩展点实现、能力声明、插件生命周期 | 以上任何一件事本身 |

M3 内部明确分成三种能力（§4.3）：**发现**（事件+复核）、**判定**（策略+审批）、
**保护**（保险箱+密钥）。三者的验收方式完全不同，不要用"安全"一个词糊在一起。

这张表还有个用处：**任何新需求先落到一行里**。落不进任何一行，说明它是第五个模块，
应该先停下来讨论，而不是塞进现有模块。

### 2.2 反例：两种会死的方式

**死法一：跨模块依赖内部实现（不是"跨模块调用"）。**
v2 明确允许模块调用彼此的**公开业务 API**，所以"M3 调了 `FileIndex::query()`"本身不是问题。
问题是：M2 为了"发送前检查一下"直接 `#include` 了 M3 的 `PolicyEngine`（内部协作者）；
M3 为了"列出敏感文件"直接查了 M1 的 `files` 表（内部数据库结构）；M4 直接调 M2 的
内部通道（绕过授权边界）。
四个月后：改 M3 的规则结构要动 M2，改 M1 的表结构要动 M3，插件作者开始依赖内部类。
**这是绝大多数桌面项目在第四个模块死掉的方式。**

判据很硬：**依赖的是 `include/contract/` 里的类型、模块门面上的批准方法、还是应用层编排？
三者之一合法；其余一律驳回。**

**死法二：每个模块自己扫盘、自己记账。**
M3 要"发现敏感文件"，就自己 `QDirIterator` 走一遍；M2 要"列出可分享的文件"，也走一遍。
结果：三份不同的文件清单、三套不同的排除规则、用户改了排除规则只生效一处、
大目录下三个线程同时打盘（这正是 A1 之前 `NoSymLinks` 那个坑的放大版）。

两个死法的共同解法：**共享的事实只有一个来源（M1 的索引 + 事件），共享的判定只有一个入口（M3 经网关）。**

## 3. 关联性：一条受控流水线 + 一个身份 + 少数契约

### 3.1 分层结构与依赖方向

```
接入层 ┃ QML 搜索浮窗 · 主面板 · 托盘 · 插件（只经 IHostApi，不碰模块）
       ┃
       ┃ ↓ 只调门面 / 契约 / 网关
       ┃
模块层 ┃ M1 文件管理 · M2 传输与共享 · M3 安全 · M4 插件
       ┃ 门面：FileIndex / TransferManager / SecurityCenter / PluginManager
       ┃
       ┃ ↓ 只依赖契约头（include/contract/）与批准过的公开 API
       ┃
契约层 ┃ C1 FileRef │ C2 FileSystemEvent │ C3 FileOpGateway 相关类型 │ C4 IHostApi
       ┃
       ┃ ↓
       ┃
基座层 ┃ FileIdentity · FileSnapshot/SnapshotManager · 事件分发器
       ┃ FileIndexDatabase 等各库访问组件 · DatabaseMigrator · ConfigManager · Logger
```

（没有右侧竖线：中英文混排宽度不一，画右边框必然对不齐。分层关系靠左侧层级名与箭头表达。）

- **接入层**：QML 搜索浮窗、主面板、托盘、插件。插件只能通过 `IHostApi` 调用宿主公开能力。
- **模块层**：四个模块各自一个薄门面。
- **契约层**：`FileRef`、`FileSystemEvent`、`FileOpGateway` 相关类型、`IHostApi` 及能力定义。
- **基座层**：身份、快照、事件分发、数据库访问、迁移、日志、配置。

**依赖方向永远向下**，下层不认识上层。两处"向上"是接口倒置：`IFilePolicy` 由 M3 实现、
`IHostApi` 由应用层实现，基座只持有指针（`main.cpp` 注入）。

三条组织规则：

1. 模块之间可以使用**明确批准的公开业务 API**，但不得依赖其他模块的内部实现头、
   内部数据库结构或私有协作者。
2. **应用层是组合根**，负责构造对象、建立依赖、注入策略实现。
3. 不得为了消除每一次公开 API 调用而新增临时抽象接口，也**不得把所有业务协调逻辑集中到
   一个新的全局门面**——那是把四个上帝对象换成一个更大的。

`FileOpGateway` 不负责任实现所有文件操作或网络操作：它负责**受控操作的统一授权与执行协调**，
实际本地文件操作由受控执行组件完成，传输作业由 M2 完成。

### 3.2 受控操作流水线

所有由本应用发起、且需要受控授权的文件变更操作，必须经过统一授权与执行边界。

```
请求提交 → 调用主体校验 → 目标对象重新解析 → 策略判定 → 必要时等待用户审批
        → 执行前再次验证 → 执行 / 创建异步作业 → 记录最终结果 → 更新相关状态
```

| # | 规则 |
|---|---|
| 1 | **调用主体由宿主解析**（依据实际调用上下文），插件不能通过自行填写 `actorId` 获得更高权限 |
| 2 | 策略判定由 M3 提供，必须明确返回 `Allow` / `Ask` / `Deny`。**策略异常、无效结果和超时均不得默认放行** |
| 3 | `Ask` 表示**尚未授权执行**。审批期间必须保存请求上下文；审批完成后**重新验证**目标对象、操作类型、目标设备及策略有效性 |
| 4 | 本地文件操作由**受控执行组件**实施；`FileOpGateway` 不直接承载所有底层文件 I/O |
| 5 | `Send` 是长生命周期操作：网关负责授权并**创建受控作业**，M2 负责分块、重试、取消、校验及作业恢复 |
| 6 | 长耗时任务**不要求每次读数据块都重新跑完整策略求值**，但必须在适当边界校验源文件身份、版本与授权有效性 |
| 7 | 文件系统通知与网关返回的操作结果**属于不同信息来源**。消费者必须识别重复处理，**不能把一次操作结果和一次文件系统通知当成两个独立变更**（用操作 id 关联） |
| 8 | 审计采用**分级持久化**：普通打开可异步记录；删除、移动、敏感文件外发、保险箱密钥操作必须记录请求、判定、执行结果与必要的恢复信息 |

**这条流水线只覆盖经由本应用的受控操作。** 资源管理器、其他应用及外部程序直接发起的操作
**不在网关的强制拦截范围内**。完整性账本只能承诺"在监控和复核能力范围内发现变化"，
不承诺阻止所有外部修改（§4.3、§8）。

### 3.3 契约

#### C1 `FileRef` —— 跨模块轻量值句柄

`FileRef` **不是**物理身份凭证，**不是**文件快照的永久保证，**不是**安全授权凭证。

```cpp
// include/contract/FileRef.h
struct FileRef {
    quint64 id      = 0;   // 进程内不透明句柄（插件只能拿到这个）
    QString path;          // 可失效的定位提示，不是稳定主键
    qint64  size    = 0;   // 快速变化提示，不是内容完整性证明
    qint64  mtime   = 0;   // 同上
    quint32 catMask = 0;   // M1 派生快照字段，可能随索引状态变化
    quint8  flags   = 0;   // Project / Inbox / Duplicate …
    quint8  secLevel= 0;   // M3 派生展示/筛选用，不得单独用于授权
};
```

- `id` 必须定义**进程重启、文件删除、句柄失效、重新解析**时的行为（这些是语义，不是实现细节）。
- 字段结构可随实现调整，但下述语义不可省略。

**重新验证与竞态：**

- 跨模块使用 `FileRef` 时，按操作风险决定是否重新解析与验证。
- 对安全敏感的读取、删除、移动、加解密或外发操作，**尽可能通过已打开的文件句柄验证实际目标对象**，
  避免"先按路径检查、再按路径打开"的检查与使用竞态（TOCTOU）。
  路径校验只能作为快速拒绝，不能作为最终保证。

**发送/接收的一致性不变量：**

- 发送前必须校验**源文件身份**（不是只看 `size`/`mtime`）。
- 传输期间必须检测源文件变化。
- 接收端必须做**分块校验 + 最终完整内容校验**。
- 若要求"发送内容与授权时的内容严格一致"，必须明确采用**可验证的快照、受控文件句柄或其他
  一致性策略**，不能仅依赖 `size` 与 `mtime`。

#### C2 `FileSystemEvent` —— 文件系统变化通知

`FileSystemEvent` **不是**持久化审计日志，也**不是**保证不丢失的事件流。

```cpp
// include/contract/FileSystemEvent.h
enum class FsEventType : quint8 { Added, Removed, Renamed, Overflow };

struct FileSystemEvent {
    FsEventType type;
    QString     path;      // Added/Removed/Overflow 用
    QString     oldPath;   // Renamed 用
    quint64     seq;       // 单调序号：生成方、作用域、比较规则见下
    quint32     rootId;    // 监控根，Overflow 时定位受影响范围
};
```

事件协议**必须明确**（这五项缺一项，消费者就只能猜）：

1. `seq` 的**作用域、生成方和比较规则**（是全局单调还是每根目录单调？跨根如何比较？）。
2. `Added` / `Removed` / `Renamed` 的**路径语义**（`Renamed` 是旧路径→新路径；目录重命名时子树怎么表达）。
3. **可获得的物理身份信息**及其缺失情况（不是每个事件都能拿到 `FileId`）。
4. `Overflow` 对应的**监控根或受影响范围**。
5. **重复事件、乱序事件、消费者失败**的处理方式。

**消费者由应用层显式组装。** 分发器不依赖 M1–M4 的实现头，不使用字符串主题构建全局 EventBus。

**恢复流程（不是"应该"、是硬性）：**

| 消费者 | 收到 `Overflow` / 监控中断 / 处理失败时 |
|---|---|
| M1 | 重扫受影响范围并修复索引 |
| M3 | 把相应账本范围标为**待复核**；**不能因为没收到后续事件就认定文件未变化** |
| M2 | 对作业关联的源文件与目标文件**主动校验**；不能仅靠通知决定作业状态 |
| 其他 | 必须明确写出自己的恢复、重试或降级策略，否则不得接入 |

固定消费者数量可以作为**当前实现约定，但不作为长期架构不变量**。新增消费者必须通过显式依赖
组装与验收，**不得以"增加一个消费者"为由引入隐式全局订阅机制**。

#### C3 `FileOpGateway` —— 受控操作的唯一授权与协调入口

`FileOpGateway` **不是**所有文件 I/O 和网络 I/O 的唯一实现类。

```cpp
// include/contract/FileOpGateway.h
enum class FileOp  : quint8 { Open, Reveal, Copy, Move, Delete, Send, Encrypt, Decrypt };
enum class Verdict : quint8 { Allow, Ask, Deny };

struct OpRequest  { FileRef ref; FileOp op; QString dest; QString actorId; }; // actorId 由宿主填
struct OpDecision { Verdict verdict = Verdict::Ask; QString reason; quint32 obligations = 0; };
struct OpResult   { bool ok = false; QString error; bool cancelled = false; quint64 opId = 0; };

class IFilePolicy {                       // 由 M3 实现
public:
    virtual ~IFilePolicy() = default;
    // 同步、纯内存规则求值；不访问磁盘/网络，不等待用户交互
    virtual OpDecision decide(const OpRequest &r) = 0;
};
```

职责划分：

| 组件 | 负责 | 不负责 |
|---|---|---|
| `FileOpGateway` | 请求校验、主体识别、策略调用、审批协调、执行前验证、结果关联 | 不实现底层文件 I/O、不实现传输 |
| `IFilePolicy`（M3） | 同步纯内存的策略判定 | 审批、持久化、哈希计算、传输准备 |
| 本地文件执行组件 | 执行受控本地文件操作 | 不做策略判定 |
| `TransferManager`（M2） | 异步传输作业与通道 | **不绕过授权边界** |
| 审计组件 | 按风险与策略要求持久化请求/判定/结果 | 不阻塞前台 |

**`FileOpGateway` 实现为由应用层注入依赖的具体协调类。** 未来确有多种实现需求时再抽接口；
当前**不因形式统一而额外增加一层无必要的虚接口**（v1 在这里过度设计了）。

`IFilePolicy::decide()` 的低延迟目标**只适用于纯内存规则求值**。用户审批、数据库持久化、
完整性哈希与传输准备都不属于该调用的执行范围。

**失败关闭范围**（比 v1 更完整）：策略异常、超时、无效结果、**审批失效**，以及
**已进入执行阶段的长生命周期作业遭遇规则更新或信任撤销**——都必须由明确的作业状态与
授权生命周期规则处理，不得默认放行。用户取消必须使后续块级操作失效。

**全仓库静态检查的真实语义：**

- 覆盖实际使用的文件变更 API：Qt（`QFile`/`QDir`）、Win32（`SHFileOperation`/`IFileOperation`/
  `MoveFileEx`/`DeleteFile`）、Shell、标准库（`std::filesystem::remove/rename/copy`）。
- 规则必须**允许经批准的底层执行组件**实现操作，同时**拒绝** QML 接入层、插件及其他模块私自执行。
- 验收标准**不是**"某个源文件里没有匹配字符串"，而是**证明所有受控文件变更的调用路径都经过统一边界**。
- 确有不适用的操作时，**逐项记录例外及原因**，不允许静默绕过（例外清单进 `tests/` 的
  白名单文件，随代码一起 review）。

#### C4 `IHostApi` + Capability —— 插件唯一入口

```cpp
// include/plugin/IHostApi.h  （只依赖公共类型层，不依赖任何模块头）
class IHostApi {
public:
    virtual ~IHostApi() = default;
    // 每个方法标注所需 capability；默认拒绝（deny by default）
    virtual QList<SearchResult> search(QStringView text, int limit) = 0;        // index.read
    virtual std::optional<FileRef> resolve(quint64 id) = 0;                     // file.read
    virtual bool submitIngest(const QString &path, const QString &source) = 0;  // ingest.write
    virtual bool requestSend(quint64 id, const QString &deviceId) = 0;          // transfer.send（必过授权）
    virtual void showPanel(const QString &qmlUrl) = 0;                          // ui.panel
};
```

能力清单（v1 就 8 个，**名称集中定义在一处常量**，不允许各处随意拼写）：
`index.read` / `file.read` / `file.write` / `op.execute` / `ingest.write` / `transfer.send` /
`security.policy.read` / `ui.panel`。

**Capability 负责声明与检查"允许调用哪些宿主 API"，不构成进程内安全边界。**（§3.4 第 7 条、§4.4）

### 3.4 依赖规则

1. 禁止跨模块依赖**内部实现头、私有数据库结构和内部协作者**。
2. 允许使用**明确批准的公开业务 API**、共享契约及应用层编排进行模块协作。
3. 只有当职责独立、生命周期明确或存在真实扩展需求时才新增接口；**不得为单个调用临时制造抽象**。
4. 契约头不得依赖模块实现头。插件 API 使用公共类型层定义的稳定数据类型，**不直接导出 M1 的内部查询模型**。
5. 门面之间的所有权由应用层管理，优先使用清晰的所有权模型与必要的非拥有引用，**不允许形成所有权环**。
6. 事件消费者必须**显式组装**，并定义重复处理、失败隔离与恢复策略。
7. Capability 负责声明和检查允许的宿主 API 调用，**不构成进程内安全边界**。

**契约数量与代码行数是设计审查的提示，不是正确性指标。** 任何新增契约都必须说明：
**独立职责、必要性、依赖方向、失败语义**。四项说不清就是不该加；说得清就不必因为"超过四个"而绕道。

### 3.5 七条边：方向 / 协议 / 失败模式

加任何新交互前，先看它落在哪条边上；落不进就是新增了一条边，需要重新讨论。

**每条边只允许走三种东西**：C1–C4 契约之一、模块门面上**批准过的公开 API**、或应用层编排。
出现第四种（尤其"为这条边新建一个接口"）说明契约漏了或职责重叠——回头改设计，不要就地加接口。

| 边 | 传递什么 | 走什么 | 失败模式与对策 |
|---|---|---|---|
| **M1 → M2** | 待发送的选择集（`QList<FileRef>`） | `TransferManager::enqueue()`（公开 API） | 排队到发送时文件已改/删 → 发送前**重新解析并校验身份**（不只 size/mtime），不匹配则重新取 ref 或标 `Stale` 跳过，**绝不发半截文件** |
| **M2 → M1** | 新落地文件（`upsert` + 来源信息） | `FileIndex::upsert()/remove()`（公开 API） | 索引未就绪/扫描中 → **排队不丢**（与 `FileIndex` 的 pendingRefresh 同款语义）；M1 不可用时 M2 仍能完成传输，只是"暂时搜不到"，恢复后补提交 |
| **M1 → M3** | 视野（query / 快照统计）+ 变更事件 | `query()`（公开 API）+ C2（订阅） | 事件 `Overflow`/中断 → M3 把该根标"待复核"，巡检兜底；**M3 不得自己扫盘** |
| **M3 → M1** | 密级回写（`secLevel` 进快照） | 快照重建（与 `catMask` 同机制） | 规则变更后快照未重建 → `rulesVersion` 单调号驱动重建；**且授权时必须重新判定**，不得只信快照里的 `secLevel` |
| **M3 → M2** | 授权结论 `OpDecision` + `obligations` | 网关判定后**创建受控作业**；M2 只执行作业 | 判定异常/超时/审批失效 → `Deny`；作业执行中规则更新或信任撤销 → 按作业状态机处理（§3.3 C3） |
| **M2 → M3** | 外来文件的校验请求（哈希、隔离清单、来源设备） | `SecurityCenter::verifyIncoming()`（公开 API） | 校验不符 → 留在隔离区、**不 Ingest**、不进索引（否则"搜得到但打不开"更糟）；崩溃后按恢复状态机续验或清理 |
| **M4 → 全部** | 能力调用 | `IHostApi`（内部转公开 API / 网关） | 能力不足 → 明确错误码 + UI 文案，不许静默失败；插件异常 → 见 §8（v1 承认可能拖垮主进程） |

## 4. 逐模块设计要点

### 4.1 M1 文件管理的接缝

M1 继续负责文件索引、查询、分类、排除、box 登记和去向追踪，**不承担** M2 的传输执行或
M3 的安全授权。`FileIndex` 保持薄门面：M2/M3 是它的**客户**，不是成员。

**`sec_level` 与 `prov_id` 分别论证，不作为必须同时添加的字段。**

| 字段 | 加的条件 | 必须明确的语义 |
|---|---|---|
| `sec_level` | M3 密级结果的**派生缓存**，且能识别规则版本过期 | 授权时**必须重新判定**；该字段只用于展示/筛选/粗筛，不能作为授权依据 |
| `prov_id` | 来源关联、查询性能或现有数据模型**确有需要**时才进索引库 | 来源记录的**权威存储位置**、关联失效时的行为、删除与迁移策略 |

- 若来源记录位于独立数据库，**不得假设两个独立数据库之间具备普通跨库外键的完整一致性保证**；
  跨库关联通过稳定标识与可恢复的应用逻辑维护（§5）。
- 新增字段必须服务于**明确的查询或恢复需求**，不能仅因为"未来模块可能需要"而无限扩展索引模型。
- `secLevel` 若进快照：`std::vector<uint8_t>`，20 万条约 0.2 MB，按 `rulesVersion` 重建（不重扫盘）。

### 4.2 M2 传输与共享的安全边界

M2 采用统一的传输作业内核，负责：任务状态、分块、校验、重试、取消、恢复、传输通道。

**首版分三个独立交付单元**（不要一次做完，每单元单独可验收）：

| 交付单元 | 内容 | 验收焦点 |
|---|---|---|
| **① 传输作业内核** | 状态机、分块校验、取消、恢复 | 先用**本地模拟通道**验证，不碰网络 |
| **② 渠道目录通道** | 复用已有 box、来源追踪与归档机制 | 入库与索引一致性 |
| **③ LAN 通道** | 设备配对、经过验证的 TLS、接收隔离区、分块续传、最终提交 | ①②稳定后再做 |

**LAN 首版不要求 mDNS。** 手动地址与配对码作为初始连接方式。是否加入 mDNS 在后续阶段根据
设备发现体验、维护成本和依赖情况重新评估，**不视为永久禁止**。

**接收端硬性要求：**

- 远端**不能**决定最终绝对落盘路径。
- **未完成校验的文件不得进入正式索引**。
- 默认**不覆盖**同名文件。
- 拒绝路径穿越、ADS（`:`）、保留设备名（`CON/PRN/AUX/NUL/COM1-9/LPT1-9`）、危险的 reparse point。
- 接收、验证、入库、索引更新**必须可在崩溃后恢复**（§5）。
- 源文件变化、重复块、任务取消、最终提交失败**必须有明确的状态转移**。

**TLS 规则（v1 的红线，已修订）：** 如果目标环境无法提供**经过验证的** TLS 后端，
**暂停 LAN 发布**，不得自动退化为未经验证的自研加密协议。
**应用层 AES-GCM 不得被当作 TLS 的直接替代品**——两者解决的是不同层面的问题。

### 4.3 M3 安全模块

M3 明确区分三种能力（验收方式不同，不可互相代替）：

| 能力 | 内容 | 依赖 |
|---|---|---|
| **发现** | 通过文件系统通知、快速签名和周期性复核发现变化 | C2、`FileIdentity` |
| **判定** | 对经由本应用的受控操作执行策略求值、审批和拒绝 | C3 |
| **保护** | 保险箱、密钥管理和受控的明文生命周期 | 加解密/DPAPI |

**完整性账本不承诺覆盖所有外部文件操作，也不把文件系统通知视为完整日志。**

- **快速签名只用于低成本的变化筛查，不等于完整内容哈希。** 需要验证完整内容一致性时，
  必须使用**全量内容哈希**，或**经过验证的分块哈希 + 最终内容哈希**。
- 账本状态必须能区分：**正常 / 待复核 / 已变化 / 不可验证**。监控中断、事件溢出、
  文件读取失败必须显式标记，**不能静默视为正常**。
- 变更检测两级：`mtime/size` 变了才重算 `quickSig`（便宜的先判）；`quickSig` 命中变化才升级到
  全量哈希（仅对需要裁决的文件）。

**敏感文件发现默认关闭。** "扫内容判敏感"要把用户文档正文读进内存做匹配，隐私风险大于收益：
默认 `off`，开启时明确告知读取范围，且**匹配结果不落盘、不记路径明文**（只记"某目录命中 N 个"，
防止索引/账本库本身成为泄漏源）。另一条更划算的路是先做**路径/名称/种类规则**，零内容读取。

**保险箱 v1 采用静止态加密**，必须明确五件事：

1. **数据加密密钥**的生成与管理（内容用 AES-256-GCM，密钥由 DPAPI 保护）。
2. **nonce 不重复的保证**（同一密钥下的 nonce 管理策略；随机 nonce 的碰撞概率论证或计数器方案）。
3. **文件名、元数据与密文之间的认证关系**（AAD 里绑什么；元数据被篡改能否被检出）。
4. **恢复码**的生成、保存、验证和密钥恢复语义（含"用户丢失恢复码"的明确后果）。
5. **临时明文的创建、使用、清理与异常恢复**；以及**文件修改后重新加密与冲突处理**的规则。

**关于"擦除"的诚实表述**：普通删除临时文件**不能**保证 SSD、文件系统日志、备份和分页文件中的
明文副本都被彻底物理擦除。产品**只承诺受控的临时明文生命周期**，不承诺无法验证的绝对擦除。

**v1 不承诺**：运行期间无明文、驱动级透明加密、外部程序访问时的全程无明文（它们需要驱动或
常驻解密服务，见 §8）。

### 4.4 M4 插件

插件 v1 面向**用户主动安装并明确授权的可信代码**，采用**进程内加载**。

**必须先说清的一句**：进程内插件可以直接调用 Win32 API、访问进程内存或影响宿主，
因此 **manifest、签名和 Capability 不是安全沙箱**。插件签名用于**识别来源和完整性**，
**不代表插件行为天然可信**。

宿主必须：

- 从**可信的加载位置**加载插件，并明确安装与启用流程。
- 校验 **manifest、API 版本和能力声明**。
- **由宿主识别实际插件身份**，不能信任插件自行提交的 `actorId`。
- 在**每次**宿主 API 调用时校验所需能力。
- 管理停用、卸载、初始化失败、宿主关闭时的生命周期（`init()` 失败要干净回滚，
  `shutdown()` 幂等，不留半初始化的 provider）。
- 对插件异常提供明确错误信息，并**承认进程内插件仍可能导致主进程崩溃**。

**能力名称采用固定定义，不允许各处随意拼写。API 版本兼容与能力授权分别判断**
（版本不兼容拒绝加载；能力不足拒绝调用——两个错误码不能混）。

进程外插件与 IPC 隔离列为**后续候选，不属于 v1 交付范围**。
**mDNS 与插件进程外化是两个不同的后续决策，不互相绑定。**

## 5. 存储边界与恢复语义

保留各功能独立数据库 + 统一启动迁移协调的设计。每个数据库必须明确：
**权威性、唯一写者、迁移失败策略、恢复方式**。

| DB | 性质 | 唯一写者 | 迁移失败 |
|---|---|---|---|
| `file_index.db` | **派生**（可从磁盘重建） | `FileIndexDatabase` | 备份后**重建**（代价 = 重扫） |
| `downloads.db` | **权威**（box / 去向链重建不出来） | `DownloadsDatabase` | 保留原始数据 → **停止依赖该数据的功能**，拒绝启动 |
| `security.db` | **权威**（账本/审计/保险箱清单**丢了不可重建**） | `SecurityDatabase` | 保留原始数据 → **停止相关功能**，拒绝启动（比 downloads 更硬） |
| `transfer.db` | **半权威**（作业历史可弃，**配对信任不可弃**） | `TransferDatabase` | 保留原始数据 → **降级启动**：禁传输、提示重新配对 |
| `plugins/<id>/` | 插件私有（命名空间隔离） | 插件自己（经 `IHostApi` 拿路径） | **隔离相应插件**，不破坏主程序状态 |

**跨数据库操作不得依赖隐式原子性。** 传输完成、来源登记、安全校验、box 提交、索引更新
必须通过**可恢复状态机**协调。每个状态必须明确四件事：

1. 已完成的持久化操作。
2. 可以安全重试的操作。
3. 必须补偿或回滚的操作。
4. 无法自动恢复、需要用户处理的状态。

两个必须写成用例的例子：

- **接收文件已写入 quarantine 但尚未入库** → 重启后继续验证，或安全清理（不得留在"半入库"）。
- **来源登记成功但索引更新失败** → 重新提交索引更新，**不要重新接收整个文件**。

**数据库独立性不意味着所有跨库状态天然一致。** 每个跨库流程都必须有明确的**恢复入口**和
**验收用例**（§6.3）。这是 v1 只写了"靠应用逻辑维护"、v2 要求补上的部分。

### 5.1 迁移时序（不变）

打开 DB → 读 `user_version` → 逐版本迁移 → commit → 之后才允许其它 DB 访问。
5 个存储区需要一个**统一启动迁移阶段**跑完再进主循环，不要各自在构造函数里偷偷建表。
只做前向迁移，每步一个事务，禁止 `DROP TABLE` 重建（加列用 `ALTER TABLE ADD COLUMN`）。

## 6. 分期落地

### 6.1 实施顺序

```
内核 A3–A6（身份 · 事件恢复 · 受控操作边界）
  │
  ├─ B 治理过滤 ──┐        两线可并行开发；但 box 会同时依赖二者的
  ├─ M3-p1 安全 ──┤        接口与恢复语义，所以集成前须各自验收
  │               │
  │               ├─ C/D box + 来源追踪 + 入库恢复闭环
  │               │    ├─ M2① 作业内核 ─▶ M2② 渠道通道 ─▶ M2③ LAN 通道
  │               │    └─ E 归档多源（不被 LAN 待定阻塞）
  │               │
  │               └─ M3-p2 保险箱（独立验证；不依赖 M2 业务模块）

公开 API 定型 ─▶ M4 插件（不挂在任何一条实现链后面）
```

读法：主干是"内核 → 判定/治理 → 本地闭环 → 传输三级 → 插件"；
保险箱是旁支（只需加密工具与 M3，不需要 box 或传输）；
插件挂在"公开 API 定型"这个条件上，而不是挂在某条实现链的末尾。

1. 完成**文件身份、索引、事件恢复和统一操作边界**的基础设计。
2. 治理过滤与安全判定**允许并行开发**，但在依赖这些能力的 box/追踪集成之前，
   **必须验证各自的接口和恢复语义**。
3. 完成本地 box、来源追踪与**入库恢复闭环**。
4. 先交付**传输作业内核**，再交付**渠道目录通道**。
5. 在作业内核、TLS 环境验证、接收隔离和恢复流程稳定后交付 **LAN 通道**。
6. 归档多源 E 按实际依赖推进，**不因为 LAN 的发现机制尚未决定而阻塞本地归档功能**。
7. 保险箱**独立验证**加密、密钥、恢复码和临时明文处理；可复用经过验证的底层加密工具，
   但**不强制依赖 M2 的业务模块**。
8. 插件系统在核心公开 API 稳定后交付。

**并行与串行的界线**：可以并行的是"互不依赖的实现工作"（B 与 M3-p1）；
**不能并行的是"被同一闭环依赖的接口"**——box 要同时依赖分类与判定，所以两者的接口与恢复语义
必须先各自验收。

### 6.3 验收标准的修订原则

验收指标必须反映**真实的行为保证**——不以"某个类存在""某个字符串未命中""某个方法返回成功"
代替系统级正确性。

| 领域 | 必须验证 |
|---|---|
| **文件操作** | 受控操作调用路径；**绕过执行器的反例**（含 QML 层、插件、其他模块直调） |
| **策略判定** | 异常、超时、**审批失效**、规则更新时**不会默认放行** |
| **身份校验** | 路径替换、文件 ID 变化、同名文件、硬链接、**源文件在传输中被改** |
| **事件恢复** | 重复通知、溢出、进程中断、消费者失败后能修复状态 |
| **传输** | 块校验、**最终内容哈希**、取消、断点恢复、**崩溃后的重复提交** |
| **保险箱** | nonce 管理、恢复流程、密钥丢失、临时明文、异常退出 |
| **插件** | 能力不足、**身份伪造（自填 actorId）**、版本不兼容、初始化失败、禁用后的行为 |

**性能目标必须在明确测试环境中验证，并同时记录失败率、资源消耗和前台响应性。**
未经实测的数值只能作为**目标**，不作为已实现能力的声明。下表是**目标值**，不是承诺：

| 指标 | 目标（待实测） |
|---|---|
| `IFilePolicy::decide()` | P99 < 2 ms（纯内存） |
| 账本基线 | 白名单 2 万文件 < 20 s |
| LAN 传输 | 千兆网 1 GB 文件 ≥ 40 MB/s |
| 插件加载 | < 100 ms |

## 7. 技术选型（只列新增）

| 需求 | 选型 | 理由 / 备注 |
|---|---|---|
| 物理身份 | Win32 `GetFileInformationByHandleEx(FileIdInfo)` | 128-bit `FILE_ID_INFO`；既有 `FileIdentity` 已定此路 |
| 受控句柄校验 | `CreateFileW` + `GetFileInformationByHandle` | 支撑 C1 的"用句柄验证而非按路径重开" |
| 快速签名 | `QCryptographicHash` SHA-256（`size‖首64KB‖尾64KB`） | 只做变化筛查；完整性裁决须全量哈希 |
| 全量哈希 | `QCryptographicHash` SHA-256（流式） | 大文件必须流式，不能整读进内存 |
| 加解密 | **Windows CNG**（`BCryptEncrypt`，AES-256-GCM） | 零新依赖；**必须自管 nonce 与 AAD**（§4.3） |
| 密钥保护 | DPAPI `CryptProtectData`（用户作用域） | 系统级、无需自管主密钥；配一次性恢复码 |
| LAN 传输 | `QTcpServer/QSocket` + `QSslSocket`（自签 + SPKI pinning） | **TLS 后端必须先实测**（vcpkg 版 Qt 需 OpenSSL 或 6.5+ Schannel）；不可验证则暂停 LAN 发布，**不退化** |
| 设备发现 | v1：配对码 + 手动 IP:port；mDNS 后续评估 | Qt6 无内置 mDNS，v1 不引依赖 |
| 文件系统变更 | `ReadDirectoryChangesW` | 已有计划；必须处理 `Overflow` 与重复事件 |
| 插件加载 | `QLibrary` | 进程内；接口参数只用 POD/JSON，为后续进程外化留路 |

**明确不选**：文件系统过滤驱动（`minifilter`）——需要签名与内核调试，学习收益/成本比极差；
自研加密协议；把应用层 AES-GCM 当作 TLS 替代；USN Journal 之外的卷级监控；
在插件里做"沙箱"承诺。

## 8. 风险与不做的部分

| 风险 | 处理原则 |
|---|---|
| 安全模块产生假安全感 | 明确区分**发现 / 判定 / 保护**，不宣称能阻止所有外部操作 |
| 网关成为上帝对象 | 网关负责授权与协调，**执行器**和**传输模块**分别负责实际操作 |
| 文件身份与路径不一致 | 执行前重新解析并验证目标对象，不能仅依赖路径、大小和时间戳 |
| 事件丢失或溢出 | 补偿扫描 + **待复核**状态 + 可恢复任务（§3.3 C2） |
| 跨数据库状态不一致 | 持久化状态机 + 幂等处理 + 明确恢复流程（§5） |
| TLS 不可用 | **暂停 LAN 发布**，不自动退化为未经验证的自研加密协议 |
| 保险箱数据丢失 | 独立验证密钥与恢复流程，明确恢复码责任与临时明文边界 |
| 插件崩溃或越权 | v1 明确**完全信任模型**，不承诺进程内沙箱；宿主解析主体、不信任自填 actorId |
| 事件消费者增长 | 保持**显式组装**与单向依赖，不以消费者数量作为架构正确性判断依据 |
| 契约膨胀 | 新增接口必须有**独立职责与必要性**，不以行数或数量作为唯一标准 |

**v1 明确不承诺**：文件系统过滤驱动级拦截、全系统外部操作强制控制、进程内插件沙箱、
运行期间完全无明文的保险箱、自研 TLS 替代协议、NAT 穿透与公网直连。

**mDNS** 不纳入首版验收要求，但保留为后续可重新评估的设备发现方案。是否引入应根据
真实使用需求、依赖成本和目标环境测试决定。

## 9. 与既有文档的 Delta 汇总

| 既有结论 | 修订后的处理 |
|---|---|
| 物理身份与路径分离（重构方案 §3.6） | **保留**；进一步区分**进程内句柄 / 物理身份 / 文件版本** |
| 轻量事件分发，不做 EventBus（治理 §2.12） | **保留**；补充溢出、重复事件、消费者失败与恢复语义 |
| `FileIndex` 保持薄门面（重构方案 §2.2） | **保留**；M2/M3 是客户，不把传输与安全判定塞进 M1 |
| 文件操作统一入口 | **保留并细化**：网关负责授权与协调，**不包揽所有 I/O** |
| 四个跨模块契约 | **保留为当前目标集合**；允许经过论证的公开业务 API，**不机械冻结数量** |
| `sec_level` 与 `prov_id` 随 A3 一起加 | **分别评估**，不默认同时增加到索引表 |
| LAN 配对与传输 | **保留**手动地址与配对码的首版路径；mDNS 后续评估 |
| TLS 与应用层加密的退路 | **取消**"TLS 不可用时自动退化到自研加密"的方案 |
| 插件 API 能力模型 | **保留**能力模型；明确**完全信任**与**无进程内沙箱**的边界 |
| 保险箱 | **保留**静止态加密 v1；补全密钥、恢复码、nonce/AAD 与临时明文的安全语义 |
| 数据库 | **保留**独立数据库 + 统一迁移协调；补充**跨库恢复状态机** |
| 版本体系 | **不改变** `v0.4.x` / `v0.5.x` / `v0.6.0` 的既有定位 |
| GUIDE Phase 4 的 `init()/name()/shutdown()` 纯虚基类 | **替换**为 `IHostApi` + capability（纯虚基类没有权限面） |

## 10. 决策记录

v1 的四个待决问题已由评审拍板，结论如下（这是本文与 v1 最重要的差别）：

| # | 决策 | 结论 | 对方案的影响 |
|---|---|---|---|
| 1 | 统一文件操作边界 | **做，但网关只做授权与协调**；执行器独立，传输归 M2 | §0.2、§3.1、§3.2、§3.3 C3 全部重写；"唯一写文件处"的说法作废 |
| 2 | LAN 首版是否做 mDNS | **不做**，但**不永久禁止**，后续按需求评估 | §4.2、§6.1、§8 明确"不纳入首版验收" |
| 3 | 插件 v1 信任模型 | **接受完全信任（进程内）**，manifest/签名/capability **不是沙箱** | §4.4 补齐宿主 7 项职责；§3.4 第 7 条写明 capability 不是边界 |
| 4 | 保险箱 v1 的承诺 | **只承诺静止态加密**，且不承诺无法验证的擦除 | §4.3 补齐密钥/nonce/AAD/恢复码/临时明文/重加密六项语义 |

**仍待实现阶段验证的事项**（不是设计待决，是必须先测再定）：

1. **Qt TLS 后端是否可用**——这是 LAN 发布的**前置门槛**，不可验证就暂停（§4.2、§7）。
2. **`prov_id` 是否进索引库**——取决于来源关联的查询需求与性能实测（§4.1）。
3. **mDNS 的引入**——取决于真实设备发现体验与依赖成本（§8）。
4. **插件进程外化**——与 mDNS 无关的独立决策，不互相绑定（§4.4）。

## 附：一句话记住四模块的关系

> **M1 管"看得见"，M2 管"出得去进得来"，M3 管"准不准、该不该、要不要保护"，M4 管"谁来加功能"。**
> 四者共用一个身份（`FileRef`/`FileIdentity`）、一条受控流水线（授权 → 协调 → 执行 → 事件 → 消费者）、
> 一小组契约与批准过的公开 API。其余一切耦合都是设计失误。
