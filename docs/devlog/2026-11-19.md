# 2026-11-19 反向连接的第一步：让主机也有对方的地址

## 追加：对端别名自动读取（同日）

起因：用户「能不能自动读取对端的别名，而且我感觉现在互连操作有点麻烦，能不能优化一下」。

以前配对完，用户还得手动去对方界面上抄「别名」，再回自己这边一个字一个字填进同步范围——
两边写错一个字母就永远碰不上（各占一棵子树）。这次让协议把这件事说清楚：

- `SyncServer` 在认证成功的 `HelloAck` 里加 `roots:[{alias, name}]`（name 只取目录名，
  不泄露路径）
- `NetTransport::remoteRoots()` 收下；`SyncBridge::refreshRemoteRoots()` 在后台线程连一次，
  把结果变成一行摘要「对端开放：share（SyncHub）、docs（资料）」
- `alignAliasesToRemote()` 按**目录名**匹配（`QFileInfo(localPath).fileName()` vs 远端 `name`，
  大小写不敏感），同名才改别名——名字不同就不猜，避免把两个不相干的目录当成一个
- 配对成功时自动读 + 自动对齐（`m_alignAfterPairing`），用户一次都不用点；
  想手动重来，「同步范围」卡上还有「读取对端文件夹」和「对齐别名」两个按钮
- 顺带把配对码做成可复制（`复制配对码`，只在配对窗口开着时出现）

验证：`ctest -C Debug` 14/14（`net_transport` 新增 `remoteRootsExposeAliases`：
单根夹具下 alias 为空、name 为 `shared`）；`assistant_tests` 65 passed。

## 起因

用户连问三件事，都指向同一个根源：**连接是单向的**（连接方主动连主机）。

- 「为什么不是 p2p 模式，每个节点既是主机也是客户端」
- 「对端和主机连接之后，自动获取对端的 IP 地址」—— IP 确实早就拿到了
  （`conn.peer = socket->peerAddress().toString()`，认证失败限速就按它计数），
  但拿到 IP ≠ 能反连：TCP 里看到的端口是**出站临时源端口**，不是服务端口。
- 「主机向客户端的发送快点做啊」

上一轮只能用发件箱（`_outbox/`）暂存，等对方来取。这一轮补的是"能反连"所需的四块地基。

## 关键取舍

- **地址只在"它连过我"之后才有**。这是不需要中继的代价：谁先连谁，谁的地址就被记下来。
  两台都在 NAT 后面时仍然互相够不着 —— 那要靠 Tailscale / 端口映射，应用层解决不了。
- **反连的认证靠 devices 表**。主机连回客户端时，客户端要能回答"这个 deviceId 的口令对不对"，
  所以配对成功时**双方各写一条** `devices`；只写一边，反连会卡在 `AUTH_FAILED`。
- **`::ffff:127.0.0.1` 要先还原**。双栈监听时对端地址是 IPv4 映射形式，直接存进库里
  下次 `connectToHost` 会失败，所以落库前剥掉前缀。
- **自动监听**与手动按钮并存：端口被占用时 `netStatus` 会报出来，不影响其它功能。

## 还没做

## 对称发起 + 远端锁（同日追加）

### 起因

用户问「主机向客户机和客户机向主机都能实现吗」，核对后发现单文件投递双向都通，**目录同步只有连接方能发起**（`syncNow()` 在 `!hasPeerCredentials()` 时直接 return）。进一步核对暴露出更麻烦的一点：`NetTransport` 没实现 `tryLock`（沿用 `ITransport` 的恒真默认值），服务端也没处理已定义的 `Lock/LockAck` 帧 —— 也就是说**一旦放开双向发起，两端会同时对同一批文件读写**，收敛靠 mtime 大小，但会满目录冲突副本。用户选了「B：对称发起 + 锁仲裁」。

### 做了什么

| Task | 改动 | 测试 |
|---|---|---|
| 1 | `sync_state` 主键改 `(device_id, rel_path)`；四个基线 API 加 `deviceId` 尾参；旧表改名 `sync_state_legacy_<epoch>` 保留 | `baselineIsPerDevice` |
| 2 | `SyncEngine::setBaselineDevice()`，基线读写全带上 | `engineWritesBaselinePerDevice` |
| 3 | 服务端锁：`handleLock/handleUnlock/lockExpired/releaseLock`，TTL 120 s，Ping 续租，掉线即释放 | `lockIsExclusive` |
| 4 | `NetTransport::tryLock/unlock` 走真实帧，拿不到时 `lastError` 写明持有者 | `lockIsExclusiveOverWire` |
| 5 | `syncNow()` 按角色组 Round 列表：连接方连配置里的主机，主机反连每台有地址的设备，串行各跑一轮 | — |
| 6 | 计划勾选 + `CLAUDE.md` | — |

### 关键实现点

- **基线为什么必须按设备隔离**：基线是"上次同步后双方都认可的状态"。主机同时同步 A 和 B 时，一份基线会被两边交替覆盖，判定全乱；换设备跑一轮时 L 与 R 已经一致，所以正确行为是「只补基线、不重传」（UpdateBaseline 而不是 Upload）。
- **锁的语义**：拿到锁才有资格写。别人持锁回 `LockAck{ok:false, holder, retryAfterMs}`，调用方按 `retryAfterMs` 轮询、超时放弃 —— 不无限阻塞，也不会把「对方在同步」误报成网络故障。
- **掉线必须立刻释放**：`onDisconnected` 里判断 `m_lockSocket == socket` 就 `releaseLock()`。只靠 TTL 的话，持锁方崩溃会让对端白等 120 秒。
- **主机侧串行**：多台设备各自跑一轮，不复用连接 —— 简单、且天然避开"两台设备同时被同一主机写"。

### 踩坑

1. **`QString()` 默认参数是 null**，绑进 `NOT NULL` 列报约束失败（这是本项目第三次踩：`outbox.last_error`、`devices.last_error` 之后）。统一 `deviceId.isNull() ? "" : deviceId`。
2. **全局字符串替换误伤**：把 `q.addBindValue(deviceId)` 批量改成 `dev` 时，`device()`/`updateDeviceEndpoint()` 等函数里没有 `dev` 变量 → `error C2065`，按行号改回。
3. **`Sync::DeviceRecord` 不存在**：它在全局命名空间（`include/database/SyncDatabase.h`），`SyncBridge.cpp` 里要写 `DeviceRecord` 而不是 `Sync::DeviceRecord`。
4. **`SyncResult` 没有 `skipped` 字段**：汇总多轮结果时只能累加 `uploaded/downloaded/conflicts/deleted`。

### 验证

- 全目标 Debug 构建 exit 0；`ctest -C Debug` **14/14**
- `assistant_tests` **67 passed**；`assistant_net_server_tests` **14 passed**；`assistant_net_transport_tests` **11 passed**
- 提交：`d18b397` 基线隔离、`f526cb0` 引擎按设备基线、`59e1de3` 服务端锁、`894f89e` 客户端锁、`d91a91c` 主机反向发起

### 已知代价与未覆盖

1. **真正对称仍受网络限制**：两台都在 NAT 后且未组网时互相够不着（需要 Tailscale 这类工具）。
2. **锁泄漏**只能靠 TTL 兜底（120 s）；持锁方进程活着但卡在磁盘 IO 上时，对端会白等。
3. **设备多时串行慢**：每台一个 TLS 握手，5 台以上要几秒。
4. **地址过期**：DHCP 换了地址就是连接失败，目前只有一次性文案，没有自动重新发现。
5. **真机双实例走查仍未做**（本轮只有回环用例）。

## 追加：收取文件改领发件箱（同日）

### 起因

走查直发链路时发现 `SyncBridge::fetchIncoming()` 把「能领的远端路径」过滤成了 `_inbox/`，
而它自己算好的 `_outbox/<本机 deviceId>/`（局部变量 `boxPrefix`）从头到尾没被用过 ——
这是服务端直接落收件箱改造之前的写法。后果有两层：非监听状态的连接方点「收取文件」，
拉的是**主机自己的收件箱**；主机推不过去而暂存在 `_outbox/`、专门等它来取的文件反而永远取不走。

### 改动

- `src/ui/SyncBridge.cpp` 的 `fetchIncoming()`：过滤改用 `boxPrefix`；同时去掉「正在监听就早退」
  那一支 —— 早退的前提是主机能直推，但主机暂时够不着时（对端离线、地址过期）文件只进了
  发件箱，不点就永远到不了。主机侧（没有对端凭据）仍然早退，文案改为
  「你是主机：对端发来的文件会直接进收件箱，不用收取」
- `resources/qml/SyncPage.qml`：四处与现状矛盾的说明文字（"由连接方点立即同步"、
  "每轮同步会同时挂载直连通道"、"主机不主动连人"、`hostMode` 的注释）；
  删掉一块 `visible: false` 的重复收件箱行（注释还写着"等 B 阶段做完"）

### 验证

- Debug 增量编译：`SyncBridge.cpp` 与 QML 资源重编通过；`Assistant.exe` 链接被运行中的实例
  占用（`LNK1168`），需关掉应用后重链
- `ctest -C Debug` **14/14** 通过（19.6 s）
