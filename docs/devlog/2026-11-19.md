# 2026-11-19 文件索引：不再每次启动全量扫盘（24h + 空闲 + 目录 mtime 闸门）

## 起因

用户反馈："每一次启动仍要扫描全文件"。之前 A6a 的设计是"先把 DB 快照发布出去（立即可查），
随后后台校正"——**校正**这一步是无条件的：每次启动都 `FileScanner::scan(全部 roots)`
+ `loadAll()` 全表 + diff + 重建快照。磁盘一个字节没变也照做一遍。

2026-11-12 那次卡顿（UNC 的 stat 挂在 GUI 线程，见同日 devlog）修完之后，
"启动必扫"就变成纯浪费：它是后台线程，但抢磁盘、写 WAL、重建 6.5 MB 快照。

## 改法：三道闸门 + 一个"变了就全扫"

`FileIndex::startAsync()` → 冷启动发布缓存快照 → `scheduleAutoScan()`：

| 闸门 | 判定 | 不满足时 |
|---|---|---|
| **24h** | `roots.last_scan` 距今 < 24h | 直接结案（连 worker 都不起），并挂一个定时器在满 24h 时醒来 |
| **空闲** | `GetLastInputInfo` 空闲 ≥ 45s | 每 30s 重看；等了 15 分钟仍不空闲就跑（兜底，见 `kMaxScanDeferMs`） |
| **目录 mtime** | 逐目录 stat，与 `dirs.mtime` 比对 | 一条没变 → 只 stamp、不扫；有变化 → 走**完整全扫** |

前两道在 GUI 线程（`scheduleAutoScan`），第三道在 worker（`ScanWorker`）。
`rebuild()`（设置页「重建索引」）两道闸门都不看，强制全量。

### schema v3：`dirs.mtime`

`DatabaseMigrator` 加一步 `ALTER TABLE dirs ADD COLUMN mtime INTEGER NOT NULL DEFAULT 0`。
写入值是 **FILETIME tick（100ns）**，不是 Unix 秒——这条是被测试逼出来的（见"踩坑 2"）。
全扫时把这次**打开过的每个目录**（含空目录）都 stamp 一遍：只 stamp"有文件的目录"会让空目录
永远停在 0，下次必然判脏，闸门就白设了。为此 `FileScanner::Options` 新增可选输出
`visitedDirs`，扫到哪个目录就 append 哪个。

## 踩坑 1：把"脏目录"当扫描根，语义就变了（实测多出 13k 行）

第一版做的是"只重扫变了的子树"：`buildIncrementalPlan()` 找出脏目录，直接
`FileScanner::scan(脏目录列表)`，再把"干净目录的旧行 + 新扫的行"拼起来。

结果一台机器上 6679 行变成 **19596 行**。原因：脏目录被当作 scanner 的 **roots** 后，
丢掉了父级上下文——根目录不做"目录级排除名"判定、不做工程哨兵识别、不继承 demote 标记。
`Desktop/vcpkg`、`Documents/My Games/...` 这类本该被剪掉/降权的树被当根扫了进来。

**结论：增量不能改变"一条路径的上下文"。** `FileScanner` 的语义是"root 是用户显式指定的，
必须扫"，这个语义不能拿来当增量入口。所以改成：**mtime 只做闸门**——变了就整棵全扫，
不变就跳过。一天最多一次全扫，而且它在空闲窗口、后台线程里跑。

## 踩坑 2：目录 mtime 用"秒"会漏判同一秒内的增删

`dirMtimeSec()` 返回 Unix 秒、`dirs.mtime` 存秒。测试里"扫完立刻删一个文件再加一个"
落在同一秒 → 比对相等 → 判"没变" → 跳过 → 新文件搜不到。
真实场景同样会中（扫描刚结束、用户马上存一个文件）。改成存 **FILETIME tick** 后消失。

## 踩坑 3：测试把 `file_index.db` 放在被扫目录里

`kindFilterAppliesAtQueryTime` 断言 3 个文件，实际 6 个——多的三个是
`file_index.db` / `-wal` / `-shm`。以前扫描在 DB 建好之前就跑完了，看不出来；
现在校正延后触发，DB 必然已经存在，于是索引把自己的 WAL 当文件收了。
测试改成把 DB 放进另一个临时目录（生产路径本来就分居两处：DB 在
`%LOCALAPPDATA%`，根目录是用户文件夹）。

## 验收（真机，6679 文件 / 1062 目录）

| 场景 | 改动前 | 改动后 |
|---|---|---|
| 24h 内启动 | 每次都扫：200 ms 扫描 + 写库/快照，总计 ~950 ms | **0 次枚举**；启动到可搜索 **0.83 s**（冷启动 67 ms + 闸门判定） |
| 隔天启动、无变化 | 同上 | 1062 次 stat、**0 次枚举**，判定 **~107 ms**；总 1.84 s |
| 隔天启动、有新文件 | 同上 | 检出"目录变动 1 处"→ 全扫 197 ms，新文件入库（6700 → 6701） |
| 设置页「重建索引」 | 不存在 | 强制全量，不看闸门 |

自动化：`assistant_index_tests` **9 passed**（新增 `dirMtimesAreStamped` /
`skipsRescanWithinADay` / `unchangedTreeSkipsScanAfterDay`），`ctest` 15/16
（唯一红灯仍是既有的 `net_tls`）。`a3_migrate` 的断言从 `user_version == 2` 改成 `== 3`
并新增 `dirs.mtime` 存在性检查。

## 仍然开着的

- `USN Journal` 才是终局（按变更日志增量，连 stat 都省），但它要卷句柄（通常管理员）、
  只支持 NTFS、FAT/网络盘要 fallback —— 仍在 `C2c/C8` 待办里。
- 「原地修改但不改父目录 mtime」的文件，size/mtime 会保持旧值直到下次 24h 全扫；
  搜索结果仍在，只是元数据偏旧（frecency 做起来后这里会更明显）。
- 进程内每日定时器只在 `startAsync` 之后挂；如果进程活过 24h 会自己醒一次（12h 上限兜底）。
