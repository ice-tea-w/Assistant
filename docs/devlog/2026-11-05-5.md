# 2026-11-05（五）N2：`devices` 表、`SyncServer`、`NetTransport` 与引擎回环

## 起因

N1 收在"回环 TLS 能握手、挑战应答能验过"，但那还只是协议自测：没有人真的按
`ITransport` 的接口收发文件。N2 要证明的是**引擎一行不改就能跑在直连通道上**。

## 关键实现点

- **`QSslServer` 的 pending 队列是空的**。它的 `incomingConnection` 先把 socket 记进
  内部 `socketData`，要等收到首字节 `0x16`（ClientHello）才 `startServerEncryption()`，
  `encrypted` 之后才 `addPendingConnection`。所以 `nextPendingConnection()` 永远拿不到东西，
  表现为"客户端等到 Challenge 超时"。改成自写 `TlsAcceptor : QTcpServer`：收到 fd 就
  `setSocketDescriptor` + 连 `encrypted` + `startServerEncryption()`。
- **`resolveUnder` 要求父目录已存在**（它要解引用 junction 才能复核前缀）。收文件时
  目标子目录往往还没建 → `mkpath("")` → `MKDIR_FAILED`。但也不能先裸 `mkpath` 再检查：
  共享根里被塞一个指向 `C:\Windows` 的 junction，就会在外部建目录。新增
  `PathGuard::ensureDirUnder()`：逐段推进，每推进一级都解引用并复核仍在根下。
- **客户端 `push` 要边发边看错误**。服务端在 `Put` 阶段就会拒（目录建不出来 / 路径不安全），
  客户端如果照旧灌完所有块，对端会对每块回一条 `NO_PUT`，这些应答留在流里，
  下一个文件的 `PutAck` 就会读到上一个文件的错误 —— 症状是"第一个文件失败，后面全失败"。
  现在每块之后看一次 `bytesAvailable()`，收尾读 `PutAck` 时也按 `reqId` 过滤。
- **阻塞式客户端必须配独立线程的服务端**。`test_net_server.cpp` 里两边同线程，只能靠
  `processEvents` 泵事件；`NetTransport` 是 `waitFor*` 的，同线程就互等死锁。
  `test_net_transport.cpp` / `test_net_engine.cpp` 因此把服务端放进带 `exec()` 的 `QThread`。
- 别名对齐照旧：`relPath = <别名>/<相对路径>`，服务端只是把它当普通相对路径落盘，
  所以"多本地文件夹"在直连下不改一行。

## 验证

- `cmake --build build --config Debug`：`BUILD_EXIT=0`。
- `ctest --test-dir build -C Debug`：**14/14 Passed**（新增 `net_transport` 0.63 s、
  `net_engine` 0.37 s）。
- `assistant_tests.exe`：**62 passed, 0 failed**（原 61，加 PathGuard 那条）。
- 引擎回环实测日志：首轮 `上传=2`，次轮 `上传=0 下载=0`，对端新增文件后 `下载=1`。
