# 2026-11-12 · Phase B 功能一：种类过滤 + 工程排除 + 查询语法

按 `docs/architecture/文件治理功能设计.md` §1 落地文件治理的第一阶段。四个层次全部接进产品路径：

| 层 | 内容 | 实现 |
|---|---|---|
| L2 采集过滤 | 目录名 / 文件通配 / 大小 / **工程哨兵** | `ExcludeRuleSet` + `FileScanner` |
| L3 文件归类 | 扩展名 → 16 位 `catMask` | `FileClassifier` + `FileKind` |

## 三个设计取舍

### 1. 工程哨兵用“前瞻缓冲”，不是“先枚举整目录”

句柄栈是**流式**的：进入子目录时还没有它的清单，而“整棵跳过”必须在读第一条子项之前决定
（否则 DFS 前序与截断集合都会变）。做法是打开子目录时先读最多 **256 条**进缓冲：

- 命中哨兵 → `skip` 直接丢弃整棵；`demote` 给子树打 `FileFlags::Project` 并剪掉 `build/out/bin/...`；
- 没命中 → 缓冲就是正常待处理条目，继续流式读，**顺序与之前逐条相同、不额外 stat**。

超过 256 条才出现哨兵的项目根会漏判（现实中不存在；可按需调大窗口）。
这偏离了设计稿“一次目录枚举顺带判定、零额外 syscall”的写法 —— 那是“先枚举整目录再下探”的
模型，与我们为保持 golden 顺序而选的句柄栈不兼容。

### 2. 默认剪枝名单保持 5 个，`build/bin/out` 只在工程子树里剪

设计稿的 `exclude.dirNames` 默认值含 `build / out / target / bin / obj / dist / .vs`。
直接全局剪会把用户自己的 `Downloads/bin` 这类普通文件夹误剪。现在：

- 全局默认仍是 `node_modules / __pycache__ / .cache / .git / .svn`（与 A1–A4 行为一致）；
- `build/out/target/bin/obj/dist/.vs/DerivedData` 只在 `projectPolicy=demote` 的**工程子树内部**剪。

### 3. 白名单切换：收窄走快路径，放宽回 DB

- 收窄（`all → whitelist`、白名单变小、黑名单变大）：在现有快照上再筛一遍，33k 条 <10 ms；
- 放宽：被筛掉的条目已经不在快照里，必须 `reloadFromDatabase()`。

**没达标的地方**：33k 行从 DB 重建仍要 ~250 ms（冷启动实测 251 ms），设计稿目标是 <50 ms。
瓶颈是 `loadAll()` 每行两次 QString 分配，和 A6b 是同一个问题；等 A6b 的列式载入一起解。

# B 收尾（同日）：白名单改为查询期过滤 + 设置页 UI

## 1. 为什么改白名单的落点

初版按设计稿在**建快照时**筛白名单：收窄 <10 ms，但放宽必须从 DB 重建 —— 33k 行
`loadAll()` 实测约 250 ms，达不到验收口径“切换 <50 ms”。改成**查询期过滤**：

- 快照永远保存采集面全量；
- `QueryEngine::query(raw, limit, kindFilter)` 逐行先判
  `KindFilter::acceptsLower(catMask, nameLower)`（一条 `&`；白名单的额外扩展名用
  `QStringView` 比较，零分配）；
- `FileIndex::setKindFilter()` 只赋值 + 发信号，实测 **<1 ms**，0 次重建、0 次读盘。

代价：白名单模式不再节省快照内存（和“全部”一样大）。这是有意的取舍 —— 200k 快照
64 MB 本来就是 A6b 要解决的问题，不能靠“过滤后变小”掩盖；而“切换立即生效”是 B 的验收项。

## 2. 设置页 UI

`SettingsPage` 增加「文件索引范围」：

- 种类过滤：全部 / 只保留 / 排除 + 16 个种类复选；
- 「应用白名单」→ `ConfigManager::setFileKindFilter` → 信号 → `FileIndex::setKindFilter`，
  立即生效；
- 工程目录：跳过 / 降权 / 如实入库 → `setFileProjectPolicy` → main.cpp 里
  `setExcludeRules` + `refresh()`（采集规则必须重扫，后台线程）；
- 设置页内容超窗口高度，包了一层 `Flickable`，否则新增区块会被裁掉。

实测截图：白名单模式正确勾选「文档 / 图片」，工程目录显示“入库但降权 30%”。

## 3. 验收数据（真机，同一份用户目录）

| 策略 | 文件数 | 扫描耗时 | 说明 |
|---|---|---|---|
| `skip`（默认） | 6674 | 341–650 ms | 9 个工程根整棵跳过 |
| `demote` | 33094 | 1.4–2.7 s | 372 个工程子树入库，剪掉 666 个构建/噪音目录 |
| `index` | 33118 | 1074 ms | 全部入库（构建目录也进） |

白名单切换：`setKindFilter` <1 ms；查询结果立即受限于 doc/img —— 截图验证输入 `:all`
只返回 `.md` / `.png` / `.tex` 等文档与图片。

## 4. 测试

`kindFilterAppliesAtQueryTime` 改为断言“**快照条目不变、查询结果变化**”，并覆盖
`extraExtensions` 放行；新增 `configPersistsGovernanceSettings`（`QStandardPaths` test mode，
验证设置页写入的 mode/kinds/projectPolicy 能重新读回）。`ctest` **8/8**。

# Phase C（S9）：下载收件箱骨架

按 `文件治理功能设计.md` §2 落地 **Download Box 骨架**。本阶段**不做去向追踪**（D）、
不做归档规则/查重/IM 源（E）；目标只是把「下载 → 完成判定 → 拉入 box → 用户看到」
这条闭环真正跑通。

## 新增模块

| 文件 | 作用 |
|---|---|
| `include/core/FileIdentity.h` + `.cpp` | 物理身份 `(volumeSerial, FileId)`、`quickSig = Sha256(size‖首64K‖尾64K)`、独占打开检测（条件 C） |
| `include/database/DownloadsDatabase.h` + `.cpp` | 独立 `downloads.db`（连接名 `downloads`，**权威数据**）；`downloads` 双状态 + `move_journal` + `tracking_events` + `download_rules` + `sources` + `app_meta`，走 `DatabaseMigrator` v1 |
| `include/core/inbox/IDownloadSource.h` | 源适配器接口（目录、临时后缀、静默期）；Phase C 只有 `BrowserSource` |
| `include/ui/InboxBridge.h` + `.cpp` | 「最近下载」页的桥：列表 / 打开 / 定位 / 撤销 |
| `resources/qml/RecentDownloadsPage.qml` | 待整理 / 已移出 / 全部 三档 + 文件列表 + 每行动作 |
| `tests/test_downloads.cpp` | 10 个用例（身份、DB、`:dl`、接管/撤销、临时后缀、同名、对账） |

## 管线（IngestEngine）

```
FileWatcher（全部索引根，与 FileIndex 共用 dispatcher）
  → 只取 Downloads 根下的事件 → candidate（路径/大小/mtime/首次见到）
  → 300 ms tick：
      A 临时后缀（.crdownload/.part/...）→ 永不接管
      B size+mtime 连续未变且 ≥ settleMs
      C CreateFileW(share=0)：失败按 1/2/5/10/30 s 退避；5 次后按 A+B 结论接收
  → MoveFileExW(src, box\name)（同名自动 "(1)"，跨卷前查剩余空间）
  → 登记 FileId + quickSig + catMask + 双状态（pipe_state=InBox / track_state=InBox）
  → journal intent → done；托盘通知 + 「最近下载」刷新
```

**撤销**：`undo(id)` 把文件从 box 移回原下载目录（同名加 `(n)`），journal 记
`op=undo`，双状态改为 `Undone / Unknown`。撤销只影响我方动作，用户自己的移动不在此列。

**启动双对账**（`start()` 里做，独立于 enabled）：
1. `move_journal` 里 `op_state='intent'` 的 fetch/undo：目标存在且 size 匹配 → 补完；否则标
   `Failed` 并保留源文件；
2. `in_box=1` 但 box 里找不到的文件 → `track_state=Unknown`、`in_box=0`
   （Phase C 没有追踪能力，**不猜位置**）。

## 三个取舍

### 1. 默认关闭，必须用户显式开启

`inbox.enabled` 默认 **false**：这套功能会移动用户文件，不能默认替用户做决定。设置页加
「下载接管」开关；开启后**只接管开启之后新产生的下载**（不扫历史 Downloads 目录）。
开关变化即时生效（引擎不重建）。

### 2. 收件箱是索引根之一，`:dl` 走路径段

box 目录（默认 `%LOCALAPPDATA%/AssistantTeam/Assistant/Inbox`）被加进 `FileIndex` 的 roots，
接管完成立刻可搜到。`QueryParser` 加了 `:dl` / `in:box` → 路径段 `inbox`。
**已知限制**：用户把 box 改成别的名字后 `:dl` 不再命中（Phase D 会改成按 DB 来源过滤）。

### 3. 移动是同步的（已知限制）

`MoveFileExW` 在 GUI 线程执行。Downloads 与 box 同卷时只是 rename（微秒级）；跨卷大文件会
阻塞界面数秒。设计稿要求独立 `QThread`，本阶段先保证正确性（journal + 对账），线程化留到
D 阶段与 TrackingEngine 一起做。

# Phase D（S10）：去向追踪

补齐「用户把文件移出 box 后，记录能指到它现在的位置」。新增 `TrackingEngine`
（`include/core/inbox/TrackingEngine.h`）。

## 关联规则

| 场景 | 判据 | 结论 |
|---|---|---|
| 同卷移动 / 改名 | `volumeSerial + FileId` 相等，且 size/mtime 一致 | `method=watcher-frn`，`confidence=exact` |
| 跨卷移动（复制 + 删源） | size/mtime 相等 → 算 `quickSig` → 相等且**唯一** | `method=watcher-sig`，`confidence=strong` |
| 多个候选 / 0 个候选 | 不选 | 窗口到期 → `Unknown`，`tracking_events` 记 `to=NULL` |
| 别处复制（原件仍在 box） | box 没有 Removed 事件 | 不追踪、不删任何东西 |
| box 内改名 | 新路径仍在 box | 只更新 `box_path`，不进入追踪 |
| 多级移动 | `FiledAway` 的 `cur_path` 再次被移走 | 重新开窗口，`tracking_events` 追加一条链 |
| 关机期间移动 | box 内 `FileId` 对账（级别 0）→ `(size,mtime)` + `quickSig` 反查（级别 1） | `startup-rescan`；仍不唯一 → `Unknown` |

配置：`inbox.tracking.windowSec`（默认 60 s）、`inbox.tracking.extraWatchDirs`
（只监听、不索引的归档目录，已接进 `FileWatcher` 的监听根）。`InboxBridge` 的
「已移出」现在会显示真实路径，状态文案区分「已归档 / 已移出（位置未知）」。

## 一个被冒烟抓到的顺序 bug

最初启动顺序是 `fileWatcher.start()` 在 `ingest.start()` 之前。此时收件箱目录还不存在，
`FileWatcher` 跳过了这个根（日志：`watching 6 root(s)` 而不是 7），
于是「文件移出 box」永远不会触发追踪。修正为：

```
ingest.start()（建 box + 对账） → fileIndex.startAsync() → fileWatcher.start() → tracking.start()
```

冒烟复测：`watching 7 root(s)`；把接管后的文件从 Inbox 移到 `Documents\...`，
日志出现 `TrackingEngine: … → …（watcher-frn / exact）`。

## 验收

| 项 | 结果 |
|---|---|
| `assistant_inbox_tests` | **16/16**（新增：实时 FileId 命中、超时 Unknown、复制不误报、二级移动链、离线级别 0 改名、离线级别 1 反查） |
| `ctest` | **9/9** |
| 真机冒烟 | 接管 → 移到 Documents → 1 秒内 `FiledAway` + 新路径；`tracking_events` 一条 `exact` |

## 没做 / 已知限制

- 离线**级别 2**（移动后又编辑，用“原文件名 + FileId”反查）与 USN Journal 未做；
  这类情况直接落 `Unknown`。
- 跨卷「复制+删源」的 `strong` 路径有代码但**没有真实跨卷 e2e**（测试环境只有 C: 临时目录）；
  逻辑由纯规则 + `quickSig` 单元测试覆盖，仍需要在真机 C:→D: 上补一次。
- `Unknown` 的 UI 出口（在整个索引里搜 / 手动指定位置 / 标记删除）未做。
- 追踪窗口固定从配置读取，运行中改配置需重启（`extraWatchDirs` 需要重建 watcher）。

# Phase E（S11 核心）：归档规则 / 查重 / Todo·剪贴板联动

按 `文件治理功能设计.md` §2.8–§2.10 落地了 S11 的**规则、查重与两个既有功能联动**；
IM 源适配器（QQ/微信/钉钉）仍未做。

## 1. 归档规则（`DownloadRules`）

- 配置 `inbox.rules`：`{ name, priority, enabled, kind, size, action, dest }`；
- 匹配：`kind`（`:kind` 同类 token，逗号分隔）+ `size`（`>500mb` / `<1k` / `1mb..10mb`）；
- **priority 升序、首个命中即止**（first-match-wins）；
- 动作：
  - `suggest`（默认）：只写 `suggest_dest` + `rule_name`，UI 显示「建议归档」；
  - `move`：仅当 `inbox.autoOrganize = true` 时自动移动；
  - `skip`：**完全不接管**（文件留在 Downloads，用于“安装包别动”）；
  - `notify`：只给建议（与 suggest 同路径，通知留到后续）。
- 模板：`{inbox} {name} {ext} {kind} {yyyy} {MM} {dd} {source}`；
- `downloads.db` 迁移 **v2**：加 `suggest_dest` / `rule_name`（只加列，不重建）。

## 2. 查重

入 box 后按 `quickSig` 查更早记录 → 写 `dup_of`；UI 状态显示「待整理（重复）」。
**只标记、不自动删除**：裁决（保留新的/旧的/都留）仍留给人；`fullSig` 仍只在需要裁决时才应计算。

## 3. 与 Todo / 剪贴板联动

「最近下载」每行的 `⋯` 菜单新增：

- **归档到建议位置** → `IngestEngine::archive()`（journal `op=organize`，不覆盖同名）；
- **加入待办** → `TodoDatabase::addTodo(路径)`；
- **复制内容** → ≤1MB 且非二进制才读入系统剪贴板 + `ClipboardDatabase`；
- **复制路径**。

# C2b 补充：离线级别 2 + Unknown 手动出口

补上 S10 的两个已知缺口：

1. **离线级别 2**（移动后又编辑）：级别 1 `(size,mtime)+quickSig` 失效时，改按
   **原文件名** 在索引里找候选（`FileIndex::pathsByName`），再取 `FileId` 与登记指纹比对
   （同卷移动 FileId 不变）。唯一命中 → `FiledAway / exact`；仍不唯一 → `Unknown`。
2. **Unknown 的手动出口**：
   - `TrackingEngine::relocate(id)` 对单条记录重跑级别 1/2（方法记 `manual-rescan`）；
   - 「最近下载」`⋯` 菜单新增「重新定位（索引反查）」与「标记为已删除」；
   - “已删除”只改记录（`track_state=Deleted`），**不碰磁盘**，也不自动判定。

**仍缺**：USN Journal；`Unknown` 的“手动指定位置”文件选择器（现在只能重跑索引反查，

# S11 安全出口：归档撤销 + 查重裁决

不做危险删除，只补“可反悔”：

1. **撤销归档**（`IngestEngine::unarchive`）：
   - 只撤销**本应用**的归档 —— journal 里最后一次 `organize` 必须 `done`，且 `to_path`
     仍是当前 `cur_path`；
   - 用户自己从 box 移走的（没有 organize）明确拒绝，不抢 TrackingEngine 的判断；
   - 文件移回 box（同名自动 `(n)`），记录恢复 `InBox`。
2. **查重裁决（最小版）**：
   - `⋯` 菜单「打开重复的原件」→ 定位更早的那条；
   - 「保留两份（清除重复标记）」→ `dup_of=0`；
   - **没有“删除”按钮**：设计里删除走回收站，但当前不做自动/一键删除。

测试仍为 `assistant_inbox_tests` **23/23**（归档后撤销回到 InBox、`dup_of` 清零）；`ctest` 9/9。

**仍缺**：规则编辑器/dry-run、`fullSig` 裁决与“删除到回收站”入口、IM 源。

# S11 收尾：规则编辑器 + dry-run

规则不再是只能手改 `config.json`：

- `ConfigManager` 新增可写接口：`inboxAutoOrganize`（Q_PROPERTY WRITE）、
  `setInboxRules(QVariantList)` + `inboxRulesChanged`；保存后主程序立即
  `DownloadRules::load` 到 `IngestEngine`，**无需重启**。
- 设置页新增「下载归档规则」：
  - 自动归档开关（默认关，只给建议）；
  - 规则行可编辑：名称 / 种类 / 大小 / action（suggest/move/skip/notify）/ 去向模板；
  - 添加、删除、保存；
  - **预览（dry-run）**：把当前收件箱记录交给 `InboxBridge::previewRules()`，
    只返回 `名字 → 规则 / action / 去向`，**不入库、不移动**。
- QML 里 ComboBox 的 `model`/`index` 会遮住 delegate 角色，因此规则 delegate 用
  `ruleDelegate.rowIndex` + 直接角色名（`action`）访问，避免“保存错行”。

验收：真机设置页能看到已配置的 `docs` 规则（名称/种类/size/action/去向齐全），
无 QML 报错；`assistant_inbox_tests` 23/23、`ctest` 9/9（dry-run 复用已测的
`DownloadRules::evaluate`）。

**仍缺**：`fullSig` 裁决与“删除到回收站”、IM 源适配器。
