## 二、四个值得单独记下的设计决定

### 1. 用**句柄栈**而不是目录栈

实施清单 §3.2 的伪码是「stack = roots；pop 一个目录；枚举；子目录 push」——那是目录栈，
遍历顺序会变成「反序的广度优先」。听起来无所谓，但 A2 的 golden 对比是靠**同一个 2 万条上限**
把 v2 与旧引擎放在同一候选集上的：**上限是按顺序截的，顺序一变截出来的集合就变了**，
A2 的验收会当场失真（而且看起来会像是"查询语义回归"，很容易查错方向）。

所以每层目录保留自己的 `HANDLE`，遍历顺序与 A1 的递归 DFS**逐条相同**。
代价是同时打开 N 个句柄（N = 路径深度，实测几十个，无所谓）。

实测回报：换成 Win32 扫描后 `assistant_golden --n=20000 --real` 仍然 **72 项检查 0 失败**，
100 条真实查询与旧引擎逐条一致。

### 2. 数据库连接在 worker 线程里开、在 worker 线程里关

`QSqlDatabase` 的连接**线程亲和**。如果门面在 GUI 线程 `open()`、worker 线程写，Qt 会报
"requested database does not belong to the calling thread"。所以 `FileIndexDatabase` 是
`run()` 里的**局部对象**：同一线程建、同一线程销毁，差量写库全程不碰 GUI 线程（§3.4）。

代价：门面没有 `m_database` 成员（§2.2 的示意图里是有的），只有 `m_databasePath`。
这是**有意的偏差**——A6 的「冷启动先载入 DB」会另开一条 GUI 线程自己的连接（WAL 支持多连接并发读），
那时才会出现第二个 `FileIndexDatabase` 实例。

### 3. 迁移框架在 A3 就要真跑一遍

`file_index.db` 的 schema：**v1** = §3.5 三张表 + 两个索引；**v2** = 治理字段增补
（`cat_mask` / `flags` / `root_id` / `origin_id`）+ `idx_files_sizemtime`。
所以一个全新的库也要走 `0 → v1（建表）→ v2（加列）`，而不是"建表时顺手带上所有列"——
§3.6 要求迁移是打开库后的**第一个动作**，不能"用到哪个表再顺手建"。

验收③就是拿一个只有 v1 的库（含 100 行数据）跑一遍，确认加列成功、行数不变、旧数据完好。

### 4. `\\?\` 只用在遍历里

扫描期用 `\\?\` 长路径形式（Win32 只对带前缀的路径解除 `MAX_PATH`）；但交给上层（快照 / DB）的
是**普通形式 + `/` 分隔**。否则 `QUrl::fromLocalFile` / `QDesktopServices` 和既有 QML
都得跟着改，而且 DB 里的路径会变成 `\\?\C:\...`，以后谁都认不出来。

## 三、验收（四条全过，均为实测）

### ① 全量扫描吞吐

```
real       files=31845   dirs=5574   pruned=665  denied=0  ms=472   67468 files/s
           外推 20 万条 ≈ 2964 ms（按本机实测吞吐折算，不是实测值）
```

对照 A2 的旧扫描器（`QDir` 递归，同一棵树）：**20000 条要 976–1047 ms**，
`FileScanner` 扫 **31845 条只要 459–502 ms** —— 每文件约 **3 倍**快，
而且这次是**扫全了**（不再有 2 万上限）。

> 20 万条是外推值，不是实测值。要真测就 `assistant_a3 --bench=200000`（会先造 20 万个文件再扫再删）。

### ② 工程目录剪枝

```
不剪枝：1330 个文件（期望 1330），12 个目录
剪枝后：30 个文件（期望 30），剪掉 2 棵子树，下降 97.7%
```

（合成工程：`src` 20 + `docs` 10 + `node_modules` 5 包 × 200 + `.git/objects` 300）

断言四条：只剩非工程目录的文件、下降 ≥95%、剪枝计数 ≥2、结果里**没有任何** `node_modules` / `.git` 条目。
"不剪枝 1330 条"那行是**基线对照**——没有它，"下降 97.7%"只是个算出来的百分比。

### ③ 迁移：v1 → v2

```
DatabaseMigrator[file_index]: → v2（加 cat_mask/flags/root_id/origin_id + idx_files_sizemtime）
FileIndexDatabase: opened …assistant-a3-migrate.db (100 rows)
==== PASS：14 项检查，0 项失败 ====
```

14 项包括：`user_version == 2`、四个新列都在、`frecency` 等原有列**没被重建掉**、
`idx_files_sizemtime` 存在、行数仍是 100、`C:/seed/file_7.dat` 的 size 仍是 107、
新列默认值是 0 而不是 NULL。

### ④ 差集收敛（两次**独立进程**）

```

run 2:  SYNC … db_rows_before=2000  added=0    changed=0 removed=0 unchanged=2000 write_ms=0   db_rows_after=2000
```

真机上的同一件事（跑两次应用，看日志）：

## 四、本次新踩的坑

1. **`QString::arg` 不是 `printf`。** 我写了 `QStringLiteral("…≥95%%（实际 %.1f%%）")
   .arg(x)` —— 结果是运行期一条 `QString::arg: Argument missing`，**不崩**，
   而且 `%%` 原样留在界面上。`arg` 只认 `%1` / `%2`，`%%` 和 `%.1f` 都是 printf 的语法。
2. **`removeDatabase` 时 `QSqlQuery` 还活着** —— `connection 'a3_verify' is still in use`。
   这是 Phase 3 那条"先 delete m_db 再 removeDatabase"老坑的变体：光 destory `QSqlDatabase`
   不够，**查询对象也必须先析构**（我把 `removeDatabase` 挪到块外，靠块作用域析构）。
3. **`[[nodiscard]]` 的 `QFile::open` / `write` 忽略返回值** → MSVC `C4834`。
   写文件的地方统一收成一个 `writeFile()` 小函数（顺带能回报"到底写没写成功"）。
4. **首次建库是一次性的 2.2 s 写盘**（31845 行，单线程 + 每 1000 条一批）。
   它在 worker 线程上，所以 UI 不卡；但会**推迟快照发布**（2.77 s 才有文件结果），
   而且会跟启动期的 QML 加载抢 CPU/磁盘（首次启动 UI 加载 3.6 s，第二次 0.7 s）。
   不在 A3 修 —— A6 的"先载入 DB 立即可查、再后台校正"正是为这个设计的。
