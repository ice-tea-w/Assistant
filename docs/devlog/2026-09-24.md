# 2026-09-24 v0.4.0 Phase A / A1 止血（独立 patch）

## 一、A1 做了什么

按 `docs/architecture/v0.4-实施清单.md` 的 A1 条目，修四个已确认的缺陷。**旧 `FileSearcher`
的接口与语义都没动**，只换实现；`search_history` 旧数据按既定决定清空。

| 缺陷 | 原计划做法 | **实际做法** | 结论 |
|---|---|---|---|
| P0-1 跟随 reparse point | `QDirIterator` 加 `QDir::NoSymLinks` | **改不了，见下**：改成自己控制递归 + `isSymLink() \|\| isJunction()` | 计划的写法**无效**，已换成正确实现 |
| P0-2 热路径字符串分配 | 删掉 `QDir::toNativeSeparators()` | 目录级剪枝：命中段名直接不进子树 | 比计划更好（真的剪枝了） |
| P1-5 搜索写库时机 | 从 `search()` 挪到 `executeCommand()` | 同 | 完成 |
| P1-6 输入防抖 + IME | QML `Timer` + `inputMethodComposing` | 同 | 完成 |

### P0-1：原计划的做法是错的（本次最重要的发现）

`QDir::NoSymLinks` **挡不住 Windows junction**：

1. Qt 的 `QFileInfo::isSymLink()` 只认 `IO_REPARSE_TAG_SYMLINK`，junction 是
   `IO_REPARSE_TAG_MOUNT_POINT`——Qt 6.2 为此专门补了 `QFileInfo::isJunction()`。
2. `QDirIterator` 的过滤器只决定"哪些条目被返回"，**不决定"是否递归进去"**，
   所以即使能识别 junction 也无从阻止下探。

实测（Desktop 放一个指回父目录的 junction，把索引全部 dump 出来对着看）：

| | 加 `NoSymLinks` 后 | 改成自己的递归后 |
|---|---|---|
| 含 `/loop/` 的索引条目 | **126** | **0** |
| 探针文件条目数 | 128（同一文件重复收 63 遍） | 2 |
| 最长索引路径 | 63 层 `loop/` 拼接 | 正常 |

教训已单独记到 `docs/troubleshooting/qt-nosymlinks-挡不住junction.md`：
**修复点选错层次（过滤器 vs 递归控制）时，它会安静地什么都不做**——编译通过、
日志正常、看起来更好了，只有 dump 出索引才发现没生效。

### 实现：`walkDir()` 前序 DFS

`QDir::entryInfoList(..., QDir::NoSort)` 逐目录枚举 + 自己递归。选前序 DFS 是为了
与旧 `QDirIterator` 的枚举顺序一致 —— 本机索引在 20000 就截断了，顺序变了截断结果就变，
A2 的 "legacy 行为一致" 验收会跟着失真。

## 二、验收（三条全部实测，不是推演）

| # | 验收项 | 方法 | 结果 |
|---|---|---|---|
| ① | junction 不递归、不重复索引 | 临时 env 门控仪器把索引全路径落盘 + grep | ✅ `/loop/` 路径 126 → **0**；探针文件恰好 2 条 |
| ② | 连打 8 字符只触发 1 次 `search` | `PostMessage` 投 `WM_CHAR` ×8 给浮窗，debug 日志统计 | ✅ 只出现 **1 行** `AppBridge::search 'abcdefgh'`（不是 8 行前缀） |
| ③ | 打字过程中 `history.db` 不新增行 | 打字前/后各查一次 `count(*)` | ✅ 43 → **43** 不变 |
| ③+ | 正向对照：执行时才写 | 输 `1+2` 后按 Enter（计算器结果恒排第一，副作用只有写剪贴板） | ✅ 43 → **44**，新增行 `query='1+2'` |

②③ 的探针脚本在 `out/`（已 gitignore）。手法：`PostMessage` 投
`WM_HOTKEY`(id=1000) 显示浮窗、`WM_CHAR` 打字、`WM_KEYDOWN VK_RETURN` 回车——
走 Qt 真实消息链，不注入代码、不改被测程序。

### 顺带发现的两个事实

1. **索引一直被 20000 上限吃满，且只覆盖 Desktop。** 本机 Desktop 有 **35607** 个文件，
   而 Desktop 是 `roots` 的第一个，所以 `Documents`(1652) / `Downloads`(596) /
   `Pictures`(324) 等**一个文件都没进索引**——用户搜不到自己文档里的东西。
   日志证据：`FileSearcher: index capped at 20000 files`。
   这是 P0-3（按遍历顺序任意截断），**不在 A1 范围**（实施清单明确写了"上限策略调整留给 A3"），
   但它意味着 A3 的优先级应该比原计划更高。
2. **`pruned 160 excluded dir(s)`**：Desktop 下有 160 个 `node_modules`/`.git` 之类的目录
   被整棵剪掉——P0-2 从这个角度看比"省几次字符串分配"重要得多。

## 四、环境/踩坑（本次新踩的）

1. **强杀进程会丢 debug 日志。** spdlog `flush_on(info)` 只保证 info 及以上立刻落盘，
   debug 行留在缓冲里；`Stop-Process -Force` 一杀就没了，看起来像"日志没打"。
   探针改成 `PostThreadMessage(WM_QUIT)` 优雅退出（事件循环正常返回 → 静态析构刷盘）后才读到。
2. **Windows PowerShell 5.1 按 ANSI 读 `.ps1`。** 带中文注释的脚本被写工具以 UTF-8 无 BOM
   存盘 → PS 把中文字节当 GBK 解 → **语法直接崩**（报"字符串缺少终止符"这种误导性错误）。
   脚本必须存成 **UTF-8 with BOM**。同理写 `config.json` 要用 `[System.IO.File]::WriteAllText`
   + `UTF8Encoding($false)`，不能让 PS 加 BOM。
3. `%LOCALAPPDATA%` 与 Desktop 都在工作区之外，**验收环节同样需要 `danger-full-access`**
   （编译在增量情况下 `workspace-write` 能过，但只要触碰用户目录就不行）。
