## A5（第一半）：事件源

按 `v0.4-实施清单.md` §A5 落地了"事件从哪来"，但**还没接进 `FileIndex`**（见文末）。

### 新增

| 文件 | 作用 |
|---|---|
| `include/contract/FileSystemEvent.h` | C2 契约：`Added / Removed / Renamed / Modified / Overflow` |
| `include/core/FileWatcher.h` + `.cpp` | 每根一个句柄、递归子树、合并去重、溢出上报 |
| `include/core/FileEventDispatcher.h` + `.cpp` | 极轻量的订阅表（不是全局 EventBus） |
| `tests/test_file_watcher.cpp` | 8 个用例：增/删/改名/修改/合并去重/订阅表/异常隔离 |

### 三个设计决定

**1. 第一次 `ReadDirectoryChangesW` 在 `start()` 里就发出去（OVERLAPPED）。**
最初用阻塞式 read + 线程里开句柄，测试里"start 之后立刻创建文件"会稳定丢事件——
线程还没跑到第一次 read。改成 `FILE_FLAG_OVERLAPPED` + 事件对象，`start()` 返回时监听已经生效，
根因消除。这也是唯一能诚实满足"≤100 ms 可见"的前提。

**2. 合并规则不是"最后一条获胜"。**

新建文件在 Windows 上会连发 `ADDED` + `MODIFIED`（写内容），按"最后一条"合并就只剩 `Modified`，
而索引里根本没有这个文件。现在的合并表：

| 已有 → 新到 | 结果 |
|---|---|
| Added → Modified | 仍是 Added |
| Added → Removed | 两条都丢（窗口内建了又删） |
| Removed → Added | Modified（同名替换） |
| Renamed → Modified | Renamed（保留 oldPath） |
| 其它 | 用新事件覆盖 |

**3. 溢出必须显式。** `GetOverlappedResult` 失败（`ERROR_NOTIFY_ENUM_DIR` 等）或返回 0 字节时，
推一条 `Overflow{path=根}`，由消费者决定重扫——绝不静默丢事件。

### 验收

```
assistant_watch_tests.exe
Totals: 8 passed, 0 failed  (352 ms)
ctest: 5/5 passed（含 golden / a3 / sync / watch）
```

单测是真目录 + 真 `ReadDirectoryChangesW`，没有桩；注释里写明"事件有合并窗口，断言一律用
`QTRY_VERIFY_WITH_TIMEOUT`"。

### 还差什么（A5 第二半）

- `FileIndex` 订阅 `FileEventDispatcher`，把事件应用到快照（不可变 → 构建新快照）与 `file_index.db`；
- `Overflow` → 触发该根的全量重扫；
- 端到端验收①：新建/改名/删除 ≤100 ms 能在搜索里看到；② 脚本制造大量变更触发溢出且索引收敛。

所以 `v0.4-实施清单.md` 的 A5 现在应读作"事件源完成、接入未做"，不勾成完成。
