# 保险箱：名称加密 + 恢复码 + DEK 模型（v0.6.0）

> 目标：补齐 M3（安全模块）在 Python 原型阶段缺的三项能力，**不改动既有 FGC1 容器格式**，
> 现有 142 个测试的行为完全不变（新增 18 条保险箱用例，全量 160 个测试通过）。

## 1. 为什么需要它

`crypto.py` 的容器是"口令直接派生密钥"，做保险箱时有三个硬伤：

| 问题 | 后果 | 本版本的解法 |
| --- | --- | --- |
| 文件名明文（`合同.docx.fgc`） | 看目录就知道里面是什么，M3 的 NameCipher 缺失 | 容器名 = 随机 32 hex；原文件名只存在**加密清单**里 |
| 没有恢复码 | 忘记口令 = 数据永久不可读，用户不敢用 | 恢复码（32 字符 Crockford Base32）作为第二把钥匙包住 DEK |
| 改口令要重加密所有容器 | 大文件库轮换口令代价高、失败风险大 | DEK 模型：改口令只重新包 DEK，**容器一个字节不动** |

## 2. 架构

```
                   vault.keys.json（只存密文块）
口令 ──PBKDF2──▶ KEK ──AES-GCM──▶ 包裹 DEK ─┐
恢复码 ────────▶ KEK ──AES-GCM──▶ 包裹 DEK ─┤
DPAPI（可选）────────────────────▶ 包裹 DEK ─┤
恢复码明文（备份展示用）──AES-GCM(DEK)──────┤
                                            ▼
                            DEK（32B 随机）作为"口令材料"
                                  │
              ┌───────────────────┼────────────────────┐
              ▼                   ▼                    ▼
     containers/<随机32hex>.fgc  containers/...   names.jsonl
     （FGC1 容器，AES-GCM）      （FGC1 容器）    （DEK 加密 + HMAC 链的名称清单）
```

关键点：

- **容器格式零改动**：DEK 只是作为 `encrypt_file` 的"口令材料"（`bytes`）传入，FGC1 内部仍然是
  PBKDF2(DEK, 每容器随机盐) + 分块 AES-GCM。所以旧的 `encrypt/decrypt/verify` 全部兼容；
- **名称清单复用审计日志内核**：`EncryptedLog` 提供逐条 AES-GCM + 随机 nonce + HMAC 链 + meta 高水位，
  改一行/删一行/回滚都会被 `vault verify` 发现；
- **恢复码不是后门**：它和口令是同一把 DEK 的两条恢复路径；`recovery_code_under_dek` 只用于
  "凭口令重新展示恢复码"，不是额外入口；
- **DPAPI 包裹的是 DEK**（不是口令）：Windows 当前用户免密解锁；换用户/换机器自动失效（预期语义）；
- **keys 文件原子写 + ACL 收紧**：tmp + `os.replace` + `fsync`，Windows 上 `icacls` 收到仅当前用户。

## 3. CLI

```bash
# 1) 创建保险箱（生成恢复码，只显示一次）
python -m file_guard vault init
#   → 返回：目录 / DPAPI 是否启用 / 恢复码（XXXX-XXXX-...×8）

# 2) 放入文件（容器名随机；--remove-source 会在校验通过后删源）
python -m file_guard vault add "合同.docx" "客户名单.xlsx" --note "2026 合同"
python -m file_guard vault list
#   1. 合同.docx      32.0B  2026-11-18T21:48:10+08:00  # 2026 合同

# 3) 取出（按序号 / 容器名 / 原文件名，恢复原文件名与 mtime）
python -m file_guard vault extract 1 -o D:\恢复

# 4) 校验：名称清单链 + 逐个解密容器核对 SHA-256
python -m file_guard vault verify          # --quick 只校验清单链

# 5) 轮换口令（容器与清单不重加密）
python -m file_guard vault passwd --new-password "..."

# 6) 忘记口令：用恢复码解锁，或重新展示恢复码
python -m file_guard vault list --recovery-code "XXXX-XXXX-..."
python -m file_guard vault recovery        # 凭口令重新展示
```

## 4. Python API

```python
from file_guard import Vault

vault = Vault("D:/secure/vault", iterations=600_000)
info = vault.init("口令")                       # 返回 recovery_code（只显示一次）
vault.add_file("合同.docx", note="2026", remove_source=True)
vault.list_files()                              # [{"name": "合同.docx", "size": ..., ...}]
vault.extract(1, dest_dir="D:/恢复")            # 还原原文件名 + mtime
vault.verify(full=True)                         # {"ok": True, "files": 1, "checked": 1}
vault.change_password("旧口令", "新口令")        # 容器不重加密
vault.show_recovery_code("口令")                # 重新展示恢复码
```

## 5. 安全边界（诚实的部分）

**承诺**：

- 磁盘上不出现原文件名（容器名随机，名称清单是密文）；
- 容器/清单被改一行、删一行、截断、回滚都会被 `verify` 检出（GCM + HMAC 链 + meta 高水位）；
- 口令轮换不产生新的明文窗口（只重包 DEK）；
- 删除源文件前先解密校验容器（失败保留源文件）。

**不承诺**（与 M3 设计一致）：

- 运行期内存中无明文（Python 做不到，进程内存/页面文件不保证）；
- SSD/日志/备份里的物理擦除（`Crypto` 层同样只承诺受控临时文件生命周期）；
- 防住"同 Windows 账户的恶意程序"：它可以直接读 `vault.keys.json` + 调 DPAPI；
  真正的对抗需要独立服务/驱动（M3 二期）；
- 恢复码安全由用户离线保管决定：**泄露恢复码 = 泄露保险箱**（UI/文档已明确提示）。

## 7. 与 M3 设计的对照

| M3 要求（`四模块完整架构.md` §6 / `关联与方案.md` §4.3） | 本版本 |
| --- | --- |
| AES-256-GCM 内容加密 + DPAPI 保护的 DEK | ✅ DEK + DPAPI 包裹（`.keys.json`） |
| 名称加密 | ✅ 随机容器名 + 加密名称清单（最小可行形态；M3 正式版建议把名称密文写进容器头） |
| 恢复码（生成/保存/验证/丢失后果） | ✅ 生成、展示、重新展示、恢复码解锁、doc 明确"丢失即不可恢复" |
| nonce 不复用 | ✅ 沿用 v0.3 加固后的"逐条随机 12B nonce + AAD 绑定" |
| 临时明文生命周期 | ✅ 容器层 `.part` + 原子替换；`extract` 只在目标文件落盘 |
| 账本落 `security.db` | ⏳ 原型仍用加密 JSONL；C++ 版按 `security.db` 实现（本模块清单可作迁移输入） |
| 运行期无明文 / 驱动级 | ⏳ 明确不承诺（M3 v1 同样只承诺静止态） |
