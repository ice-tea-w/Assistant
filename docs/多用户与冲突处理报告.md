# 多用户修改与冲突处理报告（v0.4.0）

> 起因：一个很实际的问题——**两个用户改同一份文件时，谁的权限高、谁有修改权、改了哪些内容、模块怎么处理？**
> 这份报告给出权限边界的结论、本次为此新增的代码能力、验证结果和残余风险。
> 范围：`backup.py`（冲突保护 / 版本 diff）、`cli.py`（CLI 与 doctor）、`service.py`（RPC）、`tests/test_extras.py`。

---

## 1. 问题拆成三层

| 层 | 问题 | 由谁负责 |
| --- | --- | --- |
| 操作系统层 | 谁能读/写/删这个文件？ | **Windows ACL / 所有者 / 管理员**，模块不参与判定 |
| 模块层 | 并发修改时会不会产生不一致数据？覆盖别人改动会不会丢数据？改了哪些内容能不能查？ | file_guard（本次补强） |
| 应用层 | 哪个"人"在操作？要不要做编辑锁/提示？ | 桌面助手主程序（PySide/tkinter） |

**结论先讲清楚：模块以当前登录用户的普通权限运行，不提权、不绕过 ACL。**
"谁的权限高"由 Windows 权限决定，与模块无关；模块保证的是"有权限时，加密/备份/留痕正确，覆盖别人的修改不会悄悄丢数据"。

---

## 2. 改前的缺口（为什么需要这次改动）

| 缺口 | 改前行为 | 风险 |
| --- | --- | --- |
| 还原覆盖不检查 | `restore --force` 直接覆盖目标 | A 回滚旧版本会把 B 刚改的内容**静默覆盖** |
| 不知道"改了哪些内容" | 备份只有版本号 + SHA-256，只能判断"变没变" | 出事时无法定位具体改了什么 |
| 数据目录权限没人看 | 只检查"可读写" | 数据目录若被共享（Everyone/Users），同机其他用户可读 token/审计/备份 |

---

## 3. 本次改动

### 3.1 还原冲突保护（核心）

**判定规则**：还原前计算目标文件**当前内容的 SHA-256**，与"该路径所有已备份版本的内容哈希"比较：

- **当前内容命中某个已备份版本** → 内容在库里可找回，属于正常版本回滚，不拦截；
- **当前内容不在任何版本里**（说明备份后被改过、还未入档）→ 判定为冲突：
  1. 先把当前内容**自动备份成一个新版本**（保证不丢数据）；
  2. 默认**拒绝覆盖**，报错提示"目标文件在备份后被修改过且未入档，已自动快照为 vN；确认覆盖请加 `--allow-conflict`"；
  3. 用户显式确认（`--allow-conflict` / `allow_conflict=True`）后才覆盖，并在返回结果里标记 `conflict=true`。

**返回结构新增字段**：`conflict`（是否发生冲突覆盖）、`preserved_current_version`（自动快照的版本号，无则为 null）。

**代码位置**：`backup.BackupStore.restore(..., allow_conflict=False)`、`_auto_snapshot()`。

### 3.2 备份版本差异（`diff`）

- 默认比较：**上一版 vs 最新版**；也可指定 `--from/--to`；
- 文本（≤1 MiB）→ unified diff（最多 400 行，超长截断）；
- 二进制 / 超大文件 → 只给"变了没 + 大小差 + 两版哈希"，不把内容 dump 出来（避免 UI 卡死、也避免把敏感内容二次暴露）；
- 返回结构：`{path, from{version,sha256,size,ts}, to{...}, changed, kind: text|binary|none, size_delta, diff, truncated}`。

**代码位置**：`backup.BackupStore.diff()`、`_materialize()`（解密到临时目录并校验索引哈希）。

### 3.3 doctor 增加"数据目录权限"检查

Windows 上用 `icacls` 读取数据目录 ACL：发现 `Everyone` / `BUILTIN\Users` / `Authenticated Users` 授权时给 **warning**，提示同机其他用户可能读到 token/审计/备份，建议收紧。不影响退出码（warning 不算 error）。

## 4. 改前 / 改后对照

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| A 备份 v1；B 改了文件；A 回滚 v1（`--force`） | 直接覆盖，B 的修改丢失且不可恢复 | 先自动把 B 的内容存成 v2，拒绝覆盖；A 确认后加 `--allow-conflict` 才覆盖，B 的版本仍可回滚 |
| A 备份 v1；没人改；A 回滚 v1 | 直接覆盖 | 内容命中已知版本 → 正常回滚，不打扰 |
| 想知道 B 改了什么 | 只有"sha256 不同" | `backup diff`：文本给行级 diff，二进制给摘要 |
| 数据目录被共享给 Users | 无人察觉 | `doctor` 报 warning |
| 多人同时写同一文件 | 最后写入者生效（OS 行为，不变） | 模块不改变 OS 语义，但"谁改的"由审计 `user/host/pid` 记录，覆盖风险由还原冲突保护兜底 |

## 6. 使用示例

```bash
# 1) 冲突拦截：目标被改过且未入档
$ python -m file_guard backup restore "合同.docx" --version 1 --force
错误：目标文件在备份后被修改过且未入档（可能是其他用户/程序改的）：
     当前 SHA-256 9f2c… 不在任何备份版本里。已把当前内容自动备份为 v2；
     确认要用旧版本覆盖请加 --allow-conflict

# 2) 确认覆盖（当前内容已快照，可随时恢复）
$ python -m file_guard backup restore "合同.docx" --version 1 --force --allow-conflict
[OK] 已还原 合同.docx（版本 1）
     注意：目标文件此前有未入档修改，已自动快照为 v2

# 3) 看两个版本改了什么
$ python -m file_guard backup diff "合同.docx"
v1 -> v2：text 差异，大小 +18 B
--- v1
+++ v2
@@ -1,2 +1,2 @@
-第一版
+第二版（未入档）
```

```python
from file_guard import BackupStore

store = BackupStore("~/.file_guard/backups", password)
info = store.restore("D:/docs/合同.docx", version=1, overwrite=True, allow_conflict=True)
print(info["conflict"], info["preserved_current_version"])   # True 2
diff = store.diff("D:/docs/合同.docx", from_version=1, to_version=2)
print(diff["diff"])
```

HTTP（服务模式）：`restore` 增加 `"allow_conflict": true` 参数；新增 `{"method":"backup.diff","params":{"path":"...","from_version":1,"to_version":2}}`。

## 7. 兼容性说明（升级须知）

- **默认行为变严**：以前 `restore --force` 会静默覆盖任何内容；现在如果目标内容未入档，会拒绝并要求 `--allow-conflict`。依赖"静默覆盖"的自动化脚本需要补一个参数。
- 返回结构**只增不改**：新增 `conflict` / `preserved_current_version` 字段，旧字段保持不变。
- 备份索引格式不变，旧的备份目录无需迁移。

## 8. 残余风险与后续建议

| 风险/缺口 | 说明 | 建议 |
| --- | --- | --- |
| 不知道"哪个进程/哪个人改的" | 轮询监听只能拿到变更事件，拿不到进程信息 | 二期用 Windows ETW（`Microsoft-Windows-Kernel-File`）关联进程与用户；或由主程序在打开文件时 `audit.record(..., actor=用户)` |
| 应用层多用户身份 | 模块只有 Windows 账户维度 | 主程序调用时传 `actor` 字段（`audit.record(..., actor="张三")` 已支持 `**extra`） |
| 真正的"编辑锁" | 模块不做跨用户互斥（那是 OS/Office 的事） | 需要时由应用层加"打开前申请锁"，锁事件写审计 |
| 字段级合并 | 只做版本快照 + diff，不做三路合并 | 多人协作建议用 Git/文档协作平台，模块负责"加密 + 留痕 + 可恢复" |
| 共享数据目录 | 一个 home = 一个口令 = 一个信任域 | 多用户各用各的 home；`doctor` 已能发现 ACL 过宽 |
| 完整回滚 | 原子快照/覆盖都基于本地文件 | 需要更强保证时用 `log head` 外部锚点 + 代码签名 |

---

## 9. 一句话总结

> 文件修改权由 Windows ACL 决定，模块不提权；它新增的是**"覆盖别人改动前必须先检测、先快照、再确认"**和**"版本之间改了什么可以看 diff"**——把"最后写入者获胜"的 OS 语义，变成了"覆盖有提示、内容可追溯、数据不会悄悄丢"。
